## 4. THE REVERSAL'S COST — the best bound I could find, and whether the outage is visible
The reversal: future-beyond-tolerance refuses (exit 0, nothing written) until a person deletes the file or corrects the writer timepiece — unbounded for a dead file left ahead. The source's argument: a stateless mtime read cannot tell a live holder with a fast writer timepiece from a dead file left ahead, so one error must be chosen; refusing takes the visible error over a silent overlap (tree rewritten under a running gate that nothing announces and nobody diffs).

Best bound I could find: none from anything the system currently records. The engine keeps no lease history (no first-seen stamp, no touch log; `checkLease` is pure over one `stat` plus `Date.now()`, no caller passes `opts`), so no bound computes from engine state without adding one. The file's contents do not help (advisory by design): identical-input probe (`probe-bound.mjs` under the OS temp area, pinned `nowMs 1720000000000`, `mtimeMs` one hour ahead) returns `future` for holder `live-fast` and `future` for holder `dead-ahead` — `live=future dead=future same=true`. Different contents, same verdict. Nothing else in the tree observes harness touching (snapshots, `changes.jsonl`, linkcheck, freshness, queue all record the world, not the lease). Any deterministic rule on `(mtime, now)` that proceeds for a dead file 1h ahead proceeds for a live holder 1h ahead at the same instant; the probe is that proof in miniature, and the source's "at any instant the two look identical" is correct. A stateful bound (record first-seen future mtime, refuse while it moves, proceed once proven untouched across runs) could work but costs a write on today's write-nothing refusal path, a second timepiece to be skewed, and its own silent-overlap window on the (N+1)th firing — new machinery for a bounded-but-clever outage over today's unbounded-but-simple one. Not built (read-and-measure scope), not recommended blind. A design that survives this attack is worth more than one nobody attacked; the attack confirms the core claim.

Is the outage actually visible? The refusal prints one line to the run's own stdout and exits 0. What would surface a stopped Pulse: the loop queue reader warns only on missing or invalid JSON, never on age (`loop/lib/queue.mjs`); none of the four Desk breakers fires on a stale queue or an absent Pulse (`loop/lib/breakers.mjs`: consecutive-failures, build-or-deploy-red, review-bypass, reserved-path); freshness measures corpus-date intervals, not Pulse liveness; the refusal exits before build/publish so no `HOLD.md` is written or re-tested; the scheduler's exit-code signal cannot distinguish refused (0) from done (0) — the exit-race note in `run.mjs` names that code the unattended engine's only signal. The one signal that moves is the live site's `/status.json` build stamp going stale, and this repository's own stated check for exactly that (two consecutive scheduled runs with identical stamps mean publishing is broken whatever the logs say) is a manual observation, not an automatic surfacing. Finding: "announces itself on every run" is true of the run log and false of every mechanism in the tree. A dead future lease yields on each firing a line nobody pages on, a code nothing alarms on, a queue going stale that nothing ages, and a site going stale that only a human comparing stamps notices.

## 5. WHAT THIS SUITE CANNOT SAY, with a constructed example
It proves what a fixed mtime does. The only case where refusing is unambiguously correct — a holder that keeps touching the file — is conduct across time, which no trial watches. Every timing trial pins one mtime and asserts one run; touching is dismissed as conduct in `RESULT3.md` and never exercised. The missing pair, run live (`probe-renew.mjs`, throwaway root, `--no-build --no-mint --offline`, holder `live-holder`): mtime 14 minutes old → `pulse: GATE_LEASE present at ... (age 840s, holder live-holder) — a gate run holds the tree, refusing this run, nothing done.`, exit 0, no queue; same file at 16 minutes old → `pulse: WARN stale GATE_LEASE at ... (age 960s exceeds max 900s) — disregarding it and proceeding; holder live-holder may have died without releasing.`, queue written; retouched to 60s → refuses again. Each run is individually exactly what the suite pins — and the pair is the hole: a holder that touches once, runs 20 minutes without retouching, and is still live at minute 16 is overlapped by the second run with every trial green. At any instant "dead, safe to disregard" and "live but forgot to touch" are the same fixed mtime, and the suite never looks twice. The future side mirrors it (live-fast vs dead-ahead, section 4): the suite proves the refusal, never its correctness, because correctness lives in harness touch discipline outside this repository.

Same shape, smaller: "writes nothing" means no `queue` line and no `data/derived/queue.json` (lease left standing) — a refusal additionally writing `data/derived/marker.json` is 36/0 green (section 3). And the 90s magnitude literal is timing, not logic: on the restored byte-identical baseline I observed `mtime 89s ahead of now` where the trial demands `mtime 90s ahead of now` (spawn delay past the rounding half-second), 35/1 with nothing mutated, then 36/0 on immediate re-run. `RESULT3.md`'s claim that sub-second spawn delay cannot flip the rendering holds for the state (89s is still future) but not for the exact-second literal.

## 6. THE NEW CONSTANT — display-only, checked
`LEASE_AHEAD_DISPLAY_THRESHOLD_S = 120` in `pulse/run.mjs` with `formatAheadDuration`: below it whole seconds (`90s`, `100s`), at or above it two largest whole units (`2m 30s`, `1h 0m`, `1d 0h`, `10y 0d`). Display-only holds three ways. It is read in exactly one place (the future line's `aheadText`); `checkLease` never imports it, and refuse/proceed passes only through `ageMs` vs the two ms constants. Tenfold mutation (120→1200) gives 35/1 with the single failure `display threshold, above` (`actual 'mtime 150s ahead...'` vs `expected /mtime 2m 30s/`) — still refuses as future, nothing written, exit 0. Safety did not move; only bytes for a person moved. What pins the value: the 100s-below and 150s-above live trials straddling 120 with 20s/30s margins, and nothing else — the helper is not exported, has no unit test, the exact edge (119/120/121) is never tried. Drift 120→140 stays 36/0 green. The unpinned-constant finding recurs here in miniature: the kind (seconds vs units) is pinned from both sides, the number drifts anywhere in 101–150 green. Acceptable given display-only is proven — but label it taste-with-margins, not a measured pin, which the source comment already half does.

## 7. WHAT IS SOUND and should not be touched
The refusal decision itself: future-beyond-tolerance refuses under its own line, exit 0, nothing written — indistinguishability is real (my probe reproduces it), proceed-past-tolerance was correctly ruled indefensible, and the reversal puts the error where a reader can meet it. The demotion of the tolerance to diagnostic-only (both sides refuse; the number picks the sentence, not the outcome) dissolves rather than re-tunes the dangerous constant. Strict millisecond edges with injection pins (max vs max+1, tolerance vs tolerance+1, newly-written through max-to-stale) are exact and bite at 10x on both constants plus the divisor. The mtime-authority / contents-advisory split holds across empty, garbage, holderless JSON (honest `unnamed` instead of printing the blob), plain text, directory, megabyte, thousand-line, and over-long-holder trials. STOP-first for the tested combination, the distinct `future` head with measured magnitude plus named tolerance, and the conditional remedy (delete-only-when-idle or fix the writer timepiece, never widen) are the right words — section 2 shows them under-enforced, not misworded. None of the revise items require reopening any of this.
