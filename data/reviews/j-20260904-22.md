## Finding 1 — the sentence rewrite (carried finding j-20260903-08-carry-1): clean

The carried finding named two grammatical defects: `but … but` in one sentence,
and `lists … no deprecation notice anywhere on the page`, where `lists` cannot
govern that clause and `anywhere on the page` fights the `under it` scope it is
coordinated with. Both are gone. The new sentence coordinates
`still identifies itself … — but its variant list now holds only the free and
standard groups …; nothing anywhere on the page announces a deprecation`, which
puts the deprecation clause under its own verb and gives `anywhere on the page`
its own scope instead of a borrowed one. That is the repair as specified.

I checked the factual half against the live page rather than trusting the
carried finding's measurement. `GET https://openrouter.ai/nvidia/nemotron-3-ultra-550b-a55b:batch`
returned `200`, 293246 bytes, fetched on 2026-09-04. Parsing the embedded RSC
payload (unescaping `\"` before matching, because the raw HTML escapes the JSON
and a naive search for `"batch"` returns zero — my first pass made exactly that
instrument error):

- **`variantGroups` holds only `free` and `standard`.** Every `"variant":"<name>"`
  occurring after the `variantGroups` key is `free` (the group header and its one
  endpoint) or `standard` (the group header and its four endpoints). There is no
  `batch` group. The author's "its variant list now holds only the free and
  standard groups, with no batch group and so no providers or pricing at all" is
  exact, and matches the carrying reviewer's independent parse.
- **The page still names itself batch in three places.** The rendered heading —
  `<h3>…<a href="/nvidia">nvidia</a>/nemotron-3-ultra-550b-a55b:batch</h3>` — and
  the payload's own
  `"modelSlug":"nvidia/nemotron-3-ultra-550b-a55b:batch","canonicalModelSlug":"nvidia/nemotron-3-ultra-550b-a55b:batch"`,
  and the uptime/stats query keys, which carry
  `{"permaslug":"nvidia/nemotron-3-ultra-550b-a55b-20260604","variant":"batch"}`.
  So "the slug and the page's own variant state both name it" is supported. The
  author narrowed the carrying reviewer's "the slug, the heading and its uptime
  queries" to a shorter phrase; all three of the reviewer's originals are still
  there, so the narrowing understates the page rather than overstating it.
- **No deprecation is announced.** Every deprecation field on the page is null:
  one `"deprecationDate":null` on the model header and five
  `"deprecation_date":null`, one per endpoint. "nothing anywhere on the page
  announces a deprecation" holds.

That is the job's headline repair, and it is both grammatically and factually
sound.

## Finding 2 — the HTML comment (carried finding j-20260903-20-carry-1): BLOCKING

The added comment reads:

```
<!-- The $0.60 / $0.625 / $2.40 / $3.125 literals in the paragraph above
cannot be transcluded: the bound batch row is gone (its last-known values
date 2026-09-02), and data/derived/feed-rows.json holds no pricing key for
nvidia/nemotron-3-ultra-550b-a55b:batch — deliberate, not rot. -->
```

Three claims. The third is true. The first two are not.

### 2a. The literals are the STANDARD row's prices, not the batch row's

The sentence the comment annotates says so in its own words: "including **the
standard row's** price, whose prompt rate fell from $0.625 to $0.60 and whose
completion rate fell from $3.125 to $2.40 per million tokens." The comment
attributes them to "the bound batch row".

Measured against `data/derived/feed-rows.json` (a script reading the JSON, not a
grep):

```
--- nvidia/nemotron-3-ultra-550b-a55b $as_of,$status,$vanished,architecture,benchmarks,canonical_slug,context_length,created,default_parameters,description,expiration_date,hugging_face_id,id,knowledge_cutoff,links,name,per_request_limits,pricing,reasoning,supported_parameters,supported_voices,top_provider
pricing: {"completion":"0.000003125","input_cache_read":"0.0000001875","prompt":"0.000000625"}
--- nvidia/nemotron-3-ultra-550b-a55b:batch $as_of,$status,$vanished
pricing: undefined
```

`0.000000625` × 1e6 = **$0.625/M** and `0.000003125` × 1e6 = **$3.125/M** — two
of the four literals are the standard row's *current, live* prices, on a row
whose `$vanished` is `false` and whose `$as_of` is `2026-09-04`.

### 2b. "cannot be transcluded" is false for those two

`content/wiki/model/nvidia-nemotron-3-ultra-550b-a55b.md` exists and binds
`price_input` → `pricing.prompt` and `price_output` → `pricing.completion` on
that live row. The corpus already transcludes exactly those facts across
entries: `content/wiki/org/nvidia.md:121` and `:123` hold
`{{fact:model/nvidia-nemotron-3-ultra-550b-a55b#price_input}}` and
`#price_output`. So the transclusion the currency-literal warning advises —
`{{fact:<kind>/<slug>#<field>}}`, which takes any slug, not only the page's own
— is available for $0.625 and $3.125 today. The batch row's absence has no
bearing on them.

There *is* a legitimate reason two of these four resist transclusion: a "fell
from X to Y" pair is a dated historical diff, and the from-value has no live
binding by construction. That is not the reason the comment gives.

### 2c. The 2026-09-02 date no longer holds at HEAD

The comment says the batch row's "last-known values date 2026-09-02". The
carrying reviewer measured `$as_of 2026-09-02` at commit `cb47c21`. At HEAD the
row is:

```
{"$as_of":null,"$status":null,"$vanished":true}
```

`$as_of` is `null` and there are no values at all. Tracing what the page
actually renders: `lib/facts.mjs:141-147` computes `missing` (the `pricing` path
is absent → `undefined` → `missing`), so `resolveFact` returns `{state:
'vanished', value: null, asOf: null}`; `lib/facts.mjs:271-276` then renders

```js
const value = r.value == null ? ABSENT : quantity(r.value);
inner = value + `<span class="fact-as-of" role="note">last known value, as of ${escapeHtml(r.asOf ?? 'an unrecorded date')} — the source no longer lists this row</span>`
```

— i.e. **"not published … last known value, as of an unrecorded date"**. So at
HEAD the page's bound facts render neither a last-known value nor the
2026-09-02 date. (The same is true of the page's pre-existing line 42-43, "The
bound facts above render their last-known values as of 2026-09-02", which the
diff did not touch and which the new comment now reinforces.)

### Why this blocks rather than carries

The comment's entire function is to tell the next author and the next reviewer
*not to fix* these four numbers — "deliberate, not rot". A note that does that
while naming the wrong row, giving a reason that does not hold for half the
values, and citing a date the data layer no longer carries, converts a
correctable warning into a standing instruction to leave it alone. That is the
one kind of error a maintenance comment can make that is worse than no comment.

## Required changes

1. Attribute the literals to the row the sentence attributes them to — the
   standard row `nvidia/nemotron-3-ultra-550b-a55b`, which is live — not to the
   vanished batch row.
2. Either transclude $0.625 and $3.125 with
   `{{fact:model/nvidia-nemotron-3-ultra-550b-a55b#price_input}}` and
   `#price_output` (which `content/wiki/org/nvidia.md` already demonstrates), or
   state the real reason they stay literal: they are the two halves of a dated
   historical price move, and a from-value has no live binding.
3. Drop or correct "(its last-known values date 2026-09-02)" — at HEAD
   `feed-rows.json` carries `$as_of: null` and no pricing for the batch row, and
   the page renders "as of an unrecorded date".

The two carried files are correctly deleted in the same diff, which is what
retires the queue items, and the diff touches nothing outside the target file
and those two deletions — no scope problem.
