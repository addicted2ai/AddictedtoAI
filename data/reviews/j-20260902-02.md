Free-form notes.

## Scope

The diff adds one line to `data/changes.jsonl` plus the two loop-generated
`.job/` files. Nothing existing is edited; the file stays append-only. No entry
file is touched, which is the right call under `addictedtoai-ij4h`:
`content/wiki/model/z-ai-glm-4-5v.md` has no prose body and binds `status` to
`path: $status` on the `openrouter-models` feed, so it is a STUB whose status
derives from the router and needs no authored change. No scope violation.

## What I verified, and how

**The snapshot claim — confirmed.** Read both snapshots with a script over
`data/sources/openrouter-models/{latest,previous}.json`:

```
=== latest.json fetched_at= 2026-09-02T06:00:03.835Z n= 421
{"id":"z-ai/glm-4.5v",...,"expiration_date":"2026-12-31","context_length":65536,
 "pricing":{"completion":"0.0000018",...,"prompt":"0.0000006"},...}
=== previous.json fetched_at= 2026-09-01T06:00:03.724Z n= 420
{"id":"z-ai/glm-4.5v",...,"expiration_date":null,...}
```

The field is present on 2026-09-02 and absent on 2026-09-01, as written. The
word "again" is also earned: `data/changes.jsonl:86` records the reverse flip
(`old: "deprecated"` → `new: "active"`) on 2026-08-29.

**The derivation claim — confirmed.** `pulse/lib/diff.mjs:116-132`,
`deriveStatus`: a non-null `expiration_date` within `deprecated_within_days`
(365) yields `deprecated`. 2026-12-31 is 120 days out, so `deprecated` is what
the rule produces, and the annotated change line's own excerpt carries
`"$status":"deprecated"`. The annotation attributes this to "this site's
expiration-date rule" rather than to OpenRouter, which is the correct
attribution and the hardest thing to get right here.

**The quoted definition — confirmed verbatim, from the machine-readable spec
rather than the rendered docs page.** `https://openrouter.ai/docs/api-reference/list-endpoints-for-a-model`
returns 404, so I pulled `https://openrouter.ai/openapi.json` (1,888,360 bytes)
and read the schema directly:

```
$.components.schemas.Model.properties.expiration_date =>
{"description":"The date after which the model may be removed. ISO 8601 date
string (YYYY-MM-DD) or null if no expiration.","example":"2025-06-01",
"type":["string","null"]}
```

`"may be removed"` occurs exactly once in the whole document, at that key. The
annotation's quotation is exact.

**"Both endpoints still serve it" — substantially true, with a caveat the
annotation elides.** `GET https://openrouter.ai/api/v1/models/z-ai/glm-4.5v/endpoints`:

```
Novita  status=0   uptime_last_1d=97.03   ctx=65536
Z.AI    status=-2  uptime_last_30m=91.18  uptime_last_1d=98.76  ctx=65536
```

Both are listed and both report recent uptime, so "still serve it" holds. But
the Z.AI endpoint carries `status: -2`. `$.components.schemas.EndpointStatus`
in the OpenAPI spec is `{"enum":[0,-1,-2,-3,-5,-10],"example":0}` with no
semantics attached, and I could not find OpenRouter documentation defining the
negative values — so I cannot say what -2 means, only that it is not the
normal 0 that Novita has. Not a blocker (the uptime figures show it serving),
but see the required changes.

## The required change

**The closing migration recommendation is contradicted by the very snapshot
the annotation was written from.** The annotation ends:

> "the current next-generation vision model in Z.ai's line is the active
> `z-ai/glm-4.6v` (131K context, $0.30/$0.90 per 1M vs GLM-4.5V's $0.60/$1.80
> on OpenRouter)"

The three numbers are right — `z-ai/glm-4.6v` in `latest.json` has
`context_length: 131072`, `pricing.prompt: 0.0000003`, `pricing.completion:
0.0000009`, and GLM-4.5V's are `0.0000006`/`0.0000018`. The *recommendation*
is not. Enumerating every `z-ai/` row in the same file:

```
z-ai/glm-4.6v        131072  0.0000003   0.0000009   exp=null        created=2025-12-08  mods=["image","text","video"]
z-ai/glm-5v-turbo    202752  0.0000012   0.000004    exp=2098-12-31  created=2026-04-01  mods=["image","text","video"]
z-ai/glm-5.3-flash  1310720  0.000000075 0.00000025  exp=2098-12-31  created=2026-08-26  mods=["text","image","video"]
```

GLM-4.6V was created 2025-12-08. `z-ai/glm-5v-turbo` — the next model in the
same "V" naming line the sentence appeals to — is four months newer, and
`z-ai/glm-5.3-flash` is nearly nine months newer, vision-capable, and eight
times cheaper on input. Both derive `active` (the `2098-12-31` sentinel yields
`active`; `pulse/tests/diff.test.mjs:125` asserts exactly that). Both have
entries in this corpus already (`content/wiki/model/z-ai-glm-5v-turbo.md`,
`z-ai-glm-5-3-flash.md`). I checked GLM 5V Turbo live as well:

```
z-ai/glm-5v-turbo | Z.ai: GLM 5V Turbo
  Z.AI status= 0 ctx= 202752 up1d= 100
```

So "current" is wrong and "next-generation" is wrong, and they are wrong in
the one sentence that answers the reader's stated question — what should I use
instead. A reader who follows it migrates from a model with a December
expiration date onto one that is itself two generations behind. Note also that
`~z-ai/glm-flash-latest` (also image/video-capable) arrives in the *same*
2026-09-02 diff, three lines above the annotated change; the newer options
were not merely in the snapshot, they were in the immediate neighbourhood of
the line being interpreted.

No Z.ai source is cited anywhere in the annotation, and the brief asked for
Z.ai's own published sources — the successor claim is precisely the one that
needed one, and it has none.

**To revise:** either (a) name the actual current active vision-capable Z.ai
rows from the snapshot, with a Z.ai or OpenRouter source for any lineage claim
about which one supersedes GLM-4.5V, or (b) drop the successor sentence
entirely and say only what the feed supports — that the model remains callable
and carries a 2026-12-31 expiration date. Option (b) is a complete, honest
annotation; "I could not establish the successor from published sources" is a
better line than a wrong one.

## Two smaller things, fold them into the same revision

1. **"plan around the 2026-12-31 removal date"** hardens into a certainty the
   very word the annotation just quoted. OpenRouter says the model *may* be
   removed after that date, and this row's own history shows the field is not
   stable: it was present before 2026-08-29, absent on 2026-08-29, and back on
   2026-09-02. "Removal date" should read as the scheduled-earliest date it
   is.

2. **The flap is the most interesting fact here and the annotation nearly
   hides it.** `data/changes.jsonl:90`, the annotation on the 2026-08-29 flip,
   called the field's disappearance "a metadata correction". If that reading
   was right, this reappearance is the correction being reverted — and a
   reader deciding whether to migrate deserves to know the signal has moved
   twice in four days. One clause naming the 2026-08-29 line would do it, and
   it is the difference between reporting a status and interpreting one, which
   is what an `interpret` job is for.

## What I did not check

Whether an actual inference request to `z-ai/glm-4.5v` succeeds. That needs a
credential, and manipulating or supplying one is forbidden here. The endpoint
listing plus its uptime figures is the closest available measurement, and it
is what the annotation should cite for the callability claim — the site's own
`latest.json` is the `/api/v1/models` response and contains no endpoint data,
so a later reader has nothing in-repo to check that sentence against.
