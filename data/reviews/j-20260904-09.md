## Two mechanism checks I ran rather than assumed

**Does this verdict need a `reads-human` field?** The subject is a blog post,
which made this worth checking rather than reading off the brief's template.
It does not: `loop/lib/review.mjs:61` scopes the requirement to the JOB type,
not the file —

```
export const READS_HUMAN_TYPES = Object.freeze(['post']);
```

and this job's `.job/source.json` records `"type": "repair"`. The brief's
front-matter template correspondingly carries no `reads-human` key, which
`loop/tests/review-blog-bar.test.mjs:332` asserts is the case for every
non-post type. Omitting it is correct and cannot be refused.

**Does editing an approved post strand its review record?** The post is bound
by `data/reviews/j-20260904-05.md`, whose front matter carries

```
reviewed:
  "content/blog/ifm-k2-horizon-open-fleet.md": "f36068757e00d1e5...f747efde"
```

and specs/review requires `verify-launch` to FAIL on a mismatched piece. So a
repair on reviewed content looks, from the branch, like it breaks the launch
check. It does not: `writeRecordSubjects` in `loop/lib/review.mjs:849-861`
re-hashes each subject **from the merged tree** and writes `reviewed:` into
this job's own record after the merge — "the normal path writes `reviewed:`
after the merge, not before it". The rebinding is the merge's job, not this
diff's, and its absence here is the designed state rather than a defect. I did
not re-run `verify-launch` on the branch, because on this branch it would be
measuring the pre-merge state and its answer would mean nothing either way.

I did not re-run `npm test` or `npm run build`; the loop records both PASS on
`df69dd843244`, the commit this diff was computed from.
