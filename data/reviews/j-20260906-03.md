### The two things the brief said the entry must carry, and does not

The brief states the entry must carry a `feeds` map ("the join the board relies
on") and `publishes_from`. It carries neither. I measured both before treating
that as a defect, and neither is one.

**`publishes_from` cannot be authored today.** `entrySchema` in `lib/schema.mjs`
is `.strict()` (line 223) and declares no such key. Parsing this entry's front
matter:

```
as authored                         -> valid: true
+ publishes_from: [nousresearch.com] -> valid: false
    [{"code":"unrecognized_keys","keys":["publishes_from"],"path":[],
      "message":"Unrecognized key: \"publishes_from\""}]
+ feeds: {openrouter-models: ...}    -> valid: true
```

The field lives only in the pending `separate-a-claim-from-a-fact` delta, which
the brief quotes as though it were live. Declaring it would have failed the
build. The omission is forced, not careless. (This is the proposal above.)

It is also not needed for correctness here. `orgNameTokens` normalises
`display_name` "Nous Research" to `nousresearch` and adds the word `nous`,
dropping `research` as a generic corporate token; the alias "NousResearch"
yields `nousresearch` again. The registrable label of `nousresearch.com` — and
of `portal.nousresearch.com`, which reduces to the same registrable domain — is
`nousresearch`, so `isVendorSourced` already returns true for every
vendor-hosted source this entry cites. The domain that *would* need declaring is
`psyche.network`, and nothing in the entry cites it.

**`feeds` is not what the board joins on.** `lib/render/frontier.mjs`'s
`matchProviders` (line 50) matches catalog `provider` ids against the org's
`display_name` and aliases by normalised substring — no `feeds` map is read
anywhere in that module. Running the real `boardCoverage` against this org and
`data/derived/catalog.json`:

```
boardCoverage for org/nous-research alone:
{"orgsTotal":1,"orgsWithRow":1,"orgsWithoutRow":0,
 "providersTotal":58,"providersMatched":1, ...}

catalog rows with provider=nousresearch: 4
   model/nousresearch-hermes-3-llama-3-1-405b
   model/nousresearch-hermes-3-llama-3-1-70b
   model/nousresearch-hermes-4-405b
   model/nousresearch-hermes-4-70b
providers containing "nous": [ 'nousresearch' ]
total distinct providers: 58
```

The row binds: one org, one provider matched, four rows — not blank. The four
`entry_id`s are exactly the four model ids in the entry's `mentions`. The
`providersTotal: 58` also confirms the brief's own figure. And the `shared`
alias "Nous" over-matches nothing: `nousresearch` is the only provider in the
catalog containing the substring.

Separately, the wiki spec requires a `feeds` map of "an entry that binds any
fact to a feed". This entry binds none — all fifteen facts are `source: cited` —
so no map is owed.

### Aliases

`linkable = record.claims.length === 1 && claims[0].class === 'exclusive'`
(`lib/aliases.mjs:69`). `shared` and `manual` are both non-linkable, so classing
the bare "Nous" as `shared` means the wrap-only linker will never wrap the word
in prose — which is the right call for a name that is also a Greek noun and a
British colloquialism. Only the unambiguous "Nous Research" is `exclusive`.
Sanely classed.
