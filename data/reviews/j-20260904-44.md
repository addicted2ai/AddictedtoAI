## What the diff claims, and the check that would be red if it were false

Three claims are load-bearing: (a) git really refuses a `worktree add` at a path
whose admin entry is stale, (b) the prune inside `addWorktree` really makes that
same call succeed, and (c) the prune cannot disturb a live worktree — the reason
the comment gives for preferring `prune` over `add -f`. All three are asserted by
the new test file, so the check is running that file, not the suite the loop
already ran.

    git --version
    git version 2.40.0.windows.1
    node --version
    v24.13.0

The version matters: the comment and the test docblock both name
`git 2.40.0.windows.1`, and that is the git this machine has, so the measurement
and the environment agree.

    node --test .../loop/tests/worktree-add.test.mjs
    ✔ GIT REFUSES a worktree add at a path whose stale entry was never pruned (702.1606ms)
    ✔ THE REVIEWER FORM SUCCEEDS anyway — addWorktree prunes before it adds (926.6899ms)
    ✔ THE RESUMED-JOB FORM SUCCEEDS TOO — the killed run is always a resume (886.0202ms)
    ✔ CONTROL — the prune does not disturb a LIVE worktree at another path (6079.5111ms)
    ℹ tests 4  ℹ pass 4  ℹ fail 0

The first test is the without-the-fix measurement and it is not redundant with
the others: it issues `git worktree add --detach <dir> <branch>` directly — the
exact argument vector `addWorktree` builds in its `detach` branch — and asserts
`ok === false`, `status === 128`, and stderr matching
`/missing but already registered worktree/`. Each test builds its own repository
(`makeRepo` per test), so the second test's success cannot be an artefact of the
first test's failed attempt. The pair is therefore a genuine before/after on one
variable, which is the difference between this and a test that would pass with
the prune line deleted.

The setup helper guards itself — it asserts `worktree list --porcelain` reports
`prunable` before any test proceeds — so a git that stopped producing the stale
state would fail loudly rather than let the rest pass vacuously.

## Whether the fix covers what the finding named

The carried finding named `review.mjs:712` and `run.mjs:912`, and offered two
fixes: a `gitTry(repo, ['worktree','prune'])` before each `addWorktree`, or a
trailing prune in `review.mjs:752`. The diff took a third position — one prune
inside `addWorktree` itself. Checked that this actually covers the named sites
rather than merely sounding like it does. Grepped every `addWorktree` call in
the tree; there are exactly three outside the tests, and each one deletes the
directory immediately before calling:

    loop/conformance.mjs:284  rmSync(dir, …)      → :287 addWorktree(…, { create: true })
    loop/run.mjs:912          rmSync(worktree, …) → :913 addWorktree(…, { create: !resumed })
    loop/lib/review.mjs:712   rmSync(reviewDir,…) → :716 addWorktree(…, { detach: true })

So the comment's "Every call site deletes `dir` before calling this" is
measured, not assumed, and both forms the Desk actually uses — the reviewer's
detached checkout and the resumed job's branch checkout — are the two forms the
second and third tests exercise. The third test's premise also holds: a run that
hits this state is by construction a resume (the branch exists), so `create` is
false, which is the path tested.

The comment's other factual claim — that a run reaching cleanup already prunes
on its way out — is `loop/run.mjs:1366-1367` (`rmSync(worktree, …)` then
`gitTry(ctx.repoRoot, ['worktree','prune'])`), present and unchanged by this
diff. Nothing in the comment is written from intent; each sentence points at a
line that is there.

## The one thing I looked for and did not find a problem with

An unconditional prune at the top of `addWorktree` is repo-wide, not
path-scoped, so I checked whether it could remove something that should have
survived. It cannot remove a registration whose directory exists — the control
test measures exactly that, asserting the live worktree is still registered on
its branch, still has a `.git` on disk, and is still usable from inside after
the prune runs. The only entries it removes are ones whose directory is already
gone, which is the state that was breaking the add in the first place.
