**The premise the fix rests on.** `removeWorktree` (`loop/lib/git.mjs:95-98`)
really does prune *before* the `rmSync` at `run.mjs:1366` gets its turn, so the
ordering defect the comment describes is the code as it stands, not a
hypothetical. The new prune is the same command already issued one line
earlier, so it introduces no side effect that was not already in the run.

**The test.** The new case constructs the state by deleting the directory
without ever removing the worktree, and says so in its own comment rather than
implying it drove `run.mjs` into it — an honest construction, and git cannot
distinguish the two routes because it answers from `.git/worktrees/`, not from
the filesystem. Its assertions are the same three facts I measured
independently above. The two lines added to the end-to-end test assert no
`prunable` entry and no entry naming the job survive a healthy run; those pass
with or without the fix (a successful `remove --force` self-cleans), so they
are a guard rather than a regression test for this line — which is what their
comment claims they are, and no more.
