This is a claim about what the build does, which is the `intent-not-measurement`

`pulse/lib/derive.mjs:113-126` reads exactly two snapshots and no more:

```js
const inLatest = latest?.rows?.[b.row_id];

```

The batch row is absent from both (`latest` 2026-09-04, `previous` 2026-09-03 —
confirmed above), so it takes the `null` branch. `data/derived/feed-rows.json`

unrecorded date". So the page renders no dated last-known value, and the stated

## Why I am not filing a proposal

The obvious one presents itself: a vanished row's last-known values survive
only as long as the one-deep `previous` window, after which the page silently
degrades to "as of an unrecorded date" — even though the values are still
recoverable from `changes.jsonl` and from the pinned `data/vanished/` record.
That looks like a `machinery` job.

It is already filed. `data/vanished/README.md` names it: *"It does not change
how any page renders; an entry whose row has rotated out still renders its bound
facts as absent, and that half of `addictedtoai-64fk` is still open."*
`pulse/lib/vanished.mjs`'s pinning is the answered half of the same issue.
Proposing it again would spend a cooling window re-filing a known open bead, so
the field is empty — which the brief says is the normal case.
