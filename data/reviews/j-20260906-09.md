## The brief's two structural demands — measured, not assumed

The brief states the entry "MUST carry or the row is blank" a `feeds` map and a
`publishes_from` list. The entry carries neither. I checked whether that is a
defect and concluded it is not — in both cases the brief describes machinery this
repository does not have.

**`feeds` is not the board's join.** `lib/render/frontier.mjs:50 matchProviders`
joins an org to its catalog providers **by alias**, with an explicit comment
saying so ("by alias — never a hand-authored mapping"). No org entry in the corpus
carries a `feeds` key at all — `grep '^feeds:' content/wiki/org/` returns no
files across all 24 entries. I replicated `matchProviders` against the committed
`data/derived/catalog.json` for this entry's alias set:

```

newest row (board "Current model"): created= 1736489872 = 2025-01-10T06:17:52.000Z

```

The row is not blank: the exclusive alias `Microsoft` matches provider
`microsoft`, picks up both catalog rows, and resolves a Current model. This also
independently confirms the entry's closing prose claim — that the board's newest-
model column reads the OpenRouter `created` timestamp, the last of phi-4's three
birthdays. That is a claim about what the renderer does, and it measures true.
(58 distinct providers also matches the brief's own figure.)

**`publishes_from` is unimplemented, and declaring it would fail the build.** The
string appears nowhere in `lib/` — the field belongs to the in-flight change
`separate-a-claim-from-a-fact`, which has not landed. Front matter has a closed
key list, so an unknown key is a build error; the author could not have added it.
It would also be redundant here, which is the more interesting half:
`orgNameTokens` (frontier.mjs:254) adds the normalised whole `display_name`, so
`microsoft` is a name token, and `isVendorSourced` (:329) passes any host whose
registrable **label** is a token. `microsoft.ai` reduces to label `microsoft` and
passes on the named branch without any declaration. The FM-N6 failure the brief
warns about — a real vendor claim rendering as an honest-looking blank — does not
arise for a vendor whose brand domain is its own name. Separately, there are no
`content/claims/` records in this diff and the amendment forbids constructing a
claim from an entry's facts, so nothing here reaches that column either way.
