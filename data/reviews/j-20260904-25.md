# The mechanics: does a second annotation on one key actually render?

This mattered enough to check, because the annotation opens "Follow-up to the
annotation above" — which is false if the second line replaces the first.

`lib/changes.mjs:194-218`, `changedFeed`: annotations accumulate into a
`Map` of **arrays** (`if (!annotations.has(l.annotates)) annotations.set(...,
[]); annotations.get(l.annotates).push(...)`), then attach as
`annotations.get(l.key)`, sorted by date. Both annotations carry
`date: "2026-09-04"`, so `localeCompare` returns 0 and Node's stable sort keeps
file order: j-20260904-08 first, j-20260904-25 second.
`lib/render/home.mjs:48-57` maps the array to one `<p
class="change-annotation">` each, siblings under the same change line. So both
render, in that order, and "above" is literally accurate in the produced DOM.

The `annotates` key is byte-identical to the `key` on the change record it
targets (`data/changes.jsonl:173`):
`openrouter-models|a6c7f5e5e6f3c575|554be452279cdebe|z-ai/glm-4.7-flash|status`.
It joins.

# Is it worth reading

Yes, narrowly but really. The failure it fixes is the one a reader actually
feels: a site tells you a model is dying on 2026-09-10 and stops there. This
line finishes the sentence, and it does the honest version — it names the row,
gives the two numbers that decide whether the move is acceptable, and stops
short of recommending. The reference back to j-20260902-02 earns its place
rather than padding, because it shows the site distinguishing "no successor
exists in the feed" from "we didn't look", which is the difference that makes
either statement worth trusting.
