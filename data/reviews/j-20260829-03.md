## On deleting the `feeds` binding and the four facts

This is the judgment call in the diff and I considered rejecting it, because
`specs/wiki` says a declared-but-absent row *"SHALL cause the fact to render its
last-known value with a visible as-of date"*, and after this change the page
renders no values at all. I land on approve:

- The spec sentence governs a row that is still declared. It describes the interim
  state that raises the repair finding; it does not say the repair must preserve
  it, and `specs/pulse` requires the item to leave the queue once the state is
  fixed, which forbids leaving the declaration in place forever.
- The obvious alternative — transcribing the last-known price and context window
  into `cited` facts with `accessed: 2026-08-28` — would have created facts whose
  `source_url` no longer contains the row, which I just measured directly. That
  trades a thin page for an unsupported one, and `specs/wiki` requires a fact's
  source to be reachable from the page.
- The values are not lost from the repository: they are in the `changes.jsonl`
  retirement excerpt quoted above and in `previous.json`.
- The brief's own acceptance check asks for exactly this: *"If the underlying
  resource is genuinely gone, record that as the finding rather than inventing a
  replacement."*

The residual cost is real and worth stating plainly: the diff promotes a page into
browse listings and search that now carries a name, a status and one line. It is a
legitimate obituary under the site's own rule, not a good one.

## Two things I noted that do not block this diff

1. **A re-listing would go unqueued.** `data/sources/openrouter-models/minted.json`
   still records this row (`contains olmo row: true`, 398 entries), and the entry
   no longer declares it. If OpenRouter re-lists `allenai/olmo-3-32b-think`,
   `writeStub` (`pulse/lib/mint.mjs:105-116`) finds the file present with no
   `feeds` key, so `declared === rowId` is false and the outcome is
   `slug-collision`, not a mint — `run.mjs:143` logs a warning on every run and
   nothing enters the derived queue. The entry would sit `retired` while its
   subject was live again. Visible in the log, untracked in the queue. Not a
   revision of this job: the same gap applies to every future vanished-row repair
   (`arcee-ai/virtuoso-large` is next in the queue), so it is filed on its own as
   **`addictedtoai-2wa`** rather than left inside this record.
2. **`freshness.json` link-check counters moved** (`checked` 25 → 0, `due` 42 →
   17), and I checked both numbers rather than assuming one cause.
   `pulse/lib/linkcheck.mjs:614-630` computes `due` *before* checking — a link
   with no record or a `last_checked` at least 30 days old — and skips the check
   loop entirely when `offline`. So only `checked: 0` is the offline artifact;
   `due` fell because the previous run recorded 25 of the 42, leaving 17. The
   surviving state agrees: `data/linkcheck.json` holds 323 links, all last checked
   `2026-08-29` (249) or `2026-08-28` (74), i.e. **0** due by the 30-day rule, so
   the remaining 17 are corpus links with no record yet. `linkcheck.json` itself is
   not in the diff — `git diff --name-status main...HEAD` returns exactly the seven
   files reviewed here — so no rolling state was lost, and the next online run
   overwrites these summary counters. Noted rather than charged against the diff.
