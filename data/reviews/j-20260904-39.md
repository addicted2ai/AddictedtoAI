## Mutation — the part that decides the verdict

Five green tests prove nothing on their own; the brief's standing instruction
is to test the guard rail by attempting what it forbids. I wrote a scratch
script that mutates the shipped code three ways, runs the suite after each, and
restores both files in a `finally`. Observed:

**M1 — the retry never happens** (`if (!gateResult.ok &&
isTransportFailure(...))` → `if (false)`):

```
✖ a marked gate failure is retried once, and a passing retry is not a failure at all
✖ a marked failure whose retry ALSO fails still ends `failed`, and the note says so
ℹ pass 3   ℹ fail 2
```

This is the red-before the checklist asks for: without the diff's block, the
two tests that assert the new behaviour fail, and the third (unmarked failure
is not retried) stays green — i.e. the suite is not merely asserting that the
loop runs.

**M2 — the retry fires on every failure, marker or not** (`if
(!gateResult.ok)`):

```
✖ an UNMARKED gate failure is not retried, and the note says which gate failed
ℹ pass 4   ℹ fail 1
```

So the "retry ONCE, only on the marker" half of the directive is genuinely
pinned: a blanket retry is caught. Note also that both marked tests stayed
green under M2 — the retry is bounded at one attempt by structure (a straight
`if`, not a loop), and M2 confirms the boundary is not doing the discriminating.

**M3 — the constant drifts from the emitter** (`TRANSPORT failure` →
`TRANSPORT error` in `loop/lib/gates.mjs`):

```
✖ the marker the loop keys on is the marker the emitting code really writes
✖ a marked gate failure is retried once, and a passing retry is not a failure at all
✖ a marked failure whose retry ALSO fails still ends `failed`, and the note says so
ℹ pass 2   ℹ fail 3
```

This is the claim I most wanted to falsify. The header comment on

test". Measured: they cannot. `realTransportFailureText()` really invokes

text contains the constant — a self-comparison would have stayed green here and
did not.

Both files were restored (`restored both files`), and `git status --porcelain`
is clean afterwards.

## Does it fire on the real path? — the truncation check

The tests inject `gates` as a stub, so nothing above proves the marker actually
reaches `isTransportFailure` in production. `runGates` keeps only
`r.output.slice(-6000)` per script, and a transport failure in `pulse/tests`
happens with hundreds of tests still to run after it — so the marker could be
truncated away and the whole fix be a no-op in the field. I measured it rather
than reasoning about it: a scratch test file that calls the real
`assertNoTransportFailure` against an `EADDRINUSE` fixture, followed by 400
passing tests, run through `node --test` on a pipe exactly as `gates.mjs`
spawns it:

```
total output bytes: 24893
marker present in FULL output: true
last marker offset: 23838 => distance from end: 1055
marker present in LAST 6000 (what runGates keeps): true
```

Node's default reporter here repeats each failing test's full error text in a
trailing block, so the marker lands ~1KB from the end regardless of how many
tests follow the failure. The fix fires on the real path. (Scratch files were
deleted; `git status --porcelain` prints nothing.)

## Reading the two ends against each other

- `pulse/tests/helpers.mjs:195-204` is the emitter. Its thrown message contains
  the exact literal `This is a TRANSPORT failure, not a logic failure`, and it
  skips any `last_error.detail` matching `/^HTTP \d/` — so a fixture that chose
  to serve a status never produces the marker. The diff keys on that, not on
  `EADDRINUSE`, exactly as the directive required.
- `loop/lib/gates.mjs:131-157` — `runGates`'s `output` is the concatenation of
  every script's tail, so the marker reaches `isTransportFailure` by the path
  the diff assumes.
- `loop/run.mjs:1207`'s post-merge check runs `scripts: ['build']` only and is
  not retried. That is correct rather than an omission: the marker is thrown by
  a Pulse *test* helper, so `npm run build` alone cannot emit it.
- Breaker semantics are untouched — `loop/lib/breakers.mjs` still counts by
  outcome alone, and the diff adds no outcome. A retried-and-still-failing run
  records `failed` exactly as before, which the third test asserts on the
  ledger line, not on the log. `checkConsecutiveFailures` in
  `loop/lib/breakers.mjs` still counts `failed`/`discarded` by outcome alone,
  verbatim.
- The new `retried: true` key added to `gateReport` is inert downstream:
  `gatesSection` in `loop/lib/review.mjs` reads only `ran`, `why` and
  `results`.
