## What I checked

**The measurement the whole repair rests on, re-run from scratch.** I did not
take the brief's or the carry file's counts. Wrote a script hitting
`https://openrouter.ai/api/v1/models/<slug>/endpoints` for all six slugs and
printed status, `data.endpoints.length` and the provider names. Output,
2026-09-02:

```
anthropic/claude-opus-4.8-fast  HTTP 200  endpoints=0  Anthropic: Claude Opus 4.8 (Fast) || providers:
anthropic/claude-opus-5-fast    HTTP 200  endpoints=0  Claude Opus 5 (Fast) || providers:
anthropic/claude-opus-4.7-fast  HTTP 200  endpoints=0  Anthropic: Claude Opus 4.7 (Fast) || providers:
anthropic/claude-opus-4.8       HTTP 200  endpoints=11 Anthropic: Claude Opus 4.8 || providers: Amazon Bedrock, Google, Azure, Azure, Anthropic, Claude Platform on AWS, Amazon Bedrock, Amazon Bedrock, Google, Google, Anthropic
anthropic/claude-opus-5         HTTP 200  endpoints=10 Claude Opus 5 || providers: Claude Platform on AWS, Azure, Anthropic, Google, Azure, Amazon Bedrock, Amazon Bedrock, Google, Google, Anthropic
anthropic/claude-opus-4.7       HTTP 200  endpoints=8  Anthropic: Claude Opus 4.7 || providers: Amazon Bedrock, Google, Claude Platform on AWS, Anthropic, Azure, Amazon Bedrock, Google, Google
```

So the shape the repair asserts holds exactly as written on both edited pages:
HTTP 200, model record present (`data.name` returns), `endpoints` an empty
array, and the standard row still listing endpoints. Nothing in the added prose
overstates it.

**The counts moved, and the diff is right not to carry them.** The carry file
recorded "8, 11 and 10 endpoints respectively" for the surviving standard rows
in the order 4.8, 5, 4.7; I measure 11, 10 and 8 in that order. Whether that is
a transposition in the original note or genuine drift in a fluctuating provider
list, it is exactly the rot the brief warned about — and the author's prose says
only "while the standard row still lists endpoints", with no number. That is the
correct call and it is why this is not a finding against the diff.

**It does not assert unroutability, which was the explicit prohibition.** The
added sentence is "Nothing published resolves whether that means the slug is
aliased internally or genuinely unroutable" — an explicitly unresolved
disjunction, followed by naming OpenRouter's notice as the authority. The
site's own-voice claim ("still answers and still serves" / "still answers, and
existing requests still serve") survives but is now attributed rather than
free-standing, which is what the carried finding asked for.

**The 4.7 page — checked, and correctly left alone.** The brief asked whether it
makes the same claim. It does not; it makes the opposite one:
"OpenRouter has removed the row without a word about whether the old slug still
serves — do not build on it." There is no unattributed "still serves" to repair,
so adding the clause there would have been scope creep. Its empty endpoints
listing is consistent with what that page already says.

**Adjacent claims the caveat leans on, verified while I had the data.** Dumped
per-endpoint tags and pricing for the three standard rows:

- `anthropic/claude-opus-4.8` carries an `anthropic/fast` endpoint at
  `0.00001 / 0.00005` per token — $10 / $50 per million, matching the 4.8 page's
  "the fast endpoint on that row prices at $10 / $50 per million tokens".
- `anthropic/claude-opus-5` likewise carries `anthropic/fast` at
  `0.00001 / 0.00005`, matching the 5 page's "'Anthropic Fast' provider on the
  standard `anthropic/claude-opus-5` row, at $10 / $50 per million tokens".
- `anthropic/claude-opus-4.7` has **no** `anthropic/fast` endpoint among its
  eight (bedrock ×2, google-vertex ×3, claude-on-aws, anthropic, azure),
  matching the 4.7 page's "no fast endpoint among them".

So the surrounding argument the new clause plugs into is measured, not inherited.
