## The removed render claim — the measurement that decides this diff

The interesting change is (3), whose commit message claims "the data layer
stopped honouring" the old sentence. That is a machinery claim, so I measured it
rather than read it.

`data/derived/feed-rows.json`, the file a `feed` fact actually renders from:

```
KEY HIT .ibm-granite/granite-4.1-8b {"$as_of":null,"$status":null,"$vanished":true}
```

No values, and `$as_of` is `null`. Tracing why, `pulse/lib/derive.mjs:119-132`
joins `inLatest ?? inPrevious ?? null`, so last-known lives for exactly **one**
snapshot rotation. On 2026-09-05, `previous.json` was the 09-04 fetch, which
still held the row — the page then really did render values "as of 2026-09-04"
and the old sentence was true when it was written. By 2026-09-06 `previous.json`
is the 09-05 fetch, the row is in neither, and the fallback literal
`{ $status: null, $as_of: null, $vanished: true }` fires.
`lib/facts.mjs:271-277` renders that as `ABSENT` followed by `last known value,
as of an unrecorded date — the source no longer lists this row`.

So the deleted sentence is now flatly false: there are no last-known values
below it and no 2026-09-04 anywhere in the render. The replacement asserts only
what survives — that nothing below is current, and that 2026-09-04 was the last
listing — both confirmed above. This is the diff's best work, and it is exactly
the defect class this review exists to catch, caught by the author: a claim
written from what the data layer was *meant* to do would have been left
standing. The gap it exposes on the machinery side is the proposal above.
