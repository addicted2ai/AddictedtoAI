The prune this job added (`loop/run.mjs:1367`) closes the branch-deletion case for any run that reaches cleanup, but the same stale entry has a second effect the diff does not touch. `loop/lib/review.mjs:712` does `rmSync(reviewDir)` then `addWorktree(...)` at that exact path, and `loop/run.mjs:912` does the same for the job worktree — neither prunes first. Measured on a throwaway repo, git 2.40.0.windows.1: with a stale entry for a path whose directory was deleted, `git worktree add --detach <same path>` exits 128 with `fatal: '<path>' is a missing but already registered worktree; use 'add -f' to override, or 'prune' or 'remove' to clear`. `addWorktree` throws on a non-ok result (`loop/lib/git.mjs:91`), so that aborts the run. It cannot arise from a run that completes — the new prune clears it — only from one killed at the wall-clock cap after a failed `worktree remove`. One `gitTry(repo, ['worktree','prune'])` before each `addWorktree`, or the same trailing prune added to `review.mjs:752`, would close it.
