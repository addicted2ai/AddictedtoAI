As written, the second admission path keeps a cited domain "only where that domain's own registrable label is one of the subject's name tokens", and the third path admits any domain "whose registrable label is one of the subject's name tokens". The first is therefore a strict subset of the second and can never admit a domain alone. This faithfully reproduces the implementation — `orgOwnDomains` keeps a domain on `tokens.has(reg.label)` (`lib/render/frontier.mjs:323`) and `isVendorSourced`'s fallback tests the identical predicate (`lib/render/frontier.mjs:340`) — so it is not a defect introduced here, and `proposal.md` discloses the filter choice. What it does not say is that the filtered half is inert, which is what a later implementer needs: told to build three admission paths, one of them can never fire on its own. One sentence noting it is stated for fidelity with the live rule would close it. The live question underneath — R13 (v)'s prose states the recorded half unfiltered while `frontier.mjs` filters it — is keeper-class and named as such in `proposal.md`.
