## 3. RANKED CONVERSION LIST

For a transparent ranking, `I` is the conservative instance count, `A` is an avoided-cost weight (`1` routine waste, `3` review/queue waste, `5` ledger corruption or public risk), and `B` is build cost (`1` low, `2` medium, `3` high). The score is the planning ratio `I × A ÷ B`, not a measured financial return.

### 1. Critical negative-control contract — score at least 33

- **Finding:** check narrower than property; artifacts that cannot fail.
- **Host:** `loop/lib/gates.mjs`, `loop/lib/review.mjs`, and adjacent `loop/tests/*.test.mjs`, invoked through the existing test gate.
- **Mechanism:** a machinery change cannot reach merge without an independently run control tied to the changed guard and its merge-base diff. The result must be generated, not copied from a mutation table.
- **Refuses:** missing control, control that never reaches the changed path, a constant/no-op mutation that remains green, or an unparsed result.
- **Red control:** a disposable fixture where the broken path returns `done` while the required hold/publish condition is still present. Delete the guard branch or replace it with a constant; the control must exit nonzero. Restore the source; it must pass.

This covers the `ml25` vacuous ledger test, the unobservable cap, the deleted lock-wait call site, the `>=` equal-time gap, the shortfall relocation, and the absent-entry fixture.

### 2. Authority and brief fidelity — score 20

- **Finding:** truncated authority, lossy brief copying, quantifier drift, and live policy contradictions.
- **Host:** `loop/lib/brief.mjs` and `loop/run.mjs`; the command guard belongs in `scripts/` and is wired by the existing tool-hook configuration.
- **Mechanism:** record an authority hash and source-path closure with the job. Generate the brief from that authority. Refuse dispatch or resumption when required source text is missing, truncated, or contradicted.
- **Refuses:** a brief that loses “both,” turns a prohibition into permission, omits a quantifier member, or carries policy text inconsistent with the repository authority.
- **Red control:** an authority fixture places the acceptance paragraph after the truncation boundary and includes “both spawners” plus a forbidden path. A truncated or prohibition-only brief must be refused; a complete brief must pass.

This directly addresses the four truncated briefs in note 01, `"invert them"` producing a future date, the dropped “both” in note 04, and the unbounded “every injected dependency” in note 05.

### 3. Exhaustive-output command hook — score 16

- **Finding:** truncated output treated as exhaustive.
- **Host:** a new sibling command check under `scripts/`, wired alongside the existing shell-token `PreToolUse` hook.
- **Mechanism:** refuse commands that combine an exhaustive count/enumeration source with `head`, `tail`, or `Select-Object -First`, unless the caller explicitly marks the read as non-exhaustive.
- **Refuses:** the dangerous command before it runs, not after a bad brief has been assembled.
- **Red control:** a fixture command whose acceptance text appears only after the truncation point must be denied. A deliberately non-exhaustive one-line diagnostic must remain allowed, proving the detector is not a blanket ban.

The four `bd show` truncations in note 01 are the primary controls. The `bd prime` context-size truncations and the review-output tail in later notes are additional motivation, but the hook must distinguish intentional summaries from claims of completeness.

### 4. Top-ranked clearance and starvation — score 15

- **Finding:** a higher-ranked candidate is refused, a lower candidate succeeds, and escalation silently never fires.
- **Host:** `loop/lib/select.mjs` and `loop/run.mjs`.
- **Mechanism:** selection must expose the first candidate’s refusal and attempt the declared escalation before selecting lower work. If escalation is unavailable, the run records visible starvation rather than presenting lower work as normal progress.
- **Refuses:** silent lower-priority success while the top candidate was clearance-refused.
- **Red control:** candidates are `[scout, repair]`; the medium runner excludes `scout`, its declared escalation runner accepts it. The result must select `scout` through escalation. With escalation disabled, a plain `repair` selection must be rejected by the control.

This is grounded in the all-night scout starvation, the per-log escalation guard, and directives outranking the scout queue.

### 5. One floor-checked build-record writer — score 12.5

- **Finding:** build records written from an earlier or weaker signal; stale output reused.
- **Host:** `loop/lib/gates.mjs` and `scripts/verify-launch.mjs`.
- **Mechanism:** one writer accepts only the final floor-checked result, validates the build stamp, and records the input identity used for reuse. Both callers pass through it.
- **Refuses:** a below-floor or failed build record, a record written before success, or reuse after the input identity changes.
- **Red control:** copy an `out/` tree with a newer timestamp, then simulate an exit-zero build below its floor. No success record may remain and `hasCurrentBuild` must be false. A real floor-passing build must write the record.

This targets the Packet A stale-record gap, the status stamp proving only that a build started, the untested production floor default, and copied output re-use.

### 6. Immutable per-run gate evidence — score 8

- **Finding:** first-run failure evidence overwritten, fixed filenames reused, or a passing retry hides the original failure.
- **Host:** `loop/lib/gates.mjs` and `loop/run.mjs`.
- **Mechanism:** preserve a unique run/attempt record containing the gated SHA, every per-gate result, and full captured output. The existing shortened human log may remain, but it cannot be the sole evidence.
- **Refuses:** review or publish when the evidence path is missing, overwritten, or names a different SHA.
- **Red control:** make gate one fail, make the retry pass, then attempt to write the same evidence path again. The control must retain the first failure and refuse the overwrite.

This covers the destroyed six-green gate log, `RESULT1`/`RESULT2` loss, and pipe-exit confusion in notes 06–08.

### 7. Measurement lineage for corroboration — score 4

- **Finding:** two derivations sharing an instrument are reported as independent.
- **Host:** `loop/lib/ledger.mjs` plus the structured evidence writer used by `scripts/`.
- **Mechanism:** a measurement carries producer, input digest, source snapshot, and method identifier. A claim marked “independent” is refused when its lineage matches the earlier measurement; it may still be recorded as consistency.
- **Refuses:** false corroboration, not the underlying measurement.
- **Red control:** run the same helper twice over the same input while assigning different method names. The second result must be classified as dependent. A genuinely different input or producer must be eligible for independence.

The `47` coincidence, the shared ledger re-runs, and the agreeing lint counts with different scopes all motivate this.

Memory loading is not ranked as a new repository mechanism. The current settings already call `bd prime`; a fresh-session smoke test could verify that hook output contains a known key, but no code in `loop/` can inspect what a model actually read.
