### The neighbour that is still open

**MANUFACTURE-ROOM — marking existing items blocked manufactures capacity.**
The gate's capacity test is `head_counted > budget`, and `head_counted` is
computed from the branch's own tree. A branch can set that number itself by
adding `blocked-on: maintainer` — the field's one accepted value, accepted on
any track, on any item — to items that are ordinary, countable, and plainly do
not need a maintainer. `scratch/review-manufacture-room`:

- Commit 1: added `blocked-on: maintainer` to 26 of the 30 existing author
  items (ordinary post items such as "post-muse-glimmer").
- Commit 2: filed two new author items (no blocked-on).

Result:

    ok    109 docket item(s) valid (61 open)
          author: 6 open
          blocked on maintainer (excluded from capacity counts; still counted for growth):
            2026-08-10-post-fable-5-biology-safeguards.md  (author)
            ... 24 more ordinary post items ...
            2026-08-16-post-manus-splits-from-meta.md  (author)
    gate  filing gate — base read from origin/main, head from this tree
          author    base 30 -> head 32  (queue budget 6)
    exit=0

**exit 0.** The 31st and 32nd author items landed with every check green. The
26 mislabelled items are simultaneously removed from the dispatcher's `ready`,
so the run that does this also starves its own queue — it is a self-harming
attack, but it is legal, green, and available to any run that has read this
round's changelog, which documents the field in detail. The mechanism leaves me
exactly in the second situation the review brief named: the field can be
applied to items that plainly do not need a maintainer, and the honesty of the
count is doing work no check can verify.

The fix's own comment overclaims: "filing anything into an over-budget track
fails, whatever frontmatter it carries". A track that was over budget on base
ceases to be "over budget" by the gate's own test the moment the branch marks
enough items blocked. The growth test (total) catches this only when the
branch refuses to mark enough — 20 marked items still leave 11 counted against
a budget of 6, so the 20+1 variant goes red — but 26 marked items leave 6
counted, and the gate has nothing left to catch.

**Why this is the same root cause, and the fix that closes it.** The original
hole was that `blocked-on` is a label whose application nothing verifies, and
a gate that trusts the label's honesty is walkable. The fix trusted the head's
counted total; the head's counted total is set by the label's application. The
correct source of truth is the **base** counted total — `baseCounted` — which
the branch cannot touch, and which is already computed at `scripts/check-docket.mjs:317`
and currently never used. Replacing `(headCounted[track] || 0) > budget` with
`(baseCounted[track] || 0) > budget` (one line) turns the manufacture-room
attack red (exit 1) while leaving the PR branch itself green (exit 0) and all
five proofs and control 7 unchanged. I ran exactly that patch both ways and
the outputs confirm it.

## Why this is still blocking

The fix closes the exact exploit, and it is a real improvement. But the round's
own standard for success — the changelog's headline promise that the gate
"makes the 31st author item impossible" — is still false. I made the 31st and
32nd author items on a committed branch with every check green, by applying the
field's single accepted value to existing items, which nothing verifies. The
capacity number the gate trusts is set by the filing run itself; the honesty of
the blocked-on count is doing work no check can verify. The fix is one line —
measure capacity from `baseCounted`, the number the branch cannot change, and
which the implementation already computes and then ignores — and the proofs the
round should add are the negative one it has (a new blocked item must go red,
now true) and the one it still lacks: a branch that marks existing items
blocked to manufacture room must also go red.
