### Invariant audit — every value the gate compares

The whole gate function is `scripts/check-docket.mjs:320-359`. Values:

- `headPolicy`, `headTotals`, `headBudgets` — computed from this tree
  (`parseYaml(policy.yml)`, `countRef(open)`). **HEAD.**
- `baseCounted`, `baseTotals`, `baseBudgets` — from `base.baseItems` and
  `base.policy`, both read via `git ls-tree`/`git show origin/main`. **BASE.**
- Filing gate (`:346`): `headTotal > baseTotal && (baseCounted[track] || 0)
  >= budget` — `headTotal` **HEAD** (the one allowed fact), `baseTotal`
  **BASE**, `baseCounted` **BASE**, `budget` = `baseBudgets[track] ??
  headBudgets[track]` — **BASE** for every track budgeted on origin/main
  (author, build, meta); the `?? headBudgets[track]` fallback is HEAD-derived
  for a track that has no budget on base. I attacked that corner: adding a
  budget to an unbudgeted track (maintain) and filing items to it in the same
  diff fires the budget-raise rule — `maintain's queue_budget was raised none
  -> 100 and its open count grew 1 -> 2 in the same diff`, **exit 1** — and
  the docket validator rejects items on any track not in the fixed `TRACKS`
  list, so a brand-new track cannot receive items at all. The head-derived
  budget fallback is double-guarded and I could not make it grant anything.
- Budget-raise rule (`:352`): `(headBudgets[track] ?? 0) > (baseBudgets[track]
  ?? 0)` — the head's budget is the thing being tested (what the head is
  trying to add), base's is the baseline. Consistent with the invariant's
  letter: the raise rule's subject is the head's own proposal.

Conclusion: every number that can decide a green outcome is base-derived
except `headTotal`, which is the one permitted head fact. The invariant as
stated is kept for the capacity test. The holes are in what the gate measures
per track, not in where it reads the numbers.

### New attacks

**TRACK-MOVE — THE FIRST BLOCKING HOLE.** Editing an existing item's
`track:` field moves it between tracks; the gate's growth test is per-track,
and it cannot distinguish "moved an item out" from "closed an item". Minimal
case (`scratch/review3-trackmove-min`, committed): one author item relabeled
to build plus one new author item, one diff →

    gate  filing gate — base read from origin/main, head from this tree
          author    base 30 -> head 30  (queue budget 6)
          build     base  0 -> head  1  (queue budget 14)
          meta      base 29 -> head 29  (queue budget 14)
    exit=0

A new author item was filed into a track at 30 against a budget of 6, and the
gate had nothing to say. Full version (`scratch/review3-trackmove`,
committed): all 30 author items relabeled to build plus 30 new author items →

    ok    137 docket item(s) valid (90 open)
          author: 30 open
          build: 30 open
    gate  filing gate — base read from origin/main, head from this tree
          author    base 30 -> head 30  (queue budget 6)
          build     base  0 -> head 30  (queue budget 14)
          meta      base 29 -> head 29  (queue budget 14)
    exit=0

The queue grew 60 -> 90 in one diff, every check green. Nothing in the docket
validator or the gate prevents editing an item's track field, so this is
available to any run. The changelog's tolerance for churn — "a pull request
that closes one and files one leaves head_total flat and still passes" — is
laundered through relabeling, which is not closing anything: the relabeled
items are still open, still real work, just counted under a track with room.
This is the same class as the two previous holes: the gate tests numbers built
from labels the branch controls (blocked-on then, `track:` now), and the head
supplies more than one fact — it supplies the per-track composition of its
entire queue.

**BUILD-FLOOD — THE SECOND BLOCKING HOLE.** The gate's capacity test compares
`base_counted` to `budget`; it never compares the head count to the budget.
A track that is under budget on base can therefore be overshot by an arbitrary
amount in one diff. `scratch/review3-buildflood` (committed): 30 build items
filed directly →

    ok    137 docket item(s) valid (90 open)
          build: 30 open
    gate  filing gate — base read from origin/main, head from this tree
          author    base 30 -> head 30  (queue budget 6)
          build     base  0 -> head 30  (queue budget 14)
          meta      base 29 -> head 29  (queue budget 14)
    exit=0

Build's budget is 14; the 15th through 30th build items are all possible in a
single diff. The budget is "how much ready stock this track can actually
spend" in the round's own words — a queue 2x past it should be exactly what
this gate was built to stop. It is only a floor below which growth is free,
not a cap on the head.

**Attacks that did NOT work (tried and red, or correctly green):**

- **`>=` at exactly budget.** Synthetic base in a scratch clone with build
  budget 0 and base build count 0; adding one build item →
  `0 >= 0` true, **exit 1**. The `>=` boundary behaves as claimed: a track
  exactly at budget cannot be pushed to budget+1. (On the real base no track
  is exactly at budget — author 30/6, meta 29/14, build 0/14 — so this needed
  the synthetic base.)
- **A new track added to policy.yml with a budget in the same diff.**
  Two layers block it: the docket validator rejects any item whose track is
  not in the fixed `TRACKS` list (`track "reviewer" is not one of: scout,
  author, build, maintain, audit, meta`), and adding a budget to an existing
  unbudgeted track while filing items to it fires the budget-raise rule
  (tested with maintain, **exit 1**).
- **Adding a budget to an unbudgeted track without items** is green, but then
  the budget is on main next round — the inherent two-round grant noted in
  my previous review; no per-round gate can stop a sequence.
- **Renaming an item** (delete one author item, add one with a different
  filename): author 30 -> 30, **exit 0** — the designed churn tolerance, and
  on its own it grows nothing. (Its interaction with track-move is the hole
  above.)
- **A track absent from origin/main entirely** (scout, maintain, audit —
  budgetless tracks): items filed to them are not gated at all, because
  `budget == null` skips the track. This coverage gap was noted in my previous
  review and is unchanged; it is probably by design (those tracks are not
  budgeted), but it is also what makes the track-move scalable: relabel items
  into an ungated or under-budget track and file replacements indefinitely.
- **Two-round budget grant**: raise a budget in one round (green), spend it
  against the new base the next. Inherent to any per-round gate; not a defect
  of this fix.
