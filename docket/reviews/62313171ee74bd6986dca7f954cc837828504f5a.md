## 1. Snippet matching — does it actually hold, and can it be defeated?

Reproduced the original demonstration against the real running site using
the real exported functions (not reimplemented), via a small script
launching the same Chromium binary the check uses and driving it over CDP
exactly like `checkRoute` does:

    live probe after inject A: overflow=true offenders=1
    ok    A: documented snippet matching real injected offender text classifies known
    ok    B: unrelated snippet against real offender classifies NOT known
    ok    C: a genuinely different +1880px offender on the route classifies NOT known -- 1 overflowing element(s) do not match this route's documented signature: <div> "DIFFERENT-UNRELATED-BUG-zzz999 nothing to do with "

Case C is the first pass's exact demonstration, replayed against the new
code: a documented route, a completely different real overflow. It fails
correctly now.

**Then tried to defeat it**, per the coordinator's specific list:

- *An offender with no text* (an empty div, still overflowing):

      ok    E: an empty-text offender classifies NOT known (cannot be excused by any snippet) -- 1 overflowing element(s) do not match this route's documented signature: <div> ""

  Correct — an unnamed offender can never be excused by any snippet,
  because `"".includes(snippet)` is false for any non-empty snippet.

- *Whitespace/entity differences between snippet and rendered text*:
  injected `Marker&nbsp;&amp;&nbsp;value` via `innerHTML`; the real,
  decoded `textContent` the probe captures is `"Marker & value   with
  <odd>   spacing..."`. A snippet written against the raw HTML source
  (`"Marker&amp;value"`) does **not** match the decoded text and correctly
  fails closed:

      ok    F: a snippet written with raw HTML entities/spacing (not matching decoded textContent) does NOT match

  This is the safe failure direction (a bad snippet just never matches,
  so it can't accidentally excuse the wrong thing) — but it does mean a
  snippet must be copied from rendered output, not from Markdown/HTML
  source, which is worth a one-line note in the file's own header for the
  next person who adds an entry. Not filing this as a finding by itself.

- *A substring that matches by accident* — **this one succeeded**:

      FAIL  D: a short generic snippet ("the") accidentally matched unrelated offender text -- snippet matching is too loose

  The offender text was `"DIFFERENT-UNRELATED-BUG-zzz999 nothing to do
  with the documented one"`. A snippet of `"the"` matches it, because
  `.includes()` doesn't care about word boundaries or specificity.
  Escalated to the actual failure mode this implies:

      empty-string snippet verdict: {"known":true}

  `snippets: [""]` — a plausible accident (an unfilled field, a bad
  template) — makes `classifyKnownFailure` return `known: true` for
  **any** offender text on that route, unconditionally, because
  `x.includes("")` is always `true` in JavaScript. This exactly
  reconstructs the original bug (a route-wide bypass) through the new
  mechanism's own matching primitive, for whichever route carries that
  entry. Nothing in `classifyKnownFailure` or
  `checkKnownFailureBookkeeping` checks that a snippet is non-empty or has
  any minimum length/specificity, and none of the 11 shipped test cases
  exercises this — the shipped fixture snippet is a full 62-character
  docket path, which is realistic but not representative of what the
  *mechanism itself* would reject if someone wrote something shorter.

  This is real, live-verified against the actual shipped code, and it is
  the same class of gap the first finding was: something is excused by
  identity rather than caught by content. It's much narrower in
  consequence (requires a future author to write a bad snippet; the table
  is empty today so nothing is exposed right now) but the mechanism does
  nothing to prevent, warn on, or even make it hard to do. A cheap fix:
  reject snippets under some reasonable minimum length (say 10-15 chars)
  in `checkKnownFailureBookkeeping`, or assert non-empty/non-whitespace at
  minimum, so a degenerate snippet fails the build the same way a stale
  docket citation already does.

## 4. The stated residue — do both gaps genuinely fail closed?

**Gap 2 (block-level overflow invisible to the bounding-rect scan).**
Constructed it live rather than trusting the description: a `<p>` with
`width:250px; overflow-x:visible` (the default) containing one long
unbroken text run, no nested element:

    baseline /log: overflow=false scrollWidth=320 clientWidth=320
    after inject: overflow=true scrollWidth=3247 clientWidth=320 offenders=[]
    injected <p> box's own getBoundingClientRect: {"right":250,"width":250}
    ok    confirmed the gap-2 shape live: page-level overflow=true, offenders=[] (box's own rect never shows it)
    ok    classifyKnownFailure fails closed on this shape (known=false) -- page overflows but no individual element was identified as the cause -- nothing to match against the documented signature

Genuinely reproduced (the element's own box really does stay at 250px
while the page overflows by 2927px) and genuinely fails closed — a route
in this state is never classified known, so it always surfaces as a
`FAIL` in `main()`, never a silent pass. This is accurate as disclosed.

**Gap 1 (a smaller unrelated offender hiding behind a larger known one).**
This is where I disagree with the round's own account. Its code comment
and the mirrored changelog prose both say: a smaller, unrelated offender
"would not appear in `offenders` at all... produces no new offender to
check against, known or not, and passes unnoticed either way." I tested
this directly, twice:

    // synthetic, matching the scenario's own description
    { tag: 'DIV', right: 900, text: 'KNOWN-MARKER...' },   // documented, matches snippet
    { tag: 'SPAN', right: 340, text: 'a totally unrelated second bug...' } // smaller, unrelated
    ->
    { "known": false, "reason": "1 overflowing element(s) do not match this route's documented signature: <span> \"a totally unrelated second bug, much smaller, coex\"" }

A smaller offender whose own right edge still exceeds `clientWidth + 1`
**is** included in the `offenders` scan (`REFLOW_PROBE` filters every
`body *` element by its own bounding rect independent of any other
element's size) and **is** checked against the documented snippets like
any other offender. This is not just my own read of the code — the
round's own shipped test, case 3 in `scripts/test-check-reflow-known-
failures.mjs`, constructs exactly this shape (a matched 500px offender
plus an unrelated 340px one) and asserts it classifies **NOT known** —
which is the opposite of what the header comment and changelog claim
happens. The round's own regression test contradicts the round's own
residue disclosure.

The actual, narrower gap this prose seems to be reaching for is really
gap 2 restated: a second failure whose *own* element never individually
crosses the viewport threshold (so it never becomes an offender at all,
regardless of any other offender's size) is invisible to this scan — but
that's a different mechanism (box-vs-content overflow) than "smaller than
another offender," and gap 2's own paragraph already covers it correctly.

This doesn't make the code less safe than believed — if anything the
actual behavior is safer than what's published. But it is a factual claim
about the project's own mechanism, published in both a source comment and
the append-only changelog, that direct testing (including the round's own
test suite) shows is not accurate. Worth a follow-up correction to the
prose — the changelog entry itself can't be edited after merge per rule 5,
so this would need a new entry noting the correction, small as it is.
