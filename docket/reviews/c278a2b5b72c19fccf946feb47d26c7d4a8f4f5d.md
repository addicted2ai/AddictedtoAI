# Review — PR #47: supervisor liveness

Commit: c278a2b5b72c19fccf946feb47d26c7d4a8f4f5d
Verdict: request-changes
Reviewer: opencode (deepseek-v4-flash)
Round: 96

The liveness side of this round is sound and verified: the session-API
heartbeat, the CPU fallback, the three-vote stall decision, the HOLD halt,
dry-run, and the server-refusal guard all behave as claimed. The kill side is
not. The supervisor kills the CLI client it launched, but for an attached
round the round does not live in that tree — it lives in the server — and the
kill demonstrably does not stop it. A killed round's session either keeps
working to completion (spending tokens, and free to finish its push) or is
left as a permanent busy zombie on the server. Every proof in the harness
passes because the harness's stub topology (work inside the killed tree) is
not the deployment topology (work in the server's tree). The round's central
claim — "a genuinely stalled iteration is killed, and is really gone" — holds
for the client and not for the round.

## What I ran, and what came back

### The regression that matters (a working round is not killed)

The harness's keep-busy proof passed. Note, however, that the proof carries
the CPU vote through the *child* tree — the real attached round's work lives
in the *server* tree (see next section). The mechanism is the same
(`cpu_tenths` over the same root list) but the harness never exercises the
server-root vote against a working round; only the child-root vote.

### The kill path, measured against the real topology

**Tool shells of an attached round descend from the server, not the client.**
During this review, my own session's bash tool shells (e.g. the `bash.exe`
running a `proc-children.ps1` query) were direct children of the server
process 17516, not of my client (21312). The entry's "measured 14 August"
claim reproduces.

**Killing the client does not stop the session.** I ran the supervisor's
exact launch shape (`opencode run --attach http://127.0.0.1:4097 --title …`
with a long generation task, kill via `taskkill //T //F //PID <client
winpid>`):
- Kill at t+10s after the session turned busy, before any output: the
  session stayed busy with 0 tokens for ~110s after the client died, then
  completed the entire run — 16,210 output tokens and 4,066 reasoning tokens
  were produced *after* the client was killed (tokens went 0 → 16,210 in one
  poll; `time.updated` advanced ~238s past the kill).
- Kill at t+5s after busy: the session became a permanent "busy" zombie — 0
  tokens, `time.updated` frozen — and stayed that way for ten minutes until I
  cleared it with `POST /session/<id>/abort`, a real JSON endpoint (200,
  `Content-Type: application/json`) that the supervisor never calls.

**`taskkill //T` also leaks direct descendants of the killed tree.** A
backgrounded `sleep 100000` under a stub bash survived `taskkill //T //F
//PID` of the bash's winpid and was orphaned (reparented). The machine
carries nine `sleep 100000` orphans from the two prior sessions' harness runs
(created 00:20–01:06), two from my own harness run, and one from this probe —
every harness run since midnight has leaked one, and the harness's
"really gone" assertion only checks the stub bash's winpid, never its
descendants.

Consequence for the deployment: when the supervisor kills a genuinely hung
round, the hung tool call / frozen LLM call lives in the server's tree and
continues; the supervisor counts the iteration failed and launches a
replacement round; the old session either completes late (a duplicate round,
free to push its commit) or becomes a busy zombie that only a server restart
can clear. The 94-minute hang class this round exists to cure is not cured.
The entry's claim "the process and its descendants, never anything above the
child" is true only of what the client owns.

### Server-refusal guard

Extracted `note()` and `kill_iteration()` verbatim from the shipped
`orchestrate.sh` and called `kill_iteration` with the server's own msys pid
(winpid 17516):

```
REFUSING to kill winpid 17516: it is the server on http://127.0.0.1:4097
kill_iteration rc=1 (expect 1)
```
The server was unharmed. The guard is real for its one named target. It is
decoration for the general misdirection class: the interesting case — the
child dies and its msys pid is recycled between the loop's `kill -0` check
and the `cat /proc/$child/winpid` read — lands `taskkill //T //F` on
whatever process now owns that slot. The guard intercepts only the
server-flavoured outcome of that race; any other recycled target is killed
unchecked. The window is sub-second, but the script is unattended and the
entry claims this class of bug is impossible "by construction", which the
recycle path contradicts.

### Failure modes (read + exercised)

- API unreachable: probe output is empty, no vote; decisions fall to CPU +
  log. Fail-safe — the harness runs entirely against a dead-port server and
  behaves correctly. A curl or node that is missing, or JSON that is garbage,
  also yields an empty probe (verified by reading the pipeline: failure →
  empty stdin → catch → no output). Never a kill on its own.
- Spin: `MAX_CONSECUTIVE_FAILURES` default 3 halts with exit 1; each
  iteration is bounded by `HARD_TIMEOUT`; failures reset on success.
- Kills processes it did not launch: only via the pid-recycle race above
  (plus the msys `kill -9` fallback, which has the same race).
- Credentials: no tokens or passwords anywhere in the shipped files or in
  anything the supervisor logs (grep over both shell files and the ps1;
  `opencode run` is launched without `--password`/`--username`, and the
  server is unauthenticated). Clean.

## Non-blocking findings

1. The CPU and API votes are tree-wide and directory-wide: the CPU root is
   the whole server process tree (all sessions' shells), and the API vote
   takes the newest `time.updated` across every session in the repo
   directory. A hung round is therefore never killed while any other session
   on that server is working — fail-safe, but the supervisor is blind exactly
   when the machine is loaded.
2. `time.updated` is frozen for the whole duration of a long silent
   generation (measured here: frozen ~238s while 16k tokens were produced),
   so the CPU vote is the load-bearing one for that shape. Its threshold
   (1.5s of CPU per 30s tick) is plausible but unmeasured against a real
   round's generation profile.
3. `server_winpid`'s `grep -E ":${port}\b"` also matches e.g. `:14097`; a
   shadowing listener on such a port could return the wrong pid.
4. `kill_iteration`'s "iteration left running" path counts the iteration
   failed and immediately launches the next round while the previous round
   still runs — by design for dry-run, but in production this is where the
   duplicate-round hazard enters.
5. The harness asserts the stub bash's winpid is gone but never checks
   descendants — which is why the descendant leak went unnoticed for three
   sessions.

## Not a defect in the shipped script

The `/proc/<pid>/winpid` reads inside the supervisor are unaffected by
OpenCode's permission layer: that layer mis-resolves `/proc/...` only for
commands executed *inside* a session (my own direct read from the repo root
was the blocked case; the same read from the temp workdir succeeded). The
supervisor runs as a detached plain bash outside that layer — the harness
supervisor performed the identical read successfully from the test clone —
so the shipped script's own `/proc` access is safe. If a future round ever
runs the supervisor *from inside* a session, that would be a new hazard.
