## Verdict

Reject. The count guard, the malformed-date guards, the duplicate-date
guard, and the unclosed-block guard all work as claimed and are verified
above. But the fix's own headline claim is false: "a `datePublished:`
sitting inside another field's string cannot be read as the post's date"
was tested and broke. A template literal inside a description puts a
line-start `datePublished: "2026-08-17"` inside the block's text; with the
real date field removed, the check counts it as the block's one and only
datePublished, prints `ok 10 posts`, and exits 0 — on a valid-JS file whose
post carries no genuine date at all. The failure class the first review
demonstrated — a guardrail that goes green while the file's posts would
breach the cap — is open through a second door, and the changelog entry's
claim that it is shut is disproved by measurement.

Exact change required: stop extracting dates from text. `posts.js` is
importable — this session `import('./app/lib/posts.js')` from Node loaded
the module and its objects (only a cosmetic MODULE_TYPELESS warning). The
check script is already ESM (.mjs); reading each post's `datePublished` from
the exported object's property instead of a regex removes the entire decoy
class structurally — a string inside a description can never be a property,
and the count guard, the exactly-one guard, and the lacks-datePublished
guard all become redundant in the strongest way. The header's stated reason
for not importing ("posts.js is ESM in a CommonJS project") does not apply
to an ESM script. If importing is nevertheless refused, the fallback is a
quote-state-aware scan that tracks backtick and single/double-quote contexts
and excludes lines inside string values before matching field lines — but
that is strictly weaker than importing and is not the preferred fix.
