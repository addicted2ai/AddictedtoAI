## Finding 1 (blocking): CLAUDE.md's "21 rules" is wrong; the project's own build says 22

`CLAUDE.md` (new in this round, loaded into every future session and, per
its own text, read by Claude Code's approval classifier) states:

> `CHARTER.md` is the binding ruleset — 21 rules, human-owned.

The project already has a live, build-time check for exactly this number —
`scripts/check-routes.sh`, the "rule count" check added specifically because
a silent parser drift had previously let `/charter` publish a short charter
unnoticed. It computes the count the same way the rendered page does:

```
sed -n '/^## I\. Truth/,/^## Amendment/p' CHARTER.md | grep -c '^[0-9][0-9]*\. '
```

I ran that exact command against the checked-out `CHARTER.md`:

```
$ sed -n '/^## I\. Truth/,/^## Amendment/p' D:/AddictedtoAI/CHARTER.md | grep -c '^[0-9][0-9]*\. '
22
```

22, not 21. I independently cross-checked by grepping the numbered-rule
headings across sections I–V by hand (`^\d+\. \*\*`) and got the same 22,
numbered 1 through 22, with rule 13a embedded in rule 13's body rather than
consuming its own top-level number. `CHANGELOG.md` (line ~1219) has its own
record of this: `"Verified after the rewrite: rule count 22,"` from an
earlier round — so 22 is not new information this round could not have
found; it is already in this repository's own record.

`README.md`, `AGENTS.md`, and a comment in `app/charter/page.js` also still
say "21 rules" — that staleness predates this round and is not this round's
doing (none of those files are in its diff). But `CLAUDE.md` is not
inherited text; this round wrote it fresh, and its own changelog entry
claims "every command below was re-run this round, not trusted from the
brief's prose." The one sentence in the document with an existing,
one-command, build-canonical answer was not checked against that answer —
it was copied from the same stale figure the rest of the repo already has
wrong. `CLAUDE.md` has no check protecting its prose at all (unlike
`FRAME.md`, which has `check-frame.mjs`), so this number can sit wrong
indefinitely with nothing to catch it, in the one file whose explicit job is
to be current and to steer the approval classifier for months.

## Finding 2 (blocking): check-frame.mjs silently drops a fact if its heading punctuation is off — reproduced

The brief asked directly: can a fact be present in `FRAME.md` but never
executed, with the summary still reporting all-clear? I built a four-fact
test fixture in the scratchpad (not touching the real `FRAME.md`) and a
scratchpad copy of `check-frame.mjs` pointed at it, to test the parser in
isolation:

- Fact 1: normal, `## 1. Title`, real check — control.
- Fact "17": heading written `## 17: A fact whose heading uses a colon
  instead of a period` (colon, not period) — otherwise well-formed, with a
  `verified` status and a check that would print `FAIL` if run.
- Fact 18: `## 18. ...`, well-formed heading, but an **empty** fenced check
  block.
- Fact 19: `## 19. ...`, well-formed heading, but the fence uses an
  unrecognised language tag (\`\`\`shell instead of \`\`\`sh / \`\`\`bash).

Running `check-frame.mjs`'s own chunk-splitting regex against the fixture:

```
chunks found: 3
--- 1. A normal fact with a real check
--- 18. A fact with an empty fenced check block
--- 19. A fact using a non-recognised language tag on its fence
```

Fact "17" is not in the list. It is not reported malformed, not reported
missing, not counted at all — the script's `text.split(/\n(?=## \d+\. )/)`
lookahead requires the literal `". "` (period, space) right after the
number, so a colon there does not open a new chunk boundary, and the entire
fact — heading, status, and check command — is silently absorbed as trailing
text inside the previous fact's chunk. Running the actual script (a
scratchpad copy of `scripts/check-frame.mjs`, only the hardcoded path
changed) against the same fixture confirms the consequence:

```
FAIL  fact 18. A fact with an empty fenced check block -- malformed (missing Status or, for verified, a check block)
FAIL  fact 19. A fact using a non-recognised language tag on its fence -- malformed (missing Status or, for verified, a check block)
FRAME.md check -- 3 fact(s)

verified    1. A normal fact with a real check

2 fact(s) failed, 0 unverified, 0 attested
```

The header line says "3 fact(s)" against a 4-fact document, with no error,
warning, or count mismatch anywhere in the output. Facts 18 and 19 *are*
correctly caught (empty check block and unrecognised fence language both hit
the `malformed` path as designed — that part of the parser works). Only the
heading-punctuation case is invisible.

This is exactly the "laundering one level up" failure the brief named:
`check-frame.mjs` exists so a wrong claim in `FRAME.md` cannot look audited.
A malformed heading — one typo away, and not a contrived one; a colon for a
period, or a lettered sub-number like `13a.` instead of a plain integer,
both fail the same way — makes an entire fact invisible to the checker while
`check-routes.sh` and the build stay green and the summary line undercounts
without saying so. The real `FRAME.md` in this commit does not currently
trigger this (I verified all 16 of its headings use `## N. ` correctly, and
the live run reports all 16), so this is not a claim about today's state
being wrong — it's a defect in the enforcement mechanism itself, the thing
this round was built to make trustworthy.

## Finding 3 (non-blocking, but worth fixing): FRAME.md fact 2's check verifies proxies, not the claim

Fact 2 claims `docket/HOLD.md` is "the loop's own self-halt, not a
maintainer's brake," and specifically: "Every commit to this file in this
repository's history... was written by the orchestrator or a round halting
itself, not a maintainer reaching into a session already running." The
check:

```sh
count=$(git log --all --oneline -- docket/HOLD.md | wc -l | tr -d ' ')
gate=$(grep -c 'if \[ -s docket/HOLD.md \]; then' scripts/orchestrate.sh)
phrase=$(grep -c 'not a channel the maintainer currently' CHARTER.md)
```

This checks that a gate line exists, that CHARTER.md asserts the policy, and
that the historical commit count is ≥10. I ran the actual history:

```
$ git -C D:/AddictedtoAI log --all --format='%H %ae %ad %s' --date=short -- docket/HOLD.md
```

10 commits, all authored by
`223016611+addicted2ai@users.noreply.github.com` — which, per **fact 1 in
the same document**, is explicitly "the maintainer's own personal GitHub
account," shared with the loop, where "commit-author identity cannot
evidence authorship in either direction." Fact 2's check never inspects
authorship at all — it can't, by fact 1's own logic — it only counts
commits and greps for text. Mutate the world: if the maintainer personally
edited `docket/HOLD.md` tomorrow to halt a runaway loop by hand — literally
becoming "a channel the maintainer currently uses to intervene," the exact
thing fact 2 says never happens — the count goes to 11 (still ≥10), the gate
line is untouched, the CHARTER.md phrase is untouched. The check still
prints `PASS`. It cannot distinguish the claim from its negation, because
the negation lives in a domain (human intent behind a shared-account commit)
the check does not and structurally cannot examine.

The commit messages I found (`docket: hold the loop — the maintainer hit
their DeepSeek limits`, `orchestrator: release the hold — ...`) are
consistent with round/orchestrator authorship by convention, and I am not
claiming the underlying claim is false — only that the "verified" marker
overstates what this check can show. The honest fix is the one the document
already models for facts 14/15 and the second half of fact 12: split this
into a checkable piece (the gate exists; CHARTER.md states the policy) and
an attested piece (nobody but the loop has ever used it that way), rather
than labeling the whole thing verified.

## Finding 4 (non-blocking): fact 14 folds a checkable half into "attested"

Fact 14 ("OpenCode has websearch, via Exa... Claude Code's track scoping
deliberately withholds `WebSearch`/`WebFetch` from `meta`") is marked
**attested** in full, with the note "No command run from inside this git
checkout can query OpenCode's own tool configuration." True for the
OpenCode half. Not true for the second half — I found the exact mechanism in
this checkout:

```
$ grep -n -A6 'meta)' D:/AddictedtoAI/.github/workflows/loop.yml
```
```
            meta)
              # No web access: meta's charge is to fix what blocks other
              # tracks, and that answer is always inside the repository. With
              # a search tool it could justify any machinery change by finding
              # an article recommending it.
              tools="Read,Write,Edit,Glob,Grep,Bash" ;;
```

`.github/workflows/loop.yml` hard-codes meta's `--allowedTools` list without
`WebSearch`/`WebFetch`, right there, checkable with one grep. This is the
same pairing the document explicitly calls out and protects against for
fact 12 ("the exact pairing of a true attested fact... beside a checkable
one... that this round exists to keep from being collapsed into a single
false sentence") — but fact 14 does exactly what fact 12's own text warns
against, applied to itself. A check for the Claude-Code-side half was
available and wasn't written; if that line in `loop.yml` ever changed, fact
14 would keep reporting "attested — not provable from this repository" and
never notice.

## The orchestrate.sh / approval-classifier report — assessed, not reproduced

The changelog's change 2 reports that an earlier, abandoned attempt to
mutate `scripts/orchestrate.sh`'s `if [ -s docket/HOLD.md ]; then` gate (to
test whether `check-frame.mjs` would notice a real mechanism change, not
just a markdown edit) caused the approval classifier to block the very next
Bash call — the identical `node scripts/check-frame.mjs` invocation that had
just run cleanly — and that the block cleared the moment the gate line was
reverted.

Per the brief, I did not reproduce this. Reasoning about plausibility
instead: `CLAUDE.md` states the approval classifier reads repository content
(not just command text) alongside a command before deciding, which makes an
LLM-aware, context-sensitive block *mechanically plausible* rather than
requiring any purpose-built detector — no hook or script anywhere in
`.claude/` (I checked `.claude/settings.local.json` and
`.claude/skills/local-loop/SKILL.md`, the only project-level Claude Code
config in this checkout) references `orchestrate.sh` or `HOLD.md` at all, so
if the report is accurate the mechanism is not something this project built
and can point to — consistent with the round's own "second, independent
layer of defence... not chased further" framing rather than a discovered,
inspectable rule.

The report is internally consistent (specific before/after, same command,
clean revert) and, importantly, was *not* promoted into `FRAME.md` as a
verified or even attested fact — it stays in the changelog as a disclosed,
uncontrolled, single observation, which is the right epistemic weight for
an n=1 result the round itself flags as possibly coincidental. I am
treating it as unconfirmed. What would confirm it: a controlled test (ideally
run by the maintainer, or in a disposable branch/worktree with the
maintainer watching) that edits the same line a second time and checks
whether an unrelated, equally "just-ran-clean" Bash call is blocked
afterward, and whether editing a comparably-important but unrelated line
does *not* trigger the same block. I judged the cost of running that myself
mid-review — risking my own Bash calls in this session — too high for a
finding that is disclosed honestly rather than asserted as fact, per the
brief's explicit instruction not to reproduce it.

## Overall

Two defects I judge real and blocking: `CLAUDE.md`'s rule count is wrong
against the project's own build-verified figure (Finding 1), and
`check-frame.mjs` — the mechanism this entire round exists to make
trustworthy — silently drops a fact on a heading-punctuation typo with no
error and an undercounted summary (Finding 2). Both are concrete,
reproduced, and sit in exactly the territory the brief asked to be attacked
hardest: a document meant to be current, and a checker meant to catch
exactly this shape of silent failure. Findings 3 and 4 are real but
narrower — checks that verify a proxy or a partial claim rather than the
full one, in the same spirit as the 278-commit precedent this round was
commissioned to prevent, though neither currently produces a wrong
"verified" fact in the checked-out `FRAME.md`.

I did not find anything wrong with the scope widening, the changelog
append-only discipline, the `Origin` field, the UNVERIFIED-handling design,
or 12 of the 16 facts' check logic — those held up under direct testing, not
just reading.
