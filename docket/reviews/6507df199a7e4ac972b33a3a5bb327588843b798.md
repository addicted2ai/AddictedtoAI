## 3. The fixture change — the one I was told to attack hardest

Read what the original fixture (`closedGenerativeCount: counts only the
configured serves value`, from `8d0098e`) actually asserted: five `doneItems`
with varied `serves` values and **no `track:` field on any of them**,
asserting `closedGenerativeCount` returns 2 (the two `worth-a-visit` items).
At that point in the code's history `closedGenerativeCount` was
`doneItems.filter((item) => item?.serves === push.serves).length` — track
played no role at all, so the fixture's total absence of `track` fields was
incidental, not a deliberate assertion about track-independence; the
comment on the one bare `{}` item (`an item with no serves field at all must
not throw or miscount`) is explicitly about the missing *serves* field, not
about missing *track*.

Once this commit added the `VISITOR_FACING` filter, that fixture's
lack of any `track` field became load-bearing by accident: every item would
now fail `VISITOR_FACING.includes(undefined)`, and the whole test would
report 0 instead of 2. I reproduced this myself rather than trust the pasted
"expected 2, got 0" — ran the *original* fixture (verbatim, no track fields)
against the *current* `closedGenerativeCount`:

```
original (no-track) fixture against current code: closedGenerativeCount = 0 (expected 2 by the old test, would now read "expected 2, got 0")
new (track:build) fixture against current code: closedGenerativeCount = 2 (test expects 2)
```

Matches the entry exactly. This is the crux of what I was asked to determine:
was the original failure revealing a genuine regression, or just a stale
fixture? It's the latter, and cleanly so — the failure was the *intended*,
correct consequence of a deliberate contract change (the function now also
requires a visitor-facing track), not a sign that anything was broken. The
new fixture (`track: "build"` on every item, same varied `serves` values,
same expected count of 2) still asserts exactly what the original test was
built to check — serves-filtering in isolation — now under the precondition
the function actually requires. It does not silently relax that assertion:
I confirmed a totally broken (over-exclusive) `VISITOR_FACING` filter would
still fail this fixture (it would return 0, not 2, since all 5 items are on
`build`), so the fixture isn't blind to a broken filter either.

What the new fixture no longer exercises — a `worth-a-visit` item under a
*non*-visitor-facing track, and an item with *no* `track` field at all — is
covered elsewhere: the dedicated new regression test (verified in section 4)
covers the non-visitor-facing-track case directly, and my own probes in
section 1 independently covered the missing-`track`-field case (`{}` and `{
serves: "worth-a-visit" }` both returned `0`, no throw). Nothing was masked;
the coverage moved to a more precise, purpose-built test rather than
disappearing.
