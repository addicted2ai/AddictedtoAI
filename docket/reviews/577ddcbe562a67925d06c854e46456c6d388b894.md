## Claim 1 — the first ticked box

The box reads "A `loop/` pull request merges, and the build after it is
green without a human regenerating anything." What the round ran is a
reconstruction, not the event. It replayed the exact historical state the
mechanism produces — the committed snapshot (67) with a loop/ PR (#75)
merged 13 minutes after its taken_at — through the real check against the
live API. The literal event, a merge on top of this change, can only happen
after this PR lands; the branch itself is `loop/`.

Plainly: this is a reconstruction standing in for the event, and the
difference does not matter for the mechanism. The check is a deterministic
function of the committed file, the live API and the clock; the
reconstruction exercised the same values the post-merge state will have
(a committed file trailing the live count by exactly one merge), and I
verified the state this PR will itself create — 68 committed as of
12:26:57.365Z, live 69 after its own merge — satisfies the as-of
comparison. The entry says so itself: "Not yet measured: the first real
merge on top of this change ... and the build after it — the mechanism this
item exists to prove." The tick is a disclosed, faithful replay rather than
a falsified claim; I record that the box's literal event is still unperformed
and will be first tested by the build after this PR merges.
