### `scripts/check-hold-mechanism.mjs`

- Baseline: `ok` on both halves.
- Real historical clearing, using an actual commit that held the file
  (`037a659`, verified via `git show 037a659:docket/HOLD.md`) as base, current
  (unheld) tree as head: `FAIL  docket/HOLD.md was held at 037a659 and is not
  held on this branch.` Correct.
- Creating a hold (base unheld, head held — wrote a throwaway
  `docket/HOLD.md`): `ok    ... creating a hold is not reserved`. Correct.
- Editing an active hold's stated reason (base held at `037a659` with its real
  text, head held with different text): `ok    ... editing the stated reason
  is not the reserved act`. Correct.
- Tampering the `if`/`fi` fragment's body (`halt "..."` replaced with an
  `echo`): `FAIL  ...honouring block differs...`. Correct.
- Deleting the fragment outright: `FAIL  ...no longer carries the ... block in
  its expected shape`. Correct.

**Two real bypasses, both reproduced, both defeat the mechanism while both
checks report `ok`:**

1. Inserted one line immediately *before* the frozen fragment (still inside
   the same `while true` loop, in the same file, fully visible in any diff):
   ```
   : > docket/HOLD.md
   if [ -s docket/HOLD.md ]; then
     halt "docket/HOLD.md is present -- the loop stopped itself and is waiting on a decision"
   fi
   ```
   Result: `ok    docket/HOLD.md was not held at either point` / `ok
   scripts/orchestrate.sh's docket/HOLD.md honouring block is unchanged`. The
   frozen fragment is byte-for-byte identical to base, so the text-diff check
   is satisfied, but the loop can never observe a held file again: every
   iteration re-syncs `docket/HOLD.md` from `origin/main` via `git checkout
   main && git pull --ff-only` (confirmed at `scripts/orchestrate.sh:319-320`,
   which runs *after* the hold check in loop order, so the freshly-pulled file
   is truncated by this line *before* the next iteration's check ever sees
   it) — a maintainer-created hold would be silently defeated on the very next
   iteration, forever, with both new CI checks green.

2. Left the fragment completely untouched and instead edited the `halt()`
   function it calls, defined ~130 lines away (`scripts/orchestrate.sh:154`):
   ```
   halt() {
     note "HALT: $1 (ignored)"
   }
   ```
   (dropped the `exit`). Result: identical `ok`/`ok` output. The frozen
   fragment still reads `halt "docket/HOLD.md is present..."`, so the
   comparison the check performs is satisfied; the actual halting behaviour
   is gone. This is arguably the more dangerous of the two, because editing a
   three-line helper function is exactly the kind of change the check's own
   header comment says is fine and expected ("This does not freeze the whole
   file, which is ordinary, frequently and legitimately improved scripts/").

Both were reverted with `git checkout -- scripts/orchestrate.sh`; tree
confirmed clean after each.

**Why this is a real finding and not a manufactured one.** Rule 13a's own text
says the stop mechanism is reserved "so a brake the loop can teach itself to
ignore is no brake." After this round, the loop still can teach itself to
ignore the brake — not hypothetically, demonstrated twice, with the second
method requiring nothing more unusual than editing a helper function in a
frequently-touched shell script. The check's header comment discloses that it
protects only the named fragment, "byte for byte," and explains why (the same
narrow-fragment approach `check-13a-unchanged.mjs` uses for prose) — but that
disclosure describes what the check does, not that what it does is
insufficient to deliver what rule 13a promises. Nowhere in the entry, the
workflow comments, or CHARTER.md is it said that surrounding code — the
`halt()` definition, or any line that can write to `docket/HOLD.md` before the
frozen check runs — is outside this guard's reach. That is a silently missing
mechanism sitting directly behind a rule whose entire stated purpose is to
make the stop mechanism un-teachable-around. This is exactly the shape the
brief described: "A reserved surface with a silently missing mechanism is
worse than no rule, because it reads as protection."
