## Priority 5 — the changelog parser trap: real, and I think it should have been filed

Read the changelog entry's `Guardrails:` note describing the failure: a
`**4. Leads investigated and dropped**` heading in the first draft matched
`build-log.js`'s `^\*\*(\d+)\.` change-heading pattern, so `validateEntries`
demanded a Hypothesis/Change pair the plain bullets under it never supplied,
breaking `npm run build` at `/sitemap.xml`. Confirmed the fix: the merged
entry's heading now reads `**Leads investigated and dropped**` (no leading
number), and I read the full section — both dropped-lead paragraphs (OpenAI
Ultrafast/Sol duplication, Toyota/Rapidus set-aside-before-fetching) are
present and readable; nothing was lost in the edit.

Ran `node D:/AddictedtoAI/scripts/round.mjs check` myself, foreground, no
backgrounding, default timeout (completed well under it):

    ok    npm run lint
    ok    docket valid
    ok    track scope for loop/scout/gemini-pro-delay-robo-bosses-claude-academy
    ok    npm run build
    ok    all route checks passed

All green, confirming the fix holds and there is no recurrence.

**My judgment: yes, this should have been filed**, to `maintain` or `audit`
(both unbounded, so it would not have competed with the three content leads
for `author`'s scarce budget). The trap is a footgun for every future round,
not just this one: any `**N. <prose heading>**` written anywhere in a
changelog entry — not just in a "changes" section — silently breaks the
production build, with an error message (`Failed to collect page data for
/sitemap.xml`) that gives no hint the cause is a changelog heading shape.
This round only found the cause by importing `app/lib/build-log.js` directly
in a scratch script rather than reading the wrapped webpack trace — that is
exactly the kind of hard-won diagnostic knowledge a docket item exists to
preserve so the next round that hits it doesn't have to re-derive it from
scratch. Removing the number was the right immediate fix for this entry, but
it's a workaround, not a fix to the parser's over-eager pattern match; the
next accidental `**N. ...**` heading anywhere in a future entry reproduces
the same failure. Non-blocking on this round's verdict (the guardrail
already caught and fixed it before merge), but worth naming explicitly since
the brief asked for my opinion.
