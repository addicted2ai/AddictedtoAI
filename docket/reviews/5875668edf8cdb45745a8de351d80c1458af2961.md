## 3. Fail-closed on error — attacked, held for the cases tested, but found one that isn't fail-closed at all

Built a harness (`spawnSync` with `cwd` pointed at scratch directories holding
corrupted `policy.yml` files, so `process.cwd()`-based path resolution in the
real, unmodified `scripts/peak-window.mjs` picks up the bad file) and tested:
missing `policy.yml`, empty `policy.yml`, malformed YAML, valid YAML with no
`deepseek_peak_pricing` key, the key present with no `windows`, `windows: []`,
`windows: "nope"`, an out-of-range `HH:MM`, and a non-`HH:MM` string. All nine
produced a clean `ERROR ` line and a non-zero exit, and `peak_guard()`
correctly treats that as an unauthorised peak window (verified separately by
pointing `REPO` at a directory with a missing script and at a fake script that
exits 0 with garbage stdout — both correctly return `rc=1`).

**One case does not fail closed: an inverted window (`start` after `end`).**

```
--- start-after-end-inverted ---
exit=0
stdout="OFFPEAK now=2026-08-22T01:00:00.000Z"
```

`parseHHMM` validates format and range but never checks `start < end`. When a
window's `start` and `end` are swapped — e.g. `{start: "04:00", end: "01:00"}`
— the comparison `nowMin >= startMin && nowMin < endMin` (peak-window.mjs:274)
is unsatisfiable for any `nowMin`, so that window can never match anything and
the script silently reports `OFFPEAK` for every timestamp, forever, with exit
0. This is not a hypothetical edge case unlikely to occur: it is exactly the
shape of typo a human editing `policy.yml`'s two `start`/`end` pairs by hand
would make, and the item itself exists because this project has "shipped that
[drift] bug more than once." Under the round's own stated philosophy —
"fail-closed... if peak-window.mjs cannot be read... skip this pass and
retry... rather than silently falling back to the exact behaviour that
produced the 2026-08-18 hold" — this is precisely that silent fallback,
just reached through a config typo instead of an unreadable file. It fails
*open*, in the one direction that matters (the guard permanently stops
gating), and nothing in `scripts/test-peak-window.mjs` would catch it because
the test only exercises the two real, correctly-ordered windows.

This is a real gap, not a manufactured one — I would not have found it without
deliberately trying an input the round's own test suite never tries. It does
not affect the windows as currently configured (both are correctly ordered),
so it does not undermine the guard as merged, but it is a latent hole in
exactly the file this item calls the "single place these numbers live," and a
one-line `if (startMin >= endMin) fail(...)` in `parseHHMM`'s caller would
close it.

## 10. The judgement call: should the docket item have moved to `docket/done/`?

I checked how `docket/open/` is actually consumed, rather than guessing.
`prompts/orchestrator.md` line 11, in the orchestrator's very first
state-reading step, is literally `ls docket/open/` — so an item sitting there
is, mechanically, part of "available work" the next orchestrating session
sees first. Separately, `scripts/check-docket.mjs` counts every open item
without a `blocked-on` field against its track's `queue_budget` ceiling
(lines 202-210) — this item carries no `blocked-on` field, so it continues to
consume the `meta` track's open-item budget for as long as it sits in
`docket/open/`, indistinguishable from unstarted work to that script.

I think leaving it in `docket/open/` is the more defensible choice for *this*
item specifically, for a reason stronger than "no PR to cite": one of its own
checked boxes is a `prompts/` edit that CHARTER.md rule 13 makes human-owned,
and the entry itself says the `human-owned-paths` check will fail this
branch's PR *by design* — the maintainer must merge it by hand. That's not an
ordinary review-and-merge lag; the code is not live in the running supervisor
or the running orchestrator prompt until a human acts, and "done" would assert
the guard is protecting the loop when it is not yet doing so. Round 165's
precedent is a weaker comparison than it looks: that round's branch was
author-track, was pushed and had a PR opened the same night, and went through
an ordinary (if bumpy) review-and-merge cycle with no human-only gate blocking
it — closer to "shipped modulo review latency" than "shipped modulo a human
choosing to act."

That said, I don't think round 166's choice is free of the risk the brief
names. Leaving a fully-checked item sitting in `docket/open/` with no
`blocked-on` field is still a real, measured cost against the track's budget,
and still literally present in the one directory the orchestrator reads
first — the in-file "Note, 2026-08-22" mitigates this for a careful reader but
not for anything that only scans checkboxes or file presence. A `blocked-on:
maintainer-merge`-style field (the same mechanism `check-docket.mjs` already
uses to exclude genuinely-blocked items from capacity counts and to report
them separately) would have gotten both properties at once: visibly pending,
not falsely "done," and not counted as available capacity. Neither round used
it. I'd flag that as a gap in the docket's own vocabulary worth raising
separately, not as a defect in this round.
