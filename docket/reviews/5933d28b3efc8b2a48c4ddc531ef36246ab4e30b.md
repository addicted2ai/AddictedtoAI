## Read this section first — it answers the coordinator's stopping-rule question directly

**I found a real, reproduced defect. It does not warrant the proposed cut.**
The dot-truncation/de-gluing mechanism that findings 3, 4 and 5 have been
narrowing across four rounds — `dotCandidatesOf`'s uppercase-boundary rule
and `hasLongerDottedSibling`'s guard — held up completely clean under
everything I threw at it this pass. I found no new instance of *that*
ambiguity family. What I found instead is a different, older, and broader
vulnerability: any non-token character (a zero-width space, an em dash, a
smart quote, several others) lands inside a real identifier's own
characters and silently splits it into two runs, one of which can be a
real, wrong, differently-dated alias. This is not caused by any of the
dot/truncation logic under review — I proved it directly against the very
first shipped commit (`d45a8c9`, before any review or fix existed) and it
reproduces identically there. **Cutting the matcher back to "exact-token
matching only, no de-gluing, no truncation" — the proposed fallback — does
not fix this, because the vulnerability lives in the base tokenizer
(`TOKEN_PATTERN`'s character class), not in anything findings 3–5 touched.**
Reverting would ship a narrower tool with the exact same hole. See section
1 below for the full brute-force evidence. My recommendation is a
different, smaller, separately-scoped fix — strip zero-width/format
Unicode characters before tokenizing — not a sixth round on dot boundaries,
and not a revert.

## 1. Uppercase heuristic — attacked in both directions, held

Fact-checked the load-bearing claim first, against the data rather than
trusting the comment:

```
token-shaped identifiers containing any uppercase letter: 0
dotted identifiers with an uppercase right after an internal dot: 0
```

Both true. Then attacked the heuristic itself:

**Direction 1 — a real sentence boundary followed by a lowercase word,
which the rule was designed to leave unmatched:**

```
"We used gpt-4-0613.then it broke."          -> (none)
"We used gpt-4.1-nano.then it broke."        -> (none)
"gpt-image-1.5.then we upgraded."            -> (none)
```

This is real: casual writing that doesn't capitalize after a period is
common, and the rule intentionally misses it. But I want to be precise
about what kind of finding this is, because it matters for the verdict.
This is **not** a wrong answer — it's the miss the round chose on purpose,
and I checked whether it was chosen more narrowly than it needed to be:
since every dotted identifier's own internal-structure dot is followed by
a **digit**, never a letter of either case, a boundary rule of "dot not
followed by a digit" would be exactly as safe against the data as "dot
followed by uppercase" — verified, not assumed, by the same fact-check
above — while also catching the lowercase-continuation case for free. I'm
noting this as a design observation worth a cheap follow-up, not a defect:
it costs nothing to fix and would recover real coverage, but shipping
without it is still safe, just more conservative than it needs to be.

**Direction 2 — could the heuristic ever fire wrongly and produce a bad
match?** Tried acronyms, proper nouns, an initial, a digit continuation, a
quoted lowercase start, and the dangerous case combined with a typo:

```
"We used gpt-4-0613.NASA uses something else."     -> gpt-4-0613 (correct — real boundary)
"We used gpt-4-0613.OpenAI recommends upgrading."   -> gpt-4-0613 (correct — real boundary)
"gpt-4-0613.A was an internal codename."             -> gpt-4-0613 (a stretch case, but not wrong: A-as-initial is rare and the match is still to the right row)
"gpt-4-0613.5 was never a real thing."               -> (none) — digit after dot correctly treated as internal structure, no false match
"gpt-4..1-nano.Then we moved on."                    -> (none) — consecutive-dot typo plus a real boundary; no uppercase touches the malformed run, correctly a safe miss
```

No wrong answer found from this heuristic in either direction.

## 2. `hasLongerDottedSibling` — does it over-reject?

Checked the exact failure mode the brief named: does it ever catch the
full, untouched, correct run and refuse it?

```
"gpt-image-1 is retiring soon."        -> gpt-image-1 (matches — bare run, guard never consulted)
"gpt-4 is retiring soon."              -> gpt-4 -> gpt-4-0613 (matches — bare run)
"ft-gpt-4 is retiring soon."           -> ft-gpt-4 (matches — bare run)
"gpt-image-1, gpt-4o were both used."  -> gpt-image-1 (comma isn't stripped, candidate === run, guard bypassed)
"We used gpt-image-1.5."               -> gpt-image-1.5 (its own trailing period; hasLongerDottedSibling("gpt-image-1.5",...) = false, correctly unaffected)
hasLongerDottedSibling('gpt-image-1', ...) -> true
hasLongerDottedSibling('gpt-image-1.5', ...) -> false
hasLongerDottedSibling('gpt-4', ...) -> true
```

Confirmed in code, not just by testing: `findMatches` only consults the
guard when `candidate !== run` — a bare, untransformed match is never at
risk. The guard is precisely scoped to the three identifiers it names and
does not over-reject anything else. No defect found here.

## 4. Non-ASCII and whitespace — the one that survived

Tested the four things named directly, positioned as ordinary boundary
punctuation around an identifier first (non-breaking space, smart quotes,
zero-width space, em dash, en dash, a full-width period, a tab) — every one
of these resolved correctly:

```
"We used gpt-4-0613 ."                          -> gpt-4-0613 (correct)
"“gpt-4-0613”.Then we moved on."            -> gpt-4-0613 (correct)
"We used gpt-4-0613—retiring soon."              -> gpt-4-0613 (correct)
"We used gpt-4-0613．Then we moved on."           -> gpt-4-0613 (correct)
```

Then I asked the harder question: what happens when one of these
characters lands **inside** the identifier's own characters, rather than
around it — the shape a Slack emoji-adjacent zero-width joiner or a Google
Docs autocorrect artifact would actually produce. Swept every position of
every one of the 86 token-shaped identifiers with four invisible
characters (ZWSP, ZWJ, ZWNJ, soft hyphen):

```
invisible-character insertion sweep: 5808 probes across 86 identifiers x 4 invisible chars
  wrong-row matches: 248
  still resolved to own row (lucky): 64
  safe miss: 5496
```

and separately with four visible/typographic characters people's
word processors insert automatically (em dash, en dash, NBSP, smart
apostrophe) — **identical count**, confirming this is one general
mechanism, not a quirk of any one character:

```
em-dash/en-dash/NBSP/apostrophe mid-identifier sweep: 5808 probes, wrong-row: 248
```

Example, reproduced directly against the shipped module:

```
"We still reference gpt-4​o-realtime-preview in prod."
  -> matched "gpt-4" -> gpt-4-0613 row (shutdown 2026-10-23, replacement gpt-5.6-sol)
  -- the visitor's actual identifier, gpt-4o-realtime-preview, isn't even in that row;
     it's a different row entirely (shutdown 2026-05-07, replacement gpt-realtime-1.5)
```

**Root cause, and why this doesn't belong to the family under review:** any
character outside `TOKEN_PATTERN`'s class (`[A-Za-z0-9._-]`) — which
includes every zero-width character, em/en dash, smart punctuation, and
non-breaking space — acts as a token delimiter. Insert one inside
`"gpt-4o-realtime-preview"` after the `"4"` and the regex sees two separate
runs, `"gpt-4"` and `"o-realtime-preview"`; the first is a real alias of an
unrelated row. This is **not** a consequence of `dotCandidatesOf` or
`hasLongerDottedSibling` — neither is invoked in a way that matters here;
it is the base tokenization step, present unchanged since the very first
commit. I proved this directly rather than inferring it:

```
ORIGINAL d45a8c9 matcher, ZWSP inserted in gpt-4o-realtime-preview:
hits: gpt-4 -> gpt-4-0613 (also gpt-4, gpt-4-0613-completions, gpt-4-completions)
```

Same wrong answer, on the very first shipped version, before any of the
four rounds of review or fixes this whole chain has been about. **This
means the coordinator's proposed fallback — exact-token matching only, no
de-gluing, no truncation — does not close this hole,** because the hole
isn't in the de-gluing or truncation logic. It's shared by every version of
this file, including the one being offered as the safe answer.

I want to be honest about the one thing I can't fully calibrate: how often
a real paste lands one of these characters *literally inside* a token
(rather than between words or around punctuation, where I confirmed it's
safe). Smart-quote and em-dash autocorrect typically fire at word
boundaries, not mid-word, so the highest-likelihood real-world vector is
probably zero-width characters specifically (common artifacts of
copy-pasting from Slack, certain PDF text layers, or CJK-aware editors),
not the full set I swept. I don't have a way to measure that frequency
from inside this repository, so I'm reporting the mechanism and its
proven blast radius (248 of 5808 probed positions, roughly 1 in 23) rather
than asserting a visitor-encounter rate.

## Test-1 judgment — final answer, not deferred

**For the specific thing four rounds of review have been testing — does
this tool correctly and safely handle the punctuation, typos, and run-on
sentences a visitor actually types — the answer is yes.** I attacked the
uppercase heuristic from both directions, attacked the sibling guard for
over-rejection, reproduced the brute-force arithmetic independently rather
than trusting it, and found nothing. That mechanism is now genuinely
sound, not merely asserted to be: every ordinary way to reference a model
— clean JSON, a YAML value, a vendor-prefixed string, a plain sentence
ending in a period, a run-on sentence with no space, a doubled or
transposed or dropped-character typo, a stray inserted dot — resolves
correctly or safely misses, never wrongly. I would forward this tool to a
stranger for essentially every way a person actually types.

**What keeps this from being an unqualified yes is the finding above, and
I'm not going to soften that to make the answer cleaner.** A visitor whose
paste happens to carry an invisible or autotypeset character landing
inside a model name — a real, if not fully measurable, risk from exactly
the sources the brief named — can still be told a confident, wrong,
sourced answer. That is the one failure mode this tool's whole pitch
cannot survive, and it is still reachable, just through a door none of the
five defects found so far walked through.

My recommendation, stated plainly since this is the last pass: **ship the
dot/truncation work as it stands — it does not need a sixth round — and
close the Unicode gap with a normalization pass (strip zero-width and
similar format characters from the pasted text before tokenizing) as its
own small, separately-scoped fix.** That is a different shape of fix than
anything in findings 3–5 (input sanitization, not per-case disambiguation),
and I'd expect it to be simpler than any of the last three rounds, not a
repeat of them.
