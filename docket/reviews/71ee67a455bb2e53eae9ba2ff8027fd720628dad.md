## Finding 3 — the fail-open hole: fixed, and I could not reopen it

Re-ran my original 9 fuzz cases from the first review against the fixed
script — all 9 still fail closed, and the previously-broken case now reads:

```
--- start-after-end-inverted ---
exit=1
stdout="ERROR policy.yml window [0] start "04:00" is not before end "01:00" -- an empty or backwards window would silently never be peak"
```

New cases I invented for this delta, independent of
`scripts/test-peak-window.mjs`'s own two new cases (swapped, equal):

```
window-missing-both-keys      -> ERROR ...start="undefined" is not HH:MM
non-numeric-hour ("ab:00")    -> ERROR ...is not HH:MM
negative-hour ("-1:00")       -> ERROR ...is not HH:MM
unpadded-hour ("1:00")        -> ERROR ...is not HH:MM   (regex requires \d{2})
one-good-one-inverted (2nd of 2 windows backwards) -> ERROR on window [1]
minutes-out-of-range ("01:61")-> ERROR ...is out of range
windows-is-object-not-array   -> ERROR policy.yml has no deepseek_peak_pricing.windows to read
last-of-three-inverted (3rd of 3 windows backwards) -> ERROR on window [2]
deepseek_peak_pricing: null (whole block null, not missing) -> ERROR ...has no deepseek_peak_pricing.windows to read
```

Validation checks every window in the array, not just the first — both the
"one good, one bad" and "bad is the last of three" cases correctly caught the
broken entry rather than stopping early or checking only index 0.

One case did not fail cleanly: `windows: [null]` (a literal null entry in the
array, as opposed to a window object missing keys) crashes with an uncaught
`TypeError: Cannot read properties of null (reading 'start')` — a Node stack
trace on stderr, empty stdout, exit 1 — rather than the script's own
documented clean `ERROR ` line. I checked whether this reopens the fail-open
hole by running it through the real `peak_guard()`, not just
`peak-window.mjs` alone:

```

...

risking a double-rate start on an unreadable signal. Not starting a new

```

Empty stdout doesn't match `"OFFPEAK "*` or `"PEAK "*`, so `peak_guard()`'s
catch-all still fires and the guard still fails closed — this is the same
category of pre-existing rough edge I noted but didn't flag in the first
review (a missing script path produces the same kind of ugly-but-safe crash).
It predates this fix, isn't something the round claimed to have addressed,
and doesn't reopen the specific hole (silent `OFFPEAK` forever, exit 0) that
was the actual finding. I'm recording it as checked, not as a new finding.
