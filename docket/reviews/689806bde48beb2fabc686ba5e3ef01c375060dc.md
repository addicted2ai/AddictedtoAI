## Attack 1 — the line-length ceiling (107): fitted, but disclosed as fitted

Reproduced the round's own measurements from scratch, independently, against
the round's own running server (`node scripts/check-article-line-length.mjs
http://localhost:3000`, using the exact HEAD build `round.mjs check` had just
built and was serving):

    ok    /model-retirement-calendar  median 90, max 101
    ok    /what-vendors-promise       median 92, max 101
    ok    /blog                       median 93, max 105
    ok    /blog/chatgpt-ads           median 94, max 102
    ok    /model-deprecation-checker  median 87, max 96

Exact match to the CHANGELOG on every number, including the 105 max on
`/blog` that sets the tight side of the margin. **107 is not derived from any
external standard** — WCAG names no such number — **it is reverse-engineered
from this round's own pre/post measurements**: strictly between the highest
post-fix max it measured (105) and the lowest pre-fix max it measured (108).
That is exactly the shape the brief warned about. The difference from a
hidden version of that defect is that the script's own header says this in
so many words ("It is not a general readability judgement... fails if the
`80ch` rule is ever removed or loosened past this specific boundary... does
not fail on the fixed state with margin to spare") — this is disclosed, not
smuggled in as an implied accessibility guarantee.

What I'd still flag: **two characters of headroom over the worst measured
page is thin for a check whose stated job is catching CSS regressions**, not
content edits. A future round adding one longer word to a `/blog` paragraph
— no CSS change at all — could plausibly push that page's max line past 107
and fail the check for a reason that has nothing to do with the `80ch` rule
it's supposed to guard. This is a fragility risk worth a maintainer's
attention, not a defect in what this round claimed or shipped.

## Attack 2 — the nav cue: argued both ways, then proved by breaking it myself

**The case for it being colour-only in spirit:** the only CSS property that
changes between active and inactive is `border-bottom-color` — literally a
colour property, going from `transparent` to `var(--accent)`. An automated
auditor comparing declared CSS properties would plausibly still flag this as
"distinguished by a color property," and the two states share every other
computed style (width, font-weight, text-decoration untouched).

**The case for it satisfying 1.4.1's actual intent:** `transparent` is alpha
0, not a low-contrast color — genuinely no line renders, not a faint one.
Converting the page to true grayscale does not erase the distinction: the
active link still shows an opaque line (whatever gray `#5eead4` maps to),
the inactive links still show nothing, because the toggle is
opacity/presence, not hue. SC 1.4.1's concern is exactly this — can the
state still be read with color vision entirely removed — and by that test it
survives. I find this the stronger reading, but it is genuinely arguable, and
the shipped comments in both `app/globals.css` and
`scripts/check-nav-active-cue.mjs` argue it both ways themselves rather than
asserting it flatly, which is the right way to record a debatable call.

**Verified the implementation matches the claim, not just the argument:**
`.nav a` reserves `border-bottom: 2px solid transparent` (`app/globals.css`
line 94, on the base selector — every link, not just when active); `* {
box-sizing: border-box }` (line 20) is what keeps that reservation from
growing the `min-height: 44px` box (line 86). `app/Nav.js` sets
`className="nav-active"` only on an `<a>` that is itself one of the `.nav a`
elements the check queries (`isActive = pathname === link.href`, inside
`<nav className="nav">`) — there is no path where an active link exists
outside the nav the check looks at.

**Verified the detection cannot false-pass, myself, one fix at a time** (the
brief specifically asked for this over the round's own all-at-once revert).

## A real finding: the "secondary vs primary" consistency argument doesn't hold everywhere it's asserted

The round's stated reason for capping `article p` at `80ch` instead of
matching the site's existing `62ch`/`68ch` family — repeated near-verbatim in
`app/globals.css`'s comment, the CHANGELOG entry, and the closed docket
item's status note — is that `.hero-lead`, `.log-lead`, `.log-field`,
`.log-note`, and `.walkthrough-caption` all "cap secondary, supporting text
(captions, leads, per-entry fields)" while `article p` is "the primary
long-form reading column."

That holds for `.hero-lead` (the homepage), `.log-field`/`.log-note`
(structured per-round metadata), `.walkthrough-caption`, and even for
`.log-lead` on `/charter` and `/model-retirement-calendar` — on those pages
it genuinely is a short lead-in before a wider primary body. **It does not
hold for `.log-lead` on `/log`, `/log/early`, or `/log/archive`.** I read all
three route files in full: none of them wraps its content in `<article>` at
all (root element is a plain `<div>`), and the only free-running prose on
each page is three or four `.log-lead` paragraphs — there is no wider
`article p` reading column on these pages for `.log-lead` to be secondary
*to*. On `/log/early` and `/log/archive` specifically, `.log-lead` is the
entirety of the page's body prose, capped at 62ch, while `article p`
elsewhere on the same site now gets 80ch — the exact inversion of "secondary
vs primary" the round's own rationale claims as a universal distinction.

This does not undermine the actual decision for the five pages the round
measured and fixed — `article p` genuinely is the primary reading column on
all five, and the `80ch` cap is justified independently of the family
comparison, by its own rendered measurements and cost data, which are sound
(previous section). It's a mischaracterization in the supporting rationale,
not a functional, safety, or accessibility defect, and it doesn't affect any
check. But it is a real instance of this project's named pattern — prose
asserting a categorical claim slightly stronger than what's actually true —
and it's stated three times, not once, so a future round citing "the
existing family is all secondary text" as settled fact would be citing
something this review found false for at least two live routes.
