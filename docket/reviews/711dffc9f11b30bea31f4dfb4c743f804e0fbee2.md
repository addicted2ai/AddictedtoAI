## Blocking finding

**The entry's claim that the dead-default bug is gone is falsified; its sibling
survives in the same function.**

The entry: "The mutation experiment also caught a real latent bug in the first
draft of `wait_for_checkout_free`: the idle window was read in arithmetic
without its default, so an unset variable read as zero and the guard never
fired; the defaults are now captured once at the top of the function."

The function reads three configurable variables with defaults:
`CHECKOUT_WAIT_SECONDS`, `CHECKOUT_IDLE_SECONDS`, and `TICK_SECONDS`. The first
two are captured at the top (lines 110-111). `TICK_SECONDS` is not: it is read
in the loop body twice, inconsistently —

    sleep "${TICK_SECONDS:-30}"
    waited=$((waited + TICK_SECONDS))

With `TICK_SECONDS` unset, `sleep` uses 30s but `waited` adds 0, so the bound
can never be reached. I ran it against the real API with a busy attributed
session, bound=4:

    timeout 45 bash -c 'source scripts/orchestrate-liveness.sh; ... wait_for_checkout_free'
    -> no output, no return; killed at 45s (outer-exit=124)

That is the entry's own failure class verbatim — "an unset variable read as
zero and the guard never fired" — except here it is the bound that never fires,
and the guard never returns at all. (In a `set -u` shell the arithmetic errors
with "unbound variable" instead of adding zero, but the loop still never
advances.)

Reachability: in `scripts/orchestrate.sh` it cannot fire — `TICK_SECONDS` is
always set at line 103, before the source at 275 and the call at 302 — and the
test always sets it. So this is a latent hazard in an exported file (its header
says it exists "so the supervisor can source them and a test can source them
directly") and a falsified changelog sentence, not a production hang. The
changelog is permanent once merged; per the review contract a claim the record
makes about the code, that a command shows false, blocks. The fix is the same
shape as the fix it describes: capture `local tick="${TICK_SECONDS:-30}"` once
at the top and use it in both places.

## Non-blocking findings

1. The mutation descriptions are accurate quotes but incomplete. Removing
   attribution fails **two** scenarios (pre-launch boundary first, trap
   second); removing the bound fails **three** (deferral, zombie, mixed). The
   entry names one failure per mutation as if it were the only one.
2. The trap session's "is attached and advancing and never stops on its own"
   is not observable today: I sampled `ses_ff4a68c7` five times over 12+
   minutes (19:09–19:21Z) and its `time.updated` never moved (frozen at
   19:05:10Z). Its 2h52m of post-death advancing supports the historical claim;
   whether it is in a >600s silent generation or has finally stopped I cannot
   distinguish. Either way the design does not depend on its current state.
   Related: the store holds 100 sessions and the oldest entries are being
   evicted; a dropped session reads as free (fail-open — consistent with the
   liveness philosophy).
3. The 600s idle window sits between the 238s measured maximum silent
   generation and the >10-minute freezes I observed in real sessions today. If
   those freezes are generations rather than stops, a checkout can still land
   inside one — the exact failure the wait exists to prevent. If they are
   stops, 600s is fine. I could not tell which. The "Result: not yet measured"
   line covers this honestly; flagging it as the sharpest edge of the trade-off.
4. The bound counts sleep time only. Each probe is a curl (max-time 10) plus a
   node spawn; with a slow-but-accepting API the wall time can exceed
   `CHECKOUT_WAIT_SECONDS` by up to (bound/TICK) x 10s ~ 20 minutes, and the
   note's "after ${wait_bound}s" understates that. Minor.
5. `[ "$((newest + idle))" -gt "$now" ]` uses strict `>`, so a session exactly
   `idle` seconds old counts as free. Off-by-one in a 600s window; trivial.
6. `created == floor` is attributed and `created` omitted/0 is not — both
   consistent with the documented boundary ("at or after") and with fail-open.
7. The first "Done when" box ("A review session can run to completion without
   its branch being switched") is ticked on the strength of the mechanism plus
   stub tests while the entry's Result says production behaviour is "not yet
   measured". The changelog carries the honest half; noting the tension.
