## Findings

**1. The "-free exclusion is absolute" claim is false for a spelling this
round's own catalogue query would have surfaced.**

`scripts/runners.yml`'s `excluded_model_patterns` is one rule:
`pattern: "-free$"`, described as "Absolute exclusions... a runner entry
above cannot exempt itself from a standing instruction by being the one
picked" and tied to FRAME.md fact 18 ("OpenCode's `-free` model variants are
excluded absolutely"). The round proved this catches OpenCode Zen's own
`deepseek-v4-flash-free` (hyphen-suffixed) and reported that as one of seven
proofs.

OpenCode's real, live `/provider` catalogue — the same endpoint this round
queried and pasted output from — uses a *second*, different suffix
convention for free-tier models on several providers: a colon, not a hyphen
(`model:free`, not `model-free`). This convention is not exotic or unrelated
to this account: it is used by `openrouter`, which is already in this
server's own `connected` list (`opencode-go-deepseek-max`'s neighbor
providers), and by several other catalogued providers (`kenari`,
`unorouter`, `kilo`, `zenmux` all list `deepseek-v4-flash:free` or other
`:free` models). `openrouter` alone currently lists 17 colon-suffixed free
models, including `openai/gpt-oss-20b:free`.

Reproduced against the real server and the real regex:

```
$ node -e "console.log(/-free\$/.test('deepseek-v4-flash:free'), /-free\$/.test('openai/gpt-oss-20b:free'))"
false false
```

Then against the real `runner-preflight.mjs`, with one temporary entry added
to `scripts/runners.yml` (reverted immediately after; `git status --short`
confirmed empty):

```yaml
  TEMP-colon-free-proof:
    harness: opencode
    provider: openrouter
    model: "openai/gpt-oss-20b:free"
    variant: max
```

```
$ node scripts/runner-preflight.mjs TEMP-colon-free-proof
PASS        runner known: TEMP-colon-free-proof
PASS        harness known: opencode
PASS        harness present: opencode -> C:\Users\BadBitch\AppData\Roaming\npm\opencode.CMD
PASS        model not excluded: openai/gpt-oss-20b:free
PASS        harness server reachable: http://127.0.0.1:4097
PASS        provider authenticated: 'openrouter' is in the server's own connected list
PASS        model in catalogue: 'openai/gpt-oss-20b:free' is one of 350 models listed for 'openrouter'
RUNNER_OK harness=opencode provider=openrouter model=openai/gpt-oss-20b:free variant=max
```

A genuinely free-tier model, on a genuinely connected/authenticated
provider, passes "model not excluded" and gets a clean `RUNNER_OK`. This is
exactly the attack the brief named — "an excluded `-free` variant reached by
some other spelling" — and it succeeds. It is not exploitable through any of
the four runner entries this round actually shipped (none names a
colon-suffixed model), so nothing that runs today is affected. But the
mechanism is general-purpose — any future runner entry can name any
connected provider's catalogue model — and the round's own header text
promises that generality ("checked against whichever runner is selected...
cannot exempt itself... by being the one picked"). As written, a future round
adding an OpenRouter- or Kilo-routed runner (both real, both connected or
reachable through this account) would sail through the standing "`-free` is
absolute" instruction with no error, no warning, and a `RUNNER_OK` that looks
identical to a legitimate paid-tier launch — silently the opposite of the
property this round's own header spends four paragraphs asserting.

Suggested direction (not applied — reporting, not fixing, per the brief):
widen the pattern to catch both conventions (e.g. `[:-]free$`), or, since
the two conventions are provider-specific quirks rather than a single stable
grammar, treat `excluded_model_patterns` as a list built to grow rather than
a single hyphen-anchored regex, and note in the header that it was checked
against one spelling, not enumerated against the full connected catalogue.

## Why request-changes and not reject

The runner-availability half of "never silently substitute" — the property
the brief called out first — is solid: I could not get a failed preflight to
launch anything, under any of the scenarios I tried, live or sandboxed. The
exclusion-list half of the same property is not: a real, reachable, already
authenticated path exists today to run a genuinely free-tier model with a
clean `RUNNER_OK`, contradicting the round's own "absolute... by standing
instruction" framing for the mechanism it built to enforce that. Nothing
currently shipped in `runners.yml` exploits it, but the gap is in the
general mechanism, not in a specific runner entry, and the round's own
proof-by-construction methodology (querying `/provider`, inspecting Zen's
catalogue in detail) had the data in hand to have found the colon-suffixed
convention on `openrouter` — an already-connected provider — without
needing to look further afield.
