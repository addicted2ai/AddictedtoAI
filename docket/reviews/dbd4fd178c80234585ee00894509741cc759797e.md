## Findings

**1. The dispatcher's own "2x ceiling" invariant comment is now false, and
the safety argument for removing meta's share cap depended on it.**

`scripts/dispatch.mjs` (untouched by this diff, lines 245-247) still reads:

> Two constants are load-bearing and must not be tuned casually:
> - **The 2x ceiling** is what makes a hard share cap on meta unnecessary:
>   a queue that runs away can at most double its track's weight; it can
>   never take the rotation.

`effectiveWeight()` is now `weight * min(pressure, 2) * pushAppliedFor(track)`,
and `pushApplied` tops out at `PUSH_MULTIPLIER` (3.0 per `policy.yml`) when a
track's ready stock is 100% `worth-a-visit`. Both ceilings are simultaneous
and multiplicative, so the real ceiling on any track that has *both* a
`queue_budget` and `worth-a-visit` stock is **6x**, not 2x. Confirmed by
calling the round's own functions directly with the actual `policy.yml`
numbers, `build`'s real weight (15), and a saturated ready queue (28 items,
budget 14, 100% `worth-a-visit`, 0 closed):

```
effectiveWeight("build") = 15 * min(28/14, 2) * pushApplied(3.0, 1.0)
                          = 15 * 2 * 3.0
                          = 90.00   (share of total weight across all six tracks: 59.0%)
```

This isn't only build's exposure. The mirror rule (verified below) accepts
`worth-a-visit` for every advancing track, and `author` (`queue_budget: 6`)
and `meta` (`queue_budget: 14`) both go through the same `budget != null`
branch in `effectiveWeight()`, so both are equally subject to the 6x ceiling
if their ready queues ever fill with `worth-a-visit` items. That matters
specifically for meta: `policy.yml`'s own comment for meta's weight says
`max_share_of_runs: 0.10` was removed 2026-08-16 because "the dispatcher's 2x
ceiling on pressure bounds meta by construction, which is a stronger
guarantee than a cap that was never binding." This round weakens that exact
guarantee for meta — a track this round's own `check-docket.mjs` change
allows to file `worth-a-visit` items — without mentioning the exposure
anywhere in the entry, `CHARTER.md`'s amendment, or a code comment.

I then modeled whether "6x on the raw weight" actually means "build can
starve every other track," since the dispatcher doesn't award tracks
proportionally — it picks the single most-owed track each round from a
20-round trailing window (`decide()`'s `target - actual` logic). Using
dispatch.mjs's exact selection algorithm and generative-push.mjs's exact
functions, I simulated 40 rounds starting from the saturated-build snapshot
above, "shipping" one generative item every time build is picked (which both
drains its ready count and decays the multiplier, matching how the push is
anchored):

```
round  1: picked build     (target 59%, actual 0%,  M=3.00, buildReady=28/28gen, closed=0)
round  2: picked maintain  (target 18%, actual 0%,  M=2.75, buildReady=27/27gen, closed=1)
round  3: picked scout     (target  7%, actual 0%,  M=2.75, buildReady=27/27gen, closed=1)
round  4: picked build     (target 56%, actual 33%, M=2.75, buildReady=27/27gen, closed=1)
...
round 26: picked author    (target 12%, actual 5%,  M=1.00, buildReady=20/20gen, closed=8)
...
round 40: picked build     (target 23%, actual 20%, M=1.00, buildReady=17/17gen, closed=11)

build picked 12 of 40 rounds (30%)
```

So the "most owed" scheduler does throttle it — build never exceeds ~30% of
picks even under a permanently-saturated adversarial queue, and the
multiplier reaches its floor (`M=1.0`, matching the round's own boundary
test) after 8 shipped items, around round 20-26. It is not "exclusive," and
the maintainer's "high, decaying to balanced" framing is met in practice for
this scenario. But that is not something the round demonstrated or the code
documents — I had to write the simulation myself, dispatch.mjs's own comment
about "the 2x ceiling" is simply wrong now, and the removed meta cap's stated
justification is unexamined. Request-changes: at minimum the comment needs
correcting to state the real combined ceiling and mechanism (weight * 2 *
push), and the entry or a comment should say whether meta's cap-removal
rationale still holds now that meta is push-eligible too — not leave two
policy decisions quietly contradicting each other.

**What the decay counts, and whether it can be silently reset (brief item
2).** `closedGenerativeCount` reads `docket/done/` fresh on every dispatch
call, so if closed items were ever archived or pruned elsewhere the count
would drop and the multiplier would come back up — a real structural risk in
principle. I checked whether anything does this today:

```
$ git log --diff-filter=D --oneline -- docket/done/     # empty
$ git log -M --diff-filter=R --oneline -- docket/done/  # empty
```

No file has ever been deleted or renamed out of `docket/done/` in this
repository's history. `policy.yml`'s `prune_after_expiry_days` and
`scripts/preflight.mjs`'s prune report only ever look at `open` items
(`preflight.mjs` line 74 reads `policy.docket?.prune_after_expiry_days`
against `open`, not `done`); `check-docket.mjs`'s `expired` list is built
from `counted = open.filter(...)`. Nothing in this repository archives
`docket/done/` today. This is a real dependency the push mechanism takes on
forever, and nothing documents it as an invariant to protect — but it is not
a defect in this diff, so I'm not counting it as a finding, only flagging it
as unguarded.
