## 2. Punctuation matrix — a context the coordinator's fix did not cover

Derived my own cases rather than re-running the shipped
`PUNCTUATION_WRAPS`/`PUNCTUATION_SAMPLES` matrix (11 wraps × 4 identifiers,
all comma/`!`/`?`/`:`/brackets/quoted-JSON/ellipsis/possessive/end-of-line/
sentence-final-period — none of which glue a following word onto the
period). Found one real gap: **a sentence-final period with no space before
the next word** — a genuine, common typing/formatting artifact (fast
typing, some PDF-to-text extraction, casually punctuated chat) — still
defeats the token path:

```
[no space after period (typo), token id]
  text: "We used gpt-4-0613.Then we switched vendors."
  hits: (none)

[no space after period (typo), phrase id]
  text: "We used the Assistants API.Then we migrated off it."
  hits: Assistants API
```

Root cause: `tokensOf()`'s fix only strips dots at the very end of an
already-extracted token (`replace(/\.+$/, "")`). When no space follows the
period, `.` stays a token character mid-run (`TOKEN_PATTERN` never treats
it as a boundary), so the regex greedily extracts `"gpt-4-0613.Then"` as
one continuous token — the dot is no longer trailing, it's internal, and
the fix's own rule ("only a dot at the very end of a token is touched") by
its own logic does not reach it. The **phrase** path is unaffected by this
because `phraseMatches()` only inspects the single character immediately
after the matched substring, and `.` was already whitelisted as a
non-connector regardless of what follows it — so the asymmetry is real:
the token fix is narrower than the phrase fix for what is otherwise the
same underlying ambiguity the file's own comment names ("`.` is the one
character in `TOKEN_PATTERN` that is genuinely ambiguous").

This is a real, reproduced, non-manufactured defect, found by doing exactly
what was asked ("find a punctuation context I did not think of"). It is
narrower than the original finding 1 — it requires *both* no space before
the period *and* no space after it, not just the former — but it is the
same defect class returning in a shape neither the entry nor its 264-check
suite tests for, and it sits directly against the entry's claim that the
false negative "is fixed and now permanently regression-tested, in both
directions, so neither can return silently." That claim is true for the
exact repro sentences review found; it is not true in general.

Also checked, in the same session, two shapes that turned out *not* to be
bugs (reported for completeness, not padding): an identifier immediately
followed by a filename extension with no space (`"gpt-4-0613.py"`,
`"gpt-4-0613.json"`) also fails to match, but this is arguably out of
scope — it's a filename, not a mention of the model — and I would not block
on it alone.
