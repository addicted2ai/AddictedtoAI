## 2. The "one real limit" — checked, holds, with the caveat proving a negative deserves

The claim is that the loop can reach session-starting, commit-reverting, and
operating under its credentials, but cannot rotate or revoke the credential
itself — "an account-level action outside anything the loop's own token can
reach." This is an absence claim, which no single command proves the way the
presence claims above do. What I checked:

- The token is `gho_`-prefixed — a GitHub OAuth (device-flow) token, not a
  classic (`ghp_`) or fine-grained (`github_pat_`) personal access token.
  Renewing or widening it requires the interactive `gh auth login` browser
  flow; revoking it is done from the account's own
  Settings → Applications → Authorized OAuth Apps page, or by the
  registering OAuth app's client secret calling the grant-revocation
  endpoint — neither reachable by bearer-token API calls using the token
  itself.
- The observed scope list (`gist`, `read:org`, `repo`, `workflow`) contains
  nothing resembling token or OAuth-application management. GitHub does not
  expose a scope that lets a bearer token manage, rotate, or revoke itself;
  this is a platform property, not something a broader grant would change.
- Indirectly corroborated by this project's own prior finding (referenced in
  my working notes, not re-derived here): `git push` on this repository
  ignores a `GH_TOKEN` environment override, meaning the operative credential
  is the one already resolved via the stored auth, not something swappable
  by the loop setting an environment variable.

I could not find, and do not believe exists, a path by which the loop's own
token could rotate or revoke itself. This is the correct shape of evidence
for a negative claim — absence of any relevant capability in the observed
scope, plus the platform's own architecture — rather than a single
disqualifying test, and I want to be precise that it's a different kind of
verification than the presence claims in section 1.
