## Summary

The checker's core promise — paste text, get back an accurate verdict on
whether a model in it is dying — does not hold. I found a real false
negative and a real false positive, both reproduced by running the exact
shipped code (`app/lib/model-deprecation-checker.js`) against realistic
pastes, neither caught by the round's own 103-check health suite despite
the entry's claim that the suite "re-verifies... that this matching still
finds every identifier and alias currently in the data." Everything else I
attacked — the alias parser, the scope/changelog/origin guardrails, the
docket items' premises, the client-side claim, the health check's ability
to fail, and the entry's own numbers — held up under direct verification.

## What I attacked, and what happened

### 1. False negative: a trailing sentence period breaks nearly every identifier

`TOKEN_CHARS`/`TOKEN_PATTERN` in `app/lib/model-deprecation-checker.js`
include `.` as a token character (needed for dotted identifiers like
`gpt-4.1-nano`). But the tokenizer is greedy with no lookahead, so when an
identifier is immediately followed by an end-of-sentence period with no
space — the single most natural way to reference a model in prose — the
period gets absorbed into the token, and the resulting string no longer
equals the identifier in `RETIREMENT_DATES`. Reproduced directly against
the shipped module (not simulated):

```
node -e attack script against app/lib/model-deprecation-checker.js findMatches()

[trailing period, end of sentence]
  text: "We are still on gpt-4-0613."
  hits: (none)

[trailing period, primary id]
  text: "Our pipeline calls gpt-3.5-turbo-0125."
  hits: (none)

[trailing period vs no period (control)]
  text: "Our pipeline calls gpt-3.5-turbo-0125 today"
  hits: gpt-3.5-turbo-0125 -> gpt-3.5-turbo-0125 (also gpt-3.5-turbo, gpt-3.5-turbo-completions)

[alias with trailing period]
  text: "We still use gpt-4."
  hits: (none)

[vendor-prefixed with trailing period]
  text: "We call openai/gpt-4-0613."
  hits: (none)
```

`gpt-4-0613` is a *retired* row (shutdown 2026-10-23 has not passed as of
today, but the primary form's alias `gpt-4` covers an already-superseded
snapshot and the row itself is dated) — a visitor who writes the single
most natural English sentence about it gets told nothing. Comma, exclamation
mark, colon and closing-paren are all correctly excluded from the token
class and do **not** trigger this (verified: trailing comma, `!`, `:`, and
`)` all still matched correctly) — only `.` does, because it's the one
punctuation mark the tokenizer had to keep for version numbers like
`gpt-4.1-nano`.

Quantified how much of the data this exposes: of the 92 matchable
identifiers (primary + aliases) in `RETIREMENT_DATES`, 86 (93%) are
token-shaped and therefore vulnerable to this exact failure whenever a
paste ends the identifier's mention with a period and no trailing word.

I checked whether the round's own health check
(`scripts/check-model-deprecation-parser.mjs`) would have caught this. It
does not: every per-row sweep sentence is `"Our deployment still references
${primary} in the pipeline."` (identifier followed by a space, never a bare
period), and every hardcoded `FIXTURES` entry also places the identifier
mid-sentence or inside quotes, never immediately before a sentence-ending
period. The health check's own coverage has a real gap here, not just the
matcher.

### 2. False positive: unguarded substrings on the phrase-shaped identifiers

Six identifiers in the data are not made of pure token characters and so
are matched via a raw case-insensitive `haystack.includes(needle)` with
**no word-boundary check at all** (unlike the token-matched majority, which
get the `TOKEN_CHARS`/`tokenSet` protection specifically built to stop
`"gpt-4"` matching inside `"gpt-4o-mini"`). I tested whether that unguarded
path fires inside ordinary English. It does, confirmed against the shipped
module:

```
[videos api unrelated compound]
  text: "Our videos apis are all custom-built."
  hits: Videos API

[agent builder unrelated]
  text: "The agent builder-pattern used here is different from OpenAI's."
  hits: Agent Builder

[apiece false-positive probe]
  text: "We split the cost of the assistants apiece, five bucks each."
  hits: Assistants API
```

"Videos API" and "Agent Builder" are the concerning ones — both are generic
enough two/three-word phrases that a visitor describing their *own*,
unrelated product ("our videos APIs", "we built an agent builder for
internal automations") gets a confident, dated, vendor-linked "this is
retiring" result for something that has nothing to do with OpenAI. This is
exactly the failure mode the brief calls worse than no checker: not "I
don't know," but a wrong, specific, source-linked answer. This is also
untested by the health check — none of its `FIXTURES` probe a phrase
identifier inside unrelated surrounding text, only inside sentences that
are actually about it.

The brief's own named boundary case — `"gpt-4"` must not match inside
`"gpt-4o-mini"` or `"gpt-4-turbo-2024-04-09"` — I re-checked directly and it
holds; the token-matched path is sound. The gap is specifically the six
phrase-matched identifiers, which get none of that protection.

### 4. The "nothing found" state as a safety claim

The empty-result copy reads: *"No identifiers from the retirement data found
in what you pasted. That means either everything you referenced is fine, or
it is not one of the 77 OpenAI and Anthropic identifiers this checker knows
about."* This is a real, deliberate hedge against the two-vendor-only scope
concern the brief raises (a Mistral/Llama/Cohere paste correctly cannot be
claimed safe). But finding 1 above means this disjunction is not actually
exhaustive: there is a third case the copy does not name — *it is a model
in the data, and the parser simply failed to see it.* A visitor whose
`gpt-4-0613.`-ending sentence produces "nothing found" is told it's either
fine or out of scope, when in fact it may be neither. This is a consequence
of finding 1, not a separate defect, but it means the reassurance copy is
currently overstating what "nothing found" guarantees.

## Would a stranger find this worth their attention?

The concept is genuinely good and the discoverability, health-check
wiring, and docket hygiene around it are careful. But the brief asked me to
weight effort toward making the tool give a wrong answer, and it did, twice,
on paste shapes an ordinary visitor would actually use — a sentence ending
in a period, and a sentence mentioning their own "video API" or "agent
builder." A stranger who pastes clean JSON gets a trustworthy answer; a
stranger who describes their situation in a normal sentence has a real
chance of being told either "you're fine" when they are not, or "this is
retiring" about something that has nothing to do with the vendor named.
For a tool whose entire value proposition is "trust this instead of
scanning the table yourself," that is not a minor rough edge — it is the
one failure mode this specific tool cannot afford. I would not forward this
as-is; I would forward it once the tokenizer stops eating a trailing
period and the six phrase-matched identifiers get a word-boundary check
like the rest of the data already has.
