## Task 1: try to defeat the sequence check

Re-ran both of last pass's winning attacks first, to confirm the round's own
claim that they're now closed:

```
$ node D:/AddictedtoAI/scripts/check-frame.mjs "<scratchpad>/test-frame-fixture6-decoy2.md"
FAIL        sequence: recognised IDs do not form {1, ..., 2} -- missing [2], unexpected [99]
...
exit=1

$ node D:/AddictedtoAI/scripts/check-frame.mjs "<scratchpad>/test-frame-fixture7-gap.md"
FAIL        sequence: recognised IDs do not form {1, ..., 3} -- missing [3], unexpected [47]
...
exit=1
```

Both closed, naming exactly the missing and unexpected IDs as the
coordinator's own reproduction showed. Then tried four further variants
aimed at the specific seams the coordinator named:

**A fact whose heading is recognised but whose body is absent.** A
well-formed `## 3.` heading with no `**Status:**` and no check block at all,
declared total 3:

```
FAIL        3. Third fact... -- malformed (missing Status or, for verified, a check block)
...
sequence (declared): recognised IDs [1,2,3] vs expected {1..3}
exit=1
```

The sequence check itself reports no gap here — ID 3 *is* in the recognised
set, just attached to an empty chunk — but `malformedBody` (unrelated to
this round's change, present since an earlier pass) independently fails the
build over the same fact. Not a silent pass; caught by an adjacent
mechanism, correctly.

**An ID recognised twice, in place of a gap rather than an unrelated
number.** Deleted fact 3, duplicated fact 2's number instead of inventing a
new one — hoping the duplicate might inflate the set enough to paper over
the gap:

```
FAIL        sequence: recognised IDs do not form {1, ..., 3} -- missing [3], unexpected []
FAIL        fact number 2 is used by more than one heading
...
sequence (declared): recognised IDs [1,2] vs expected {1..3}
exit=1
```

It doesn't work, and the reason is structural, not incidental:
`recognisedIdSet` is a `Set`, so a duplicate collapses back to one member
rather than inflating coverage — the gap at 3 stays visible regardless of
how many times 2 is repeated. `duplicateIds` (pre-existing) also fires
independently on the same input. Two mechanisms agreeing rather than one
covering for the other's blind spot.

**A fact with no leading `#` at all** — the one gap the round's own header
comment explicitly declines to claim coverage for:

```
FAIL        completeness: ... declares 2 fact(s), but only 1 heading-like line(s) were found by any scan
FAIL        sequence: recognised IDs do not form {1, ..., 2} -- missing [2], unexpected []
...
exit=1
```

Worth stating plainly: even the one gap the header honestly discloses as
uncovered does not produce a silent pass. No diagnostic *names* the
specific hidden line (correctly disclosed — the code cannot see a line that
never becomes a candidate), but the count and sequence checks both still
fire and fail the build loudly, because the missing ID simply never enters
`recognisedIds` at all. The disclosed gap is "no specific diagnosis," not
"silently green."

**What I could not find a way past, and don't think is in scope for this
mechanism:** replacing a fact's actual claim and check command while
keeping its heading number, `**Status:** verified`, and a check that
happens to print `PASS` — a content swap under a stable, well-formed ID.
Nothing in a structural parser can tell that fact 5's check no longer tests
what fact 5's prose claims; that is a semantic question, not a structural
one, and this project already has a separate mechanism aimed at exactly
that class of problem (human/model review of the diff, `review-artifact`).
I considered this worth naming rather than silently excluding, but did not
treat it as a defeat of the sequence check specifically — the guarantee
this change makes is about IDs 1..N each having exactly one syntactically
valid, executed claim behind them, not about whether that claim's content
is the right one, and the header comment never claims the latter.

I did not find a way to make a fact structurally go missing while the
sequence reconciles.

## Task 2: is the bound now stated exactly?

Close, and I could not find a hole in the stated bound itself. The header:
"this guarantee holds as long as the declared total in FRAME.md is bumped

Two small textual imprecisions, neither a functional gap, noted for the
record rather than as findings:

- Point (4) reads: "Fixed below with an explicit set check: every integer
  from 1 to the declared total must appear exactly once among the
  recognised IDs." A pure set comparison can only prove *at least once and
  nothing outside range* — "exactly once" is enforced by pairing the set
  check with the pre-existing `duplicateIds` check (confirmed above: the
  duplicate-instead-of-gap attempt is caught by `duplicateIds`, not by set
  membership, which silently collapses duplicates). The summary sentence
  credits one mechanism with a property that needs both; the inline code
  comments next to the actual logic (lines ~215-233) are correctly scoped
  and don't make this conflation. Functionally sound, since I confirmed
  both mechanisms fire; only the top-level summary compresses two
  guarantees into one sentence.
- The bound's "no renumbering" framing has one benign edge case: a clean
  two-fact swap (fact 5's content relabelled 6, fact 6's relabelled 5)
  leaves the recognised set exactly `{1,...,N}` unchanged, so it is
  technically a renumbering the sequence check cannot see. It's harmless
  because each check still executes and reports on its own actual command
  regardless of which number labels it — nothing goes unchecked, only
  potentially mislabelled — so I'm treating it as the same content-fidelity
  question as above, not a structural defeat.
