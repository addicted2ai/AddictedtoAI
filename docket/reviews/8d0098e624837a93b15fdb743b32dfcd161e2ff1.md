## Finding — "structurally 0" overclaims; the real guarantee is process-enforced, not code-enforced, and the process has a known hole

Three places now say meta cannot reach `generative_push`, in increasingly
strong language:
- `scripts/dispatch.mjs`: "every other track's `generativeShare` is
  structurally 0 (`pushAppliedFor` always returns 1 for them)"
- `policy.yml` (`meta.weight`): "meta's `generativeShare` is structurally 0"
- `policy.yml` (`generative_push`): "Only `author` and `build` can ever earn
  this... neither can file the item this push rewards"

All three are true of the *filing* path — `check-docket.mjs` does reject a
`meta`/`worth-a-visit` item, verified below — but `dispatch.mjs`'s
`generativeShare`/`closedGenerativeCount` read `docket/open/` and
`docket/done/` directly, with no dependency on `check-docket.mjs` at read
time. "Structurally 0" and "always returns 1" describe dispatch.mjs's own
code as if it enforced this; it doesn't — a different script does, at a
different time.

I proved this is reachable, not just theoretical, two ways.

**1. Direct probe.** I hand-wrote a `track: meta`, `serves: worth-a-visit`
item straight into `docket/open/` (bypassing `check-docket.mjs` entirely,
simulating any route that lands an item without going through it) and ran
the real `dispatch.mjs`:

```
meta       22/14 = 1.57  ->  weight 8.57 (x1.71 of 5; push share 0.05 -> applied x1.09)
```

`generativeShare` was `0.05`, not `0`; `pushAppliedFor("meta")` returned
`1.09`, not `1`. Deleted the file immediately; re-ran and confirmed the
table returns to `push share 0.00 -> applied x1.00`. "Always" is false — I
have a counter-example.

**2. This is not a contrived bypass — this repository has already found and
documented exactly this hole, independent of this round.**
`docket/open/2026-08-11-branch-protection-does-not-require-review.md` (open,
`blocked-on: maintainer`, three rounds of independently re-verified
evidence — 08-11, 08-13/round-90, 08-17) establishes: `enforce_admins` is
`false` on `main`, and the account the loop pushes and merges as
(`addicted2ai`) can merge past a **red required check** — demonstrated with
real PRs (#16, #25, #27, all merged with 0 reviews, #25/#27 merged with a
failing required check). The item's own words: "A required status check is
only as strong as the account that merges; here that account is the admin
the check does not bind." `check-docket.mjs` runs as the "Check the docket"
step inside the `build-and-audit` job
(`.github/workflows/pr-checks.yml:194-195`), which is one of the three
required contexts — the same mechanism the docket item proves doesn't bind
the loop's own account. I re-read the live setting myself rather than trust
either the docket item's cached readout or the round's comment:

```
$ gh api repos/addicted2ai/AddictedtoAI/branches/main/protection --jq \
  '{admins:.enforce_admins.enabled, required:[.required_status_checks.contexts[]], count:.required_pull_request_reviews.required_approving_review_count}'
{"admins":false,"count":0,"required":["build-and-audit","human-owned-paths","review-artifact"]}
```

Matches the docket item's last readout exactly, today. So the specific chain
this round's comments assert is unconditional — "meta cannot file it" →
"generativeShare is structurally 0" — has a documented, currently open,
maintainer-blocked gap in its first link, in this exact repository, verified
against the live API in this review. This is squarely the class of thing the
brief that first sent me here warned about: a check that "reads SCOPES from
the branch it is judging" or otherwise assumes a merge cannot happen past it
has already bitten this project (round 78, PR #25, PR #27) — and it applies
here too, since `enforce_admins` is one repository-wide boolean, not a
per-job setting.

**Why this matters at this round's own stated bar, not a generic nitpick.**
This round's own commit message frames the fix as closing a hole review
found, and the task that sent me back explicitly asked: "is there any path
by which a meta round benefits from `generative_push`?" and "a comment that
is merely less wrong than before is still wrong." I found a path, and the
comment is not precisely true. The magnitude is much smaller than the
original finding — this requires the already-known admin-merge gap, not the
ordinary sanctioned filing process the first version left open — but it is
real, demonstrated twice over, and it is exactly the question I was asked to
answer.

**What I'd change, and it's small.** Soften "structurally" / "always" /
"cannot ever" in the three comments to name the actual guarantee:
`check-docket.mjs` rejects this at file-validation time, which is normally
sufficient because it is a required check, but this repository has an open,
documented gap (`docket/open/2026-08-11-branch-protection-does-not-require-review.md`)
where the account that runs the loop can merge past a red required check —
so the guarantee is "as strong as that check's enforcement," not
"structural." `policy.yml`'s own header already states the standard this
falls short of: "anything that becomes load-bearing should get a parser and
a check that can fail rather than staying a number a prompt is trusted to
keep." A cheap alternative that would make the claim literally true instead
of just better-worded: have `generativeShare`/`closedGenerativeCount`
themselves filter to `VISITOR_FACING`-eligible tracks, so the guarantee lives
in the code the comment is describing rather than in a second file's
gate.
