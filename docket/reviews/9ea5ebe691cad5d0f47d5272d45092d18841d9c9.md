## Blocking finding 1: the round fails `node scripts/round.mjs check`

The changelog's Guardrails line points at `node scripts/round.mjs check` as the
verification path ("The rendered-page check runs under `node scripts/round.mjs
check`, which also runs ... the route checks on port 3000"). Running it on the
reviewed branch fails:

```
$ node scripts/round.mjs check
=== Static checks ===
  ok    npm run lint
  ok    docket valid
  ok    track scope for loop/maintain/correct-blog-required-checks-and-one-limit-count
=== Build and serve ===
  ok    npm run build
=== Route checks ===
  FAIL  route checks failed
FAIL  /blog: mapped to round 154 (author), but its files were last touched by
      "loop/maintain: correct the blog's required-checks claim and re-sweep the
      one-limit count" (maintain) — update PRODUCING_ROUNDS
=== 1 problem(s) ===
```

Isolated: `node scripts/check-ai-disclosure.mjs` exits 1 with the same /blog line.

The cause: this round edited `app/blog/page.js`, which `app/lib/route-files.js`
line 23 lists as a source file of `/blog`. `scripts/check-ai-disclosure.mjs` judges
each route's `PRODUCING_ROUNDS` entry against the track of the newest content
commit touching the route's files. On origin/main the newest /blog commit was round
154 (author, posts.js), so `/blog: 154` held. This round makes the newest content
commit a maintain commit, so `PRODUCING_ROUNDS["/blog"]` (`app/lib/page-origins.js`
line 240) is stale and the check fails. The same check runs in CI via
`bash scripts/check-routes.sh` (`pr-checks.yml` line 262), so CI rejects this PR as
shipped. `app/lib/page-origins.js` is inside maintain's scope ("as build": `app/`),
so the round could have updated the map and did not. Fix: move `/blog` to this
round (160, maintain) and re-run the gate.

## Blocking finding 2: the changelog parenthetical misdescribes the diff

The entry says: "the branch endpoint carries no `enforce_admins` field; the earlier
'is false' claim in the same paragraph is a separate, older sentence and was left
as written." The claim "was left as written" is falsified by the diff:

- `git show origin/main:app/blog/page.js` (corrected passage): "...the required
  checks are `build-and-audit` and `human-owned-paths`, and `enforce_admins` is
  false."
- HEAD's same passage: "...the contexts carry `enforcement_level: non_admins`..."
  — the literal "and `enforce_admins` is false" was removed and replaced, not left
  as written.

The only literal "enforce_admins is false" sentence still on the page (line 168,
"Read from the GitHub API on 11 August 2026: `required_approving_review_count` is 0
and `enforce_admins` is false") sits in a different paragraph (the "That correction
did not go far enough" one), not "the same paragraph" as the corrected passage. So
under either referent the parenthetical is wrong: the corrected passage's "is
false" sentence was removed, and the surviving one is elsewhere. This is a
description of what the edit was meant to do rather than what the diff does — the
defect class this project rejects rounds for. The entry is permanent once merged.
