## Task 1: try to hide a fact again — yes, and it doesn't need a malformed heading at all

The new gate is `declaredTotal !== independentHits.length` in
`scripts/check-frame.mjs` — a **count** comparison. `independentHits` is
still produced by the same column-0-anchored `looksLikeNumberedHeading` scan
from the third fix. Comparing a declared number against a count, rather than
against a specific *set* of recognised fact IDs, means the guarantee holds
only while nothing both removes a fact and adds an unrelated
heading-shaped line elsewhere in the same document — and nothing here
checks for that.

No column-0 anchoring, no shape gap, no scan weakness of any kind is
exploited here — every heading in this fixture is perfectly well-formed by
every measure the tool has. The gap is structural: nothing in
`check-frame.mjs` checks that the recognised fact IDs form the sequence
`1..declaredTotal` with no gaps and no duplicates. `duplicateIds` catches
two headings claiming the *same* number; nothing catches a number quietly
skipped while a different one takes its place. A count can be exactly right
while the wrong facts are the ones being counted.

This is worth weighing against realistic editing, not just adversarial
construction: this project's own practice (seen across passes 1-2 of this
review, where facts were split and renumbered 14→14/15/16/17/18) is to
renumber on edits. A renumbering slip — skip a number, reuse one, or leave
an old number pointing at replaced content while the total count happens to
stay put — is an easy accident under the kind of time pressure these rounds
already operate under, not only a hypothetical attack.

## Task 2: the new bound — is it honestly stated, or a quieter version of the old problem?

The header comment states the bound as: "it holds exactly as long as the
declared number in FRAME.md is kept in sync with the facts actually there,
which is a single, human-auditable edit rather than a syntax-recognition
problem." `FRAME.md`'s own new sentence says the same thing: "Bump this
number in the same edit that adds or removes a fact below."

Given task 1: **this is not the actual bound.** "Keep the number in sync"
is necessary but not sufficient — attempt 3 above has the number in perfect
sync (3 facts declared, 3 headings physically present) and still lets one
be substituted without detection. The real requirement is stronger than a
single-number edit: whoever edits `FRAME.md` must also preserve the
*specific numbered sequence* — no fact quietly disappears while an
unrelated one takes its place under a different number, and nothing
mechanical checks that property. That is a subtler, less auditable
invariant than "one number, updated correctly" — it requires noticing an
*absence* of a specific identity, which a glance at a rendered count does
not surface (a rendered indented heading still looks like a normal
heading; a renumbered fact still looks like a complete, sequential list on
casual read).

So: yes, one unbounded problem (recognising every malformed heading shape)
has been traded for a bounded one (a count comparison) — but the header's
characterisation of what makes that bound safe is incomplete. It is not
quite "a stale declaration silently blesses a wrong count" in the sense of
the number itself going out of date; it is narrower and easier to miss than
that — a *correctly updated* declaration can still bless a wrong set of
facts, because the mechanism verifies a total, not a membership.

Worth noting for proportion, not as part of this finding: the two precedents
the round cites for this pattern — `LEGACY_ROUNDS_WITHOUT_ORIGIN = 47` and
the `/charter` rule-count check (`FRAME.md` fact 14, reviewed and accepted
in an earlier pass) — compare counts derived from two independent parses of
the same content, not a hand-declared number against a scan, and neither
validates that the counted items form a specific expected sequence either.
The comparison to "patterns already in this codebase" is accurate as a
description of the mechanism's shape, but those precedents share this same
soft spot rather than demonstrating it is safe in practice; I did not
re-open those already-reviewed facts, but flag the parallel since it bears
on how much confidence "this mirrors an established pattern" should buy.

## Task 3: is the header comment now exactly true?

Not quite, for the same reason as task 2. The literal mechanical sentence —
"That comparison does not care why a fact went unrecognised; any mismatch,
for any reason, known or not yet discovered, fails the build" — is true as
written about what the *count* comparison does. But the comment introduces
that comparison as "the actual completeness guarantee," which is the
overclaim: a reader relying on this as "if `check-frame.mjs` passes, no fact
went missing" would be wrong, per task 1's attempt 3. The count agreeing is
not the same as completeness; it is one necessary condition for it, silently
promoted to sufficient.

To the round's credit, this version is honestly framed in every other
respect — it names all three prior overclaims explicitly by number, states
plainly what each did and did not fix, and does not repeat the absolute
language ("never silently dropped") that made the earlier versions flatly
false. The overclaim this time is narrower and one level more abstract: not
"the scans catch everything" but "the number-comparison catches everything
the scans could miss," which is closer to true but still not exact.

## Task 4: item 11's legibility and its claim to a stopping point

Read `CHANGELOG.md`'s new item 11 as a reader who was not here. It is
legible: it states the finding, reproduces it with real numbers, explains
the judgement in a self-contained way (an ATX heading is finite grammar, but
learning that grammar by incremental counterexample does not converge in
practice, and even a complete recogniser would not cover "no heading markup
at all" — round 167's shape, named directly), describes the fix and its
bound, and closes with an explicit "progression" paragraph naming what each
of the three prior fixes did and did not close.

It does **not** claim a final stopping point it hasn't earned: "Whether that
is the last fix this class needs is not claimed — what changed is that the
promise in the header comment now matches what the mechanism can actually
prove." That sentence is careful about *finality*. It is less careful about
*completeness of characterisation* — "matches what the mechanism can
actually prove" is the same claim task 3 finds not quite true, so the entry
inherits the header comment's overclaim rather than independently checking
it. Legible and appropriately humble about "is this the last fix," not
independently audited against what the new mechanism actually delivers.
