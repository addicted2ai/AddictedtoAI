## 1. The Alibaba tiered-floor disagreement — re-derived from scratch

The round's brief told it to prefer the *longer* floor (90 days, mainline)
as the conservative default when a vendor's promise is tiered and
`RETIREMENT_DATES` cannot say which tier a row belongs to. The round used
the *shorter* number (30 days, snapshot) instead, arguing the brief had the
safety direction backwards.

I worked this through myself before reading the round's own justification,
using the brief's own hypothetical (mainline row, 90-day true promise, 50
days remaining) plus the boundary cases that actually decide it:

- **Remaining < 30** (below both floors): any threshold calls this
  `inside-window`. Correct under either tier — genuinely violates both a
  30-day and a 90-day promise. No ambiguity here regardless of which
  blanket number is used.
- **Remaining ≥ 90** (above both floors): any threshold calls this `held`.
  Correct under either tier. Also no ambiguity.
- **30 ≤ remaining < 90 — the only band that matters** (the brief's
  50-day example lands here): a blanket-90 threshold calls this
  `inside-window`; a blanket-30 threshold calls this `held`.
  - If the true row is **mainline** (needs 90): blanket-90 is right,
    blanket-30 is wrong — a false `held`, i.e. a missed real violation.
  - If the true row is **snapshot** (needs only 30): blanket-30 is right,
    blanket-90 is wrong — a false `inside-window`, i.e. **a false public
    accusation that a fully-compliant vendor broke a promise it never
    made.**

So the two choices are not symmetric. Blanket-30 can never manufacture a
false accusation against either tier — its only failure mode in this band
is silently mislabeling a real mainline violation as `held`. Blanket-90 can
manufacture a false accusation against a compliant snapshot model. Given
that this entire feature's named failure mode (per its own file header and
per this review's brief) is exactly "a false, public, disputable statement
that a named company is not honouring its own promise," the asymmetry
matters: **one wrong call is silence dressed as compliance; the other is a
false accusation.** For a publication making claims about real companies by
name, the false accusation is the worse failure by a wide margin — it is
the closer analogue to a factual error a news outlet would have to run a
correction for, where a missed/under-reported violation is not something
anyone would need retracted.

One nuance the round's own comments understate: calling the mainline case
`held` is not neutral silence, it is an **affirmative, incorrect,
exculpatory claim** ("promise currently held"). That is still the safer
wrong claim to publish than a false accusation, but it is a claim, not an
absence of one — worth naming explicitly since a future reader of this
code might reach for "it just doesn't flag it" as the description, which
undersells what's actually being asserted on the page in that band.

**My independent conclusion: the round's departure from its brief is
correct, for the reason it gives.** This is not "well-argued therefore
accepted" — I derived the same asymmetry from the boundary cases before
reading the round's write-up, and it holds. I would have made the same
call. The choice is presently inert (confirmed below: zero Alibaba rows
exist in `RETIREMENT_DATES` today), so nothing on the live site depends on
this yet, but the reasoning is sound for when a row appears.

## 3. Amazon Bedrock and Mistral — read the actual sentences myself

**Bedrock** (`app/lib/retirement-commitments.js`): the quoted `sentence` is
"Once a model launches on Amazon Bedrock, it will remain on Amazon Bedrock
for at least 12 months before the EOL date" — a minimum lifetime from
launch, not a notice-before-shutdown floor; treating it as one would compare
the wrong quantity. `sentenceMore` says "A model will be in the Legacy

*duration*, and at no point says entering Legacy state notifies anyone. The
round's reading (neither number is confidently a notice floor) matches what
the text actually says; I did not find a notice floor being missed here.

**Mistral**: `sentenceMore` explicitly reads "...commits to 6 months'
notice for **General Availability models**" — scoped, with no second
number for anything else and no `RETIREMENT_DATES` tag to identify GA rows.
Confirmed as described; unlike Alibaba there is genuinely no fallback
number to default to, so `null` here (rather than a shorter-number
compromise) is the only defensible choice.
