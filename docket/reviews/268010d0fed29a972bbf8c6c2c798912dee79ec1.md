## B2 — resolved, and the boundary is exact

The sandbox suite reaches only the `baseRounds === null` fallback, because none
of its temp directories is a git repository. So I built real git fixtures with an
actual `refs/remotes/origin/main` and exercised the branch that runs in CI:

| fixture | scope computed | result |
|---|---|---|
| bad entry at round **186 == baseRounds** | 1 added above 186 | **PASS**, reported by name |
| bad entry at round **187 == baseRounds+1** | 1 added above 186 | **RED** |
| bad entry merged deeper (round 185) | 1 added above 186 | **PASS**, reported |
| branch adds nothing (branch == main) | 0 added above 186 | **PASS** |
| branch *behind* main (main 187, branch 186) | 0 added above 187 | **PASS** |

No off-by-one: `number > baseRounds` puts the entry at exactly `baseRounds` on the
merged side and `baseRounds + 1` on the assertable side. It cannot drift, because
both sides are counted by the same `sections()` function and the append-only
record means a merged entry's number never moves. Every narrowing case fails
*open* — the scope can only shrink, never wrongly widen onto merged history.

The `merged-entry-not-failed-on` control is **not vacuous.** It plants
`Agent: unknown` on the *older* of two enforced-era rounds and requires
`/note {2}merged round \d+ .*carries Agent 'unknown'/` in the output, so it fails
if the checker either reds on the merged entry or silently ignores it. The
pre-era/era split now written into `syntheticChangelog` is what makes
`lastIndexOf` land on the intended entry; the round discloses that an earlier
version of this fixture mutated round 1 by accident and proved nothing, which is
exactly the failure mode a control like this invites.

Keeping composition at whole-window scope is right, and the stated distinction
holds: its remedy is to ship a `scout` or `maintain` round, which stays legal
forever, whereas rule 5 forecloses the per-entry remedy the moment an entry
merges.

## The third defect — real, and the fix is sufficient

`CHANGELOG.md` is **1,324,467 bytes**, so it genuinely exceeds `execFileSync`'s
1 MB default `maxBuffer`. The bug was real, not theoretical, and the symptom was
the worst kind: the check announced `origin/main is not in this checkout` on a
tree where it plainly was, and silently narrowed its own scope for a fabricated
reason. A check that reports the wrong reason for standing down is precisely this
file's subject matter, and finding it in its own first run is the kind of thing
worth the entry space it got.

The new limit is `256 * 1024 * 1024` — about **193x** the current file. The
changelog would have to double roughly seven and a half times to reach it, and
`execFileSync` throws on overflow rather than truncating, so the failure mode at
that distant point is a loud `fail()`, not a silent under-count. Sufficient.

The two error paths are **genuinely distinguished, not pattern-matched on a
message string**: existence is tested by a separate
`git rev-parse --verify --quiet origin/main^{commit}` with `stdio: "ignore"`
(so no buffer is involved), and only then is `git show` run for content. A throw
from the first returns `null` and narrows with an announcement; a throw from the
second calls `fail()`. That is the correct structure — the classification comes
from *which command failed*, which cannot be confused by an unfamiliar error text.
