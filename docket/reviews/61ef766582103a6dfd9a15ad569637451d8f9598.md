# Review — PR #46: review-artifact ancestry from the filename

Commit: 61ef766582103a6dfd9a15ad569637451d8f9598
Verdict: request-changes
Reviewer: opencode (deepseek-v4-flash)
Round: 95

Reviewed the full diff `origin/main...HEAD` (61ef766) and ran every experiment
below from the repository root. The core change — deciding an artifact's
ancestry from its filename before reading the file — is sound as measured: I
could not reach "informational" for a live commit by any route, and no hostile
name manufactures a covering approve. The gate's three invariants hold and
the regression tests demonstrably fail when the implementation is broken.
Two defects are blocking: the branch corrupts round 94's changelog entry with
a duplicated line that will render on `/log`, and the entry's own rule-11 and
Guardrails claims contain measurements I could not reproduce.

## The safety property (item 1)

A malformed artifact naming a commit that IS in this branch's history must
still fail. Constructed in a scratch repo (live work commit, review file
named after it, fields `Reviewer`/`Round` absent):

    node scripts/check-review-artifact.mjs <base>
      FAIL  docket/reviews/52d5e17e...md: missing field(s) Reviewer, Round — a review that cannot be parsed is not a review
      FAIL  no review artifact covers the merged tree
    2 problem(s) — exit 1

Informational is unreachable for a live commit: the only route to the note
is `git merge-base --is-ancestor <filename> HEAD` answering no, and for a
commit in history git answers yes, forcing the full field checks. No other
route reaches the note (regex failure and unreadable files are FAILs).
This property held in every construction I tried, including the verbatim
scenario above.

## The filename decision (item 2)

Scratch repos with hostile names, all run through the checker (full output
in each case):

- **Absent-sha filename, body claims a LIVE commit with approve** (`Commit:
  <live>`, `Verdict: approve`, all fields, prose): the body is never read —
  note "Commit ... is not in this branch's history", counts for nothing, gate
  fails. It can only fail to be a covering approve, never manufacture one.
- **Ancestor filename, `Commit:` field names a different commit**: caught —
  `FAIL ... Commit '2222...' does not match the filename it is stored under`.
- **Filename not a sha** (`not-a-sha.md`): `FAIL ... filename is not a full
  40-character SHA`. **Truncated (39 hex)**: same FAIL. No crash.
- **Valid 40-hex this repository does not have** (`ffff...`, `aaaa...`):
  `note`, informational, no crash. **Filename = sha of a blob object**:
  `note`, informational, no crash.
- **Manufacture attempt**: an approve named for an ancestor whose tree
  diverged is a note ("does not cover the merged tree (N file(s) changed
  after it)") — the tree-diff condition, untouched, is what stops
  manufacture, and it is computed by git from real commits, not from file
  contents.

Benign answers where the round's claim is at stake: the note path is the
round's own widening and I could not find a second way into it. The one
behavioral change beyond the disclosed one is that a file whose body
contradicts its absent-sha filename (Commit field naming a live commit) is
now a note where the old code FAILed the mismatch — disclosed in block 3,
and it cannot cover either way.

## The three invariants (item 3)

- **Covering approve passes**: exit 0, `ok ... covers the merged tree
  (f2e0d63c185a), Verdict: approve`, `review artifact verified: 1 covering
  review(s)`. Also holds with an absent-commit malformed note beside the
  covering approve (the shape of a real delegated branch): exit 0.
- **Absent-commit-only branch fails for the right reason**: exit 1 with
  exactly `no review artifact covers the merged tree`, the artifact reported
  as a note — never as a failure. The `FAIL` count is 1 (the no-covering
  problem only).
- **Covering reject / request-changes fails, stale approve does not
  override**: exit 1, `FAIL ... Verdict is 'reject'` / `'request-changes',
  not 'approve'` even with an approve artifact named for an absent commit
  sitting beside it (that one is a note).

## Blocking concern — round 94's entry is corrupted

`origin/main`'s changelog contains the line "Round 94 (build) fixes the wall
every round was about to hit: `/log`" once. This branch contains it twice:
commit 17d5de0 (the record-finishing commit) inserted a duplicate
`### 2026-08-13` section header and a duplicate of that first line directly
into round 94's entry. I diffed round 94's entry between origin/main and
HEAD: the only difference is that one duplicated line. The build-log parser
absorbs the duplication (one entry, anchor round-pr-45), but the line lands
in `entry.intro`, which `app/log/LogEntry.js` renders on `/log` — round
94's published intro will show the sentence twice. This is a modification
of a past changelog entry (rule 5 territory) introduced by the very round
whose entry devotes block 4 to record integrity. Fix before merge: delete
the duplicated line so round 94's entry exactly matches main's text.

## Concern — the pre-fix measurement claim does not reproduce

The Guardrails section states that `node scripts/check-review-artifact.mjs
470742f` with current main "reproduces the live blocker before the fix:
FAIL ... missing field(s) Reviewer, Round and 2 problem(s)". With the
pre-fix checker on main's tree (f327f96) the same command measures
**7 problem(s)**: all six artifacts fail (five as "not an ancestor", the
malformed one as missing fields) plus the no-covering failure. The blocker
is real — the number reported is not the number the documented command
produces.

## Concern — "the one check whose reach narrows" is not true

Block 3: "The one check whose reach narrows is Commit-vs-filename
mismatch". Measured against the diff: the missing-fields check, the prose
check and the readability check narrow identically — all four now run only
for artifacts whose filename is an ancestor of the head. The missing-fields
narrowing is the round's own headline case (2c497c4). The not-widened list
beside it is complete and true; this sentence understates the widening and
should be corrected so the compliance argument says what the code does.
