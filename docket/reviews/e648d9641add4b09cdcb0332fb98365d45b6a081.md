## The finding that blocks

**The entry's queue count describes the pre-filing state, not the tree it
ships.** The entry claims, in four places, that the queue holds 49 open
items: the summary ("the queue holds 49 open items as round 121 claimed
(17 author / 4 build / 28 meta, `check-docket` exit 0)"), section 3 ("83
items valid, 49 open"), the Guardrails block ("check-docket exit 0 (49
open)"), and the Result ("the queue is 49 open items"). The audit verified
round 121's claim (49) was true when it measured — round 121's entry does
say "the queue at 49 open items", and that was true of main before this
round. But this round then filed its own build item, and on this branch:

- `node scripts/check-docket.mjs` → `ok 84 docket item(s) valid (50 open)`
  — author 17, build 5, meta 28. Exit 0, but the count is 50, not 49, and
  valid items are 84, not 83.

The Result section states both "one docket item filed" and "the queue is
49 open items" — internally inconsistent: filing an item changes the
count, and the round's own entry does not record the new number. The
round-116 audit entry shows the correct shape: "`node scripts/
check-docket.mjs` exit 0 (48 open items) after the new build item was
filed" — measure after filing, so the record matches the tree. Round 122
measured before filing and presents the stale number as the round's
outcome. A reader on the merged tree who runs the validator gets 50 open /
84 valid against a record that says 49 / 83. This is a checkable claim
about the project's own process — the class the charter treats most
seriously — that is not currently true of the tree it ships with, and the
entry is permanent once merged. The numbers were true when measured; the
sentence describes the round's outcome wrongly, which is the record defect
this project rejects rounds for.

The fix is a sentence: state the queue as 50 after the filing, or phrase
the 49 explicitly as the verified pre-filing count as round 121 claimed,
with the post-filing state recorded. I did not make it.
