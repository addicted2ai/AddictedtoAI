## Blocking

### B1. The `Agent:` resolver rejects the values this repository's own live instructions tell a round to write

`scripts/check-changelog-provenance.mjs` runs inside `scripts/check-routes.sh`
(`.github/workflows/pr-checks.yml:401`), which is the `build-and-audit` required
status check. From round 185 forward it fails the build unless every entry's
`Agent:` — the text before the first parenthetical — is a key or a `model:`
value in `scripts/runners.yml`.

Four *current, live* instruction paths in this repository produce values that do
not resolve. I built sandboxes from the real tree, set only the newest entry's
`Agent:` bullet, and ran the checker:

| `Agent:` value | result | where the value comes from |
|---|---|---|
| `unknown` | **RED** | `scripts/round.mjs:300` and `scripts/build-prompt.mjs:39` — `arg("agent", "unknown")`, the default when `round.mjs start` is run without `--agent` |
| `claude-code` | **RED** | `prompts/shared/every-run.md:80` example, and `.claude/skills/local-loop/SKILL.md:58` ("including `Origin`, `Track` and `Agent: claude-code`") |
| `claude-code-action` | **RED** | `prompts/shared/every-run.md:80` example |
| `opencode (deepseek-v4-flash)` | **RED** | 70 entries in `CHANGELOG.md`; the shape produced by `default_runner: opencode-go-deepseek-max` |
| `codex` | pass | `every-run.md:80`, `AGENTS.md:72` |
| `claude-opus-5 (Claude Code subagent)` | pass | what round 185 itself wrote |

`scripts/build-prompt.mjs:90` renders `  - Agent: ${agent}` under the literal
heading "Record these in your changelog entry:". So a round started with plain
`node scripts/round.mjs start` is *instructed by its own generated prompt* to
write `Agent: unknown`, and that round's merge is then blocked by a required
check. This is not a hypothetical future model — it is the default path today.

Two things make this worse than a one-round annoyance:

1. **The resolver's stated rationale does not match the record.** The checker's
   header says "the record's own convention is to publish the MODEL", citing
   `claude-opus-5 (orchestrating model)` and `claude-sonnet-5 (Claude Code
   subagent)`. That describes 25 entries. The dominant convention — 70 entries,
   `opencode (deepseek-v4-flash)` — puts the **harness** before the parenthetical
   and the **model inside** it, which is exactly inverted. The resolver was built
   against the Claude-era minority and reads the majority convention as a defect.
   The entry is honest that historical values "would not resolve"; neither the
   entry nor the checker notices that the *forward-facing* instructions still
   emit them.

2. **Rule 5 turns a single bad merge into a permanent red.** The check evaluates
   every entry numbered >= 185 on every run, and CHARTER.md rule 5 forbids
   rewriting a merged entry ("No past entry is rewritten, deleted, softened, or
   quietly amended"). If one entry with `Agent: unknown` lands on `main` — which
   `enforce_admins: false` permits, and which this round's own entry documents
   the loop can do — every subsequent pull request in the repository is red, and
   the obvious remedy is the one thing rule 5 prohibits. The escapes are
   registering a fake runner, bumping `ENFORCED_FROM`, or bypassing again. Note
   the contrast with the precedent block 2 says it is following: `Origin:` is
   enforced as a *pinned count* of legacy entries, which degrades gracefully.
   This is a per-entry property with no valve.

Both `prompts/` and `scripts/` are already in `meta`'s `SCOPES`
(`scripts/check-track-scope.mjs`), so this is in scope for this round and rule 11
is not implicated — no permission is being granted and spent.

**To clear this,** any of: change the `--agent` default from `unknown` to a
registered runner (or make it required and validate it at `start`, which is
strictly better — it moves the failure to launch time where it is cheap);
replace `every-run.md:80`'s examples with resolvable ones and say the value must
resolve in `scripts/runners.yml`; fix `.claude/skills/local-loop/SKILL.md:58`;
and decide explicitly whether `opencode (deepseek-v4-flash)` should resolve
(either accept a harness-qualified form, or register `opencode` as an alias, or
document that the model must lead). A test case pinning "the values our own
instructions produce all resolve" would keep it fixed.

## Non-blocking

- **N1. The cross-check is the one assertion never proved able to fail.**
  `crossCheck()` — asserting this script's section count, round numbers and
  `Track:` values equal `app/lib/build-log.js`'s — is the round's sole mitigation
  for deliberately shipping a second reader of `CHANGELOG.md`. It has no planted
  defect, and it cannot get one under the current harness: the checker skips it
  whenever `root !== process.cwd()` (lines 165-171), and every one of the 14
  sandbox runs uses a sandbox root. I confirmed the skip fires in all of them. It
  does run and pass on the real tree (I saw its `ok` line over all 185 rounds),
  and the entry credibly reports it went red once during development on a missing
  `Hypothesis:`. But in a round whose own test header quotes "prove it can fail
  before trusting it", the one unproved assertion being the one guarding the
  known-risky design choice is worth fixing — e.g. by letting the sandbox export
  a `CHANGELOG.md` path the module can be pointed at.

- **N2. `Dispatch:` does not render on `/log`, and nothing is filed for it.** The
  entry names the gap in prose ("work for a track that owns `app/`") but files
  nothing. I grepped `docket/` — no open item covers it; the filed item
  (`2026-08-24-label-every-guardrail-launch-or-merge-time.md`) is about
  launch-time vs merge-time labelling and is well-formed and correctly scoped to
  `build`. So the record now has a CI-enforced field the published log does not
  show, with no queued work to close it.

- **N3. `dispatchWindow()`'s source-text parse is tighter than it needs to be.**
  `/^const WINDOW = (\d+);$/m` fails the whole build — not warns — if
  `scripts/dispatch.mjs:121` ever becomes `const WINDOW = 20; // rounds`,
  `const WINDOW=20;`, or `let WINDOW`. A cosmetic reformat by an unrelated round
  therefore blocks every merge. I judge this acceptable rather than blocking: the
  message is explicit, `composition-window-unreadable` proves it goes red, and
  `scripts/` is in four tracks' scope so the remedy is available in the same
  round. But `/^\s*const WINDOW\s*=\s*(\d+)\s*;/m` removes the vector for free
  and keeps the loud failure for a genuine removal.

- **N4. The remedy the `Agent:` error prescribes is out of scope for two tracks.**
  The failure message says "register it", meaning edit `scripts/runners.yml`.
  `scout`'s scope is `["docket/", "CHANGELOG.md"]` and `author`'s is `["app/",
  "public/", "docket/", "CHANGELOG.md"]` — neither can write `scripts/`. A scout
  or author round on an unregistered model needs a second round to unblock it.
  Worth flagging because `scout` is precisely the track the composition assertion
  exists to bring back into rotation.

- **N5. The checker's header table is a pre-shipping snapshot and no longer
  matches its own output.** Lines 22-28 record author 2 / meta 9 over rounds
  165..184. The check now prints author 1 / meta 10 over rounds 166..185, because
  this round's own entry shifted the window. Both are correct for their stated
  moment and the changelog entry names 165..184 explicitly, so nothing is false —
  but a reader comparing the comment to the output will see a mismatch.

- **N6. The test tally under-reports if a control fails.**
  `test-changelog-provenance.mjs` accumulates control failures and case failures
  into one `failures` counter, then prints
  `${CASES.length - failures}/${CASES.length}` planted defects caught. A broken
  control would silently subtract from the planted-defect score. Exit code is
  unaffected.

- **N7. Two cases do not discriminate between each other.** `enforced-era-empty`
  expects `/nothing to assert, which must not read as a pass/` and
  `heavy-tracks-vanish` expects `/has nothing to assert, which must not read as a
  pass/`. Both messages match both regexes, so neither case would notice if it
  had triggered the other's failure. Each defect is genuinely caught; the
  "recognisable about that specific defect" property claimed in the test header
  is weaker here than elsewhere in the file.

- **N8. "becomes a build failure at round 204" carries an unstated assumption.**
  Arming is `window[WINDOW-1].number >= ENFORCED_FROM` over *tracked* rounds. 49
  of 185 historical entries carry no `- Track:`, and nothing in this check
  requires one. If any round from 185 on omits `Track:`, arming slips past 204.
  The arithmetic is otherwise exactly right — `syntheticTree`'s default
  `ENFORCED_FROM + 19 = 204` and the healthy control confirm the armed path.

- **N9. `ENFORCED_FROM = 185` is stable, with one caveat.** I verified entries are
  prepended and `number = sections.length - index`, so appending never moves a
  past number, and 185 is this round. The constant silently mis-points only if a
  past entry is ever *deleted* — which rule 5 forbids and nothing here detects
  (the cross-check would not catch it; both readers would shift together). Note
  only.

- **N10. `Origin: maintainer`.** Per my brief I record a view in one sentence and
  do not make it blocking: `delegated` looks like the better fit given the round
  was reviewed and merged through the normal chain, but since round 179 removed
  the Origin-based review exemption the field has no mechanical consequence, and
  the round's reasoning is stated openly rather than hidden, so it is not worth
  more budget than this sentence.

## On the design choice the round asks to be judged

The deferral is **principled, and I would not ask for it to change.** Arming the
composition assertion from round 185 means it does nothing enforcing for 19
rounds — that much is true and the entry says so in those words. But it is not
19 rounds of silence: it prints the true zero counts under a `WARN` on every run,
so the drought is visible continuously. The stated reason for not picking a
larger N — that choosing a threshold to make today's verdict come out green is
reverse-engineering the threshold from the desired verdict — holds up, and the
116-position sweep is the right evidence for it: the threshold fires on the
current drought and on one earlier one, and stays quiet across 62 consecutive
healthy positions. That is a check calibrated against the record rather than
against the present moment.

The alternative my brief raised — arm once the drought is *fixable* — is worse on
its own terms. It would arm essentially immediately, and the round would ship a
red required check that no single round could turn green, which is the outcome
the entry correctly refuses. The one thing I would note is that the deferral is
load-bearing on the loop continuing to ship at roughly five rounds a day; if the
cadence drops, "a few days" becomes considerably longer and nothing re-examines
the estimate.

## Summary

The engineering is careful and the evidence is unusually solid — every published
number reproduced on first attempt, the test suite plants real defects, and the
honest limits are stated in three places rather than one. The blocking finding is
narrow and cheap to fix, but it is squarely the failure mode this review was
pointed at: a new assertion inside a required status check that will red-build a
round for following the repository's own written instructions, with rule 5
standing in the way of the obvious cleanup afterwards. Fix the instruction
sources (and preferably validate `--agent` at `start`), and this should go in.
