## 2. RFC 5545 traps — checked against the actual generated feed

Generated the real feed via `buildRetirementIcsFeed(RETIREMENT_DATES)` (77
rows, confirmed by direct import: `RETIREMENT_DATES.length === 77`) and
inspected the raw bytes, not the transform code in isolation.

- **Comma escaping (the named test case).** Row `dall-e-2`/`dall-e-3`,
  replacement `"gpt-image-2, gpt-image-1, or gpt-image-1-mini"`. Actual
  generated line: `Replacement: gpt-image-2\, gpt-image-1\, or
  gpt-image-1-mini.` — both commas escaped as `\,`. Round-tripped through
  `ical.js`'s real parser (`ICAL.parse` + `getFirstPropertyValue`): comes back
  as the literal three-item string with plain commas, i.e. TEXT-unescaping
  restores exactly the original meaning rather than splitting on the commas.
  Correct.
- **Semicolon escaping.** Found a second live case the brief didn't name: the
  Agent Builder row's note, `"ChatKit remains available; the page links a
  migration guide..."`. Generated line carries `\;`; `ical.js` decodes it back
  to a literal semicolon. Correct. No row contains a literal backslash, so
  that path is implemented correctly (`escapeText` replaces `\` before `;`/`,`
  to avoid double-escaping) but not exercised by real data.
- **75-octet line folding, VEVENT properties.** The longest DESCRIPTION
  (dall-e-2/3, escaped-and-prefixed length well over 75 octets) folds into
  multiple physical lines, each ≤75 octets, each continuation prefixed by
  exactly one space per RFC 5545 §3.1. One fold point lands mid-escape-
  sequence (between the `\` and `,` of an escaped comma) — verified this
  still reconstructs correctly on unfold, since folding/unfolding is a pure
  byte-level insert/remove of `CRLF+space` and doesn't care where it lands
  relative to TEXT-escaping semantics.
- **Calendar-header folding — a real gap, but outside the round's actual
  claim.** The VCALENDAR-level `X-WR-CALDESC` line is 154 octets on one
  physical line and is never passed through `contentLine()`/`foldLine()` —
  it's pushed as a raw string alongside `BEGIN:VCALENDAR`, `VERSION:2.0`,
  etc. This does exceed RFC 5545 §3.1's 75-octet line-length guidance in the
  literal generated output. Two things keep this from being a false claim
  rather than a gap: (a) §3.1's limit is a SHOULD, not a MUST, and I
  confirmed with `ical.js` — the same real parser this round added
  specifically to validate the feed — that it parses this line and returns
  the correct string despite the length; (b) the round's own CHANGELOG
  sentence ("folded and escaped per spec") is grammatically scoped to the
  VEVENT property list it names (UID, DTSTAMP, DTSTART/DTEND, SUMMARY/
  DESCRIPTION) — all of which *are* correctly folded — not to the calendar
  header. So this isn't a falsified claim, but it is a real, fixable
  inconsistency (the file's own `foldLine()` helper exists and isn't applied
  uniformly) that neither the round's manual check nor
  `check-model-retirement-ics.mjs` catches, since the health check never
  asserts folding on any line. Worth a follow-up; not blocking given it
  doesn't touch any VEVENT (the actual reminders) and round-trips correctly
  through the reference parser.
- **UID stability.** `buildUid` derives `${slugify(vendor)}-${slugify(what)}@addictedtoai.net`
  with no timestamp, counter-only tie-break for collisions (none currently
  occur — health check confirms all 77 UIDs unique). Built the feed twice in
  separate process runs: byte-identical output. The feed is stable across
  rebuilds as long as a row's vendor/what don't change, which is what a
  long-lived subscription needs.
- **DTSTAMP.** Present on every VEVENT, valid UTC DATE-TIME form
  (`20260814T000000Z`), sourced from each row's own `verified` date rather
  than the build clock — a disclosed, deliberate choice for byte-
  reproducibility. No SEQUENCE property is emitted (defaults to 0 per spec);
  fine for a PUBLISH-method feed most clients resync by UID+content on each
  fetch.
