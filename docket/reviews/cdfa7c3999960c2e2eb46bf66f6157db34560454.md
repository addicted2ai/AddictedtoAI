## 3. KNOWN_FAILURES — real finding

The brief calls this the highest-risk part of the diff and asks
specifically: does a *different* new failure on a known-failing route get
reported or swallowed, and can an entry outlive the bug it documents
without anyone noticing?

Read `main()`'s branching (`scripts/check-reflow.mjs:530-553`): a route in
`KNOWN_FAILURES` that still overflows always prints a `KNOWN` line with
the *current* `scrollWidth`/`clientWidth`/delta and is **never counted
toward `failures`**, regardless of magnitude or cause. The only thing
checked is the route name being a key in the object — not the specific
element, not the delta, not any signature of the originally-filed bug.

Confirmed live, using the same site-wide overflow probe from section 2
(so `/log` now overflows for a reason that has nothing to do with the
filed backtick/bold-span bug):

    KNOWN /log  scrollWidth 900 > clientWidth 320 (+580px at 320px) -- filed: docket/open/2026-08-22-log-note-nested-code-overflows-320px.md

The route's real, filed defect is +180px. This run shows +580px — a
completely different, much larger overflow, from an unrelated cause — and
the check still exits with `/log` uncounted, only `KNOWN`. If this had
been the *only* overflow present, the whole run would have exited 0.

So: **reported, yes** (the number is printed and would visibly differ from
+180px to anyone reading the full log) — **gated, no** (the exit code, the
only thing CI actually acts on, does not distinguish a route's filed
defect from any other defect that happens to land on the same route). The
brief's own framing was "that is the honest choice if and only if the
mechanism cannot silently absorb new failures" — it can, for the one
direction that matters (a new or worsened failure), though not for the
other (I also verified, by reading rather than reproducing, that the
opposite case — the filed bug getting fixed without the entry being
removed — is correctly caught: `scripts/check-reflow.mjs:545-550` prints
`FAIL ... still listed in KNOWN_FAILURES` and increments `failures`).

I want to be fair to the round here: it never claims the mechanism does
more than this. The changelog says only that `/log` is "still measured and
printed every run... not silently dropped" and that the check "fails
again on its own if `/log` stops overflowing without that entry being
removed" — both true and verified. It does not claim protection against a
different failure landing on the same route. But the brief's own
instruction is to flag anything real regardless of whether it was
overclaimed, and this is real and directly demonstrated.
