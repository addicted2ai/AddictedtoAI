## Finding 2 (real, from pass 1): check-frame.mjs's silent-drop bug — partially fixed, and I found the remaining gap

Re-ran my original four-fact fixture
(`test-frame-parsing.md`, unmodified, in my own scratchpad) against the real
`scripts/check-frame.mjs`, now using its new optional path argument:

```
$ node D:/AddictedtoAI/scripts/check-frame.mjs "<scratchpad>/test-frame-parsing.md"
test-frame-parsing.md check -- 4 candidate heading(s): 1 well-formed, 1 malformed heading(s), 2 malformed body

FAIL        17. 17: A fact whose heading uses a colon instead of a period -- malformed heading, does not match "## N. Title": "## 17: A fact whose heading uses a colon instead of a period"
FAIL        18. A fact with an empty fenced check block -- malformed (missing Status or, for verified, a check block)

verified    1. A normal fact with a real check

reconciled: 4 candidate heading(s) = 1 well-formed fact(s) + 1 malformed heading(s) + 2 malformed body
```

The originally-reported case (`## 17:` instead of `## 17.`) is genuinely
fixed: it is now reported, not absorbed, and the reconciliation line accounts
for all four headings in the fixture. Good.

**But the coordinator's own instruction was "try to make the counts balance
while hiding a fact" — and I could.** The fix works by first finding
candidates with a broad regex, `CANDIDATE_HEADING = /^## (\d+)\S*/`, then
classifying each candidate as well-formed or malformed. That regex is still
a strict literal match on `"## "` (two hashes, one space) at the true start
of the line. I built a second fixture
(`test-frame-fixture2.md`, scratchpad, not committed) with three heading
shapes that never become a *candidate* at all, so they never enter the
partition the "reconciled" line accounts for:

```
$ node D:/AddictedtoAI/scripts/check-frame.mjs "<scratchpad>/test-frame-fixture2.md"
test-frame-fixture2.md check -- 2 candidate heading(s): 1 well-formed, 1 malformed heading(s), 0 malformed body

FAIL        17. 17: A colon instead of a period (the original round-171 case) -- malformed heading, does not match "## N. Title": ...
verified    1. A normal fact with a real check

reconciled: 2 candidate heading(s) = 1 well-formed fact(s) + 1 malformed heading(s) + 0 malformed body
```

The fixture has **5** numbered headings (facts 1, 17, 18, 19, 20 — the last
three using `##18.` [no space], `##  19.` [two spaces], and `### 20.` [three
hashes]). Only 2 are found. Facts 18, 19, and 20 are silently absorbed into
the previous chunk's body text exactly the way fact "17:" was before this
fix — not reported, not counted, invisible — and the `reconciled:` line
balances cleanly (2 = 1 + 1 + 0) against the wrong total. This is the
identical failure the round's own header comment claims to have eliminated:

> `// EVERY CANDIDATE HEADING IS EITHER PARSED OR REPORTED MALFORMED --
> NEVER SILENTLY DROPPED.`

That sentence is false as written. It is true only for headings that already
match `^## \d+`; it says nothing about headings that don't reach candidacy
in the first place, which is exactly where the vulnerability still lives.

**Why the "reconciled" arithmetic can't catch this, structurally.** The
invariant `boundaries.length === wellFormed.length + malformedHeadings.length
+ malformedBody.length` is not a correctness check on completeness — it is
true by construction, always, because `wellFormed`, `malformedHeadings`, and
`malformedBody` are computed as a partition *of the candidates the regex
already found*. Printing it and calling it "reconciled" reads as reassurance
that nothing is missing, but it can only ever detect a bug in how already-found
candidates get classified, never a bug in whether candidacy-detection itself
is complete. That is the same shape of false confidence the coordinator's
own instruction was fishing for, one layer downstream of where the round
fixed it.

**A concrete fix, if the maintainer wants one:** either broaden
`CANDIDATE_HEADING` to also match variable spacing and heading level (e.g.
`/^#{2,4}\s*(\d+)/`), or — closer to how the round already solved this
exact shape of problem for fact 14 — add a second, independent measurement:
count lines anywhere in the file matching a much looser "this looks like it
wants to be a numbered fact" pattern (say, `/^#{0,4}\s{0,3}\d+[.:]/`) and
fail loudly if that count disagrees with `boundaries.length`, the same
"two methods must agree" design already used for the charter rule count.

This is a real, reproduced finding, but narrower than the original: the
concretely-reported colon-typo case is fixed, current `FRAME.md` is
unaffected (all 18 of its headings are well-formed, confirmed by the live
run below), and the remaining gap requires a less common typo. I'm reporting
it because it was specifically what I was asked to try, I found it on the
first attempt, and the header comment's absolute claim is not qualified
anywhere in the file.
