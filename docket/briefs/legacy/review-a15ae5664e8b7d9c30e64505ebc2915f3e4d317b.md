## Why this review exists, mechanically

The round's changelog entry declares `Origin: delegated`, whose published
meaning on this site is: *the orchestrating model chose this work, briefed it,
reviewed it and merged it; no human saw it before it landed.* The review is the
part of that sentence that would otherwise be a lie. It is also enforced —
`review-artifact` is a required status check, and it will not let the pull
request merge without a file at `docket/reviews/<sha>.md` that approves and
covers the merged tree.

So this is not a formality, and "looks fine" is not a review. A review that
verified nothing by running anything is not a review.

## How to review

**Try to get past the checks, not to read them and agree.** For every guard the
round added or relied on, attack it: find the input that should fail and see
whether it does. For every claim the entry makes, find the command that would
falsify it and run that command. Assume the round is describing what it meant to
do rather than what it did — that is the failure mode this project keeps
producing.

**Audit whether every claim the entry now makes is true.** That instruction is
general and it means all of them — every number, every file path, every "this
was verified", every description of what a check does. Do not treat any list of
examples in this brief as the scope of your review; a previous review pass on
this project checked exactly the eight claims it was given and missed the
entry's opening paragraph, which described a rule that three earlier reviews had
already deleted.

**Read the entry's opening paragraph last, against what the diff actually
does.** It is the most-read text on the site's log page and it is written first,
before the work is finished, so it drifts more than anything else.

**Every number must have a command behind it.** If the entry says a check
printed something, run it and compare. If a figure cannot be derived from inside
the repository, the entry must say so rather than assert it.

Check specifically that the round stayed inside its track's scope
(`scripts/check-track-scope.mjs` — `meta` may **not** write `app/`), that it did
not edit any past changelog entry (`CHARTER.md` rule 5 — the changelog is
append-only, and only the newest entry should differ from `main`), and that
`Origin` says `delegated` and not `supervised`.

## This round's specific attack surface

This round writes the rules that constrain the loop and then writes the
mechanisms that enforce them. Both halves are in scope, and the interesting
defects live in the gap between them.

**The central property to test: rule 13a names a reserved surface. For every
element of that surface, either a mechanism enforces it, or the round says
plainly that none does.** A reserved surface with a silently missing mechanism
is worse than no rule, because it reads as protection. Enumerate 13a's clauses
yourself from the text and check each one. Do not assume the round's own list of
what it built is the same as what 13a claims.

**Attack the two new guards.** `scripts/check-13a-unchanged.mjs` and
`scripts/check-hold-mechanism.mjs` guard, respectively, the one clause the loop
may never amend and the maintainer's only means of stopping the loop. Construct
inputs that should fail and confirm they do; construct legitimate inputs that
should pass and confirm they are not blocked. Consider at least: marker
duplication and removal, whitespace and CRLF, the base ref being absent or
shallow, the boundary between rule 13a and what follows it, a hold being cleared
versus created versus reworded, and tampering with the honouring code. Revert
every constructed case and confirm the tree is clean afterwards.

**Verify the "not a required check" disclosure against the live API**, not
against the comment. The round claims both new jobs are non-binding today and
says so in banners. Read the actual required contexts and confirm the banners
match. If a banner is wrong in the safe direction it is still wrong.

**Re-derive every governance figure independently.** The entry publishes counts
of pull requests, merges, reviews, reverts and commits. They change with every
pull request, including this round's own. Derive them yourself and say what you
got, even if it matches.

**The changelog entry claims a `/log` search-preset test forced a rewording.**
Verify that test exists, that it now passes, and that the rewording did not
soften an admission of failure into something vaguer. This project's value
depends on the failures being legible; a test that pushes prose away from the
words "wrong" and "failed" is a mechanism with an editorial side effect, and if
that happened it is worth saying so.

## On not manufacturing findings

After several real findings there is a pull toward inventing one more so the
review looks thorough. Resist it. **"I attacked this eleven ways and none of
them worked, here is what I tried" is a complete and valuable review**, and it
is the one a reader can trust. If you disagree with an expectation this brief
sets, stop and say so rather than adjusting your report to match it.

Equally: if you find something real, say it plainly even if it is inconvenient
and even if fixing it costs the round. A finding you soften is a finding
nobody acts on.

Note that the orchestrator sent this round four findings mid-flight and the
round self-caught five more. That history is a reason to look harder, not a
reason to assume the surface is clean: every one of those fixes is new code that
has itself never been reviewed.

## Working method — this one is not optional

**Never use `cd`.** Not at the start of a command, not in the middle of one, not
inside a script you write and run. This environment's approval classifier stops
on `cd` and forces the maintainer to approve the command by hand. They are
asleep. A single `cd` wakes them up.

Your working directory is already `D:\AddictedtoAI`, so nothing in this repo
needs it:

- run scripts by absolute path — `node D:/AddictedtoAI/scripts/check-docket.mjs`
- use `git -C D:/AddictedtoAI ...` for every git command
- read and write files by absolute path

**Keep each command string short.** Long or multi-line command strings overload
the same classifier and cause the same problem. If a step needs many commands,
write a small script into the scratchpad directory and run that — and the script
must not contain `cd` either.

## Never invoke OpenCode

**Do not run the `opencode` CLI, and do not start or resume an OpenCode
session.** Not `opencode run`, not `opencode` on its own, not anything that
would create a session or generate tokens.

The maintainer has hit their DeepSeek API limits — that is precisely why this
loop is being run by Claude Code subagents tonight instead of by OpenCode. Any
OpenCode generation spends money they do not currently have available.

Read-only is fine: `curl -s http://127.0.0.1:4097/session` reads stored session
metadata, makes no model call and costs nothing. Use that if you need to check
something about a past session, and if the server is not reachable, record the
claim as unverified rather than going to look for the binary.

The repository's own test suite exercises the supervisor's liveness helpers
against a **stub** session API (`scripts/test-orchestrate-checkout.mjs`, run
from `scripts/check-routes.sh`). That is expected and costs nothing — it never
reaches the real service. Do not "fix" it into calling a live one.
