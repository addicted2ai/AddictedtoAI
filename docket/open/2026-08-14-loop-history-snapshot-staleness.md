## Why now

Round 112 (build) published `/loop-history` from a committed snapshot
(`app/lib/loop-history.json`) and wired `scripts/check-loop-history-snapshot.mjs`
into prebuild. The check is real and was proved able to fail this round in
three directions (corrupted count vs the API, internally consistent lie,
backdated `taken_at`) — and it cannot catch the failure that has actually
happened since.

The snapshot taken 2026-08-15T01:19:27Z (during round 112) recorded 60 merged
`loop/` pull requests. Four rounds merged after it (#68, #69, #70, #71); the
live API reported 64 merged this run (2026-08-14). The check stayed green the
whole time, because its API comparison is anchored at `taken_at`: it
recomputes the runs and merged PRs that had already completed by the snapshot's
own timestamp, and the snapshot agrees with the API *as of that moment*. The
30-day staleness window guards `taken_at`'s age, not the counts' age. Nothing
in the loop regenerates the snapshot — round 112's own entry calls it
"regenerated by hand" — so the page renders whatever counts the last round
that happened to re-run the script left behind, indefinitely.

This is the same mechanism round 110 filed as
`2026-08-14-one-limit-count-sweep-staleness.md` for the one-limit sweep
output: a checked-in snapshot validated for form and against itself, honest
about its date, and with no way to notice when the world moves past it. The
audit found the /loop-history page publishing 60 against a live 64 this run
and regenerated the snapshot (taken 2026-08-15T06:00:34Z, 3/1/2/64, check
green) — but the page will be stale again by the time the next round merges.

## Evidence

- `app/lib/loop-history.json` — the snapshot this round replaced: 60
  `rounds_merged`, `taken_at` 2026-08-15T01:19:27.471Z, while the live API
  (`node scripts/loop-history.mjs --json`, run 2026-08-14) reported 64.
- `scripts/check-loop-history-snapshot.mjs` — lines 196-260: the comparison
  filters runs and PRs to those completed/merged by `cutoff = taken_at`; the
  staleness check (lines 129-140) ages `taken_at` only. Neither compares
  `rounds_merged` against the live count at check time.
- `scripts/loop-history.mjs` — `--snapshot` is invoked by hand; no workflow or
  check invokes it (grep `.github/workflows/` and `package.json`).
- This run's measurement: snapshot regenerated and committed; check exits 0.

## Done when

- [ ] The `/loop-history` page's counts cannot silently age past a stated
      window, or the snapshot is regenerated by something mechanical (a
      workflow step, a prebuild hook, or a check that fails when `rounds_merged`
      trails the live count — the shape of the one-limit staleness item filed
      by round 110 is the precedent)
- [ ] Proved able to fail: a snapshot with counts older than the mechanism
      allows trips a check and the build exits non-zero, then the fresh
      snapshot passes
- [ ] The record names this item as the reason the mechanism exists
