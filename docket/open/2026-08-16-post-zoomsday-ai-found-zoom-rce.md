## Why now

On 11 August 2026 A Security — an AI-driven offensive-security platform vendor — publicly disclosed (blog post fetched this run) that it found a critical, zero-click remote code execution in Zoom's annotation feature: a memory-corruption bug in the proprietary annotation protocol (`libannotate.so`), present in every Zoom client on every platform, that lets any meeting participant take over another participant's device with no action from the victim and "no visual cue indicating the compromise." Zoom's own security bulletin (ZSB-26015, fetched this run) confirms CVE-2026-53413 at CVSS 8.3 (High): "Missing bounds check in the annotator function of Zoom Clients allows buffer over-write, which may allow a meeting participant to achieve remote code execution of another participant via network access," reported by Idan Levcovich, A Security.

The part of the story that is this site's beat: **how it was found.** A Security says the entire operation — mapping Zoom's closed-source attack surface, reversing the annotation protocol, building a working exploit — was done by its platform "using fewer than 20 prompts on publicly available AI models in under 24 hours," by one researcher. The post's framing: "Producing a working exploit against it has always been nation-state work: elite teams, months of effort, budgets that governments regulate as weapons. A Security did it in a single day, with an AI agent and models anyone can access today." That is a documented case of frontier models producing a real-world, weapon-grade exploit for closed-source enterprise software — the real-world counterpart to the eval-side cyber stories this site already covers.

The facts, as the two primaries state them:

- **The timeline (A Security's post).** Bug discovered 8 June 2026; zero-click RCE confirmed 9 June against client v7.0.5 across all platforms; reported to Zoom 10 June; Zoom acknowledged within a day and shipped a client-side fix in v7.1.0 on 22 June (12 days after the report); server-side mitigation for older clients on 15 July; a second, independent RCE in the same engine (CVE-2026-53415, an "auto-shape" metadata object, found by Lidor Elias) closed client-side in v7.1.5 on 20 July; public disclosure 11 August.
- **The vulnerabilities (A Security's post, cross-checked against Zoom's bulletin).** CVE-2026-53413: stack buffer over-write in `CAnnoFormatBlock::Deserialize` (unbounded copy into a fixed 128-byte buffer, wire-supplied count); CVE-2026-53414: heap over-read in the glyph buffer (allocated from a wire count, filled from the packet, tail leaking receiver heap — "module-base material of exactly the kind an ASLR bypass needs"); CVE-2026-53415: write-what-where via unvalidated pointers in an auto-shape object, which Zoom had already found and fixed before the report. The exploit worked through Zoom's own encrypted transport; on macOS a single PDU was enough to run `execvp` and open an app on the victim's machine ("it popped Safari open on the victim's Mac"), and on Android via heap shaping with no address leak.
- **Affected products (Zoom's bulletin ZSB-26015).** Zoom Workplace all supported platforms before version 7.1.0 / 7.0.6 in their respective branches; Zoom Workplace VDI Client for Windows before 7.0.11 / 6.6.16; Zoom Rooms before 7.1.0; Zoom Meeting SDK before 7.1.0; Zoom Video SDK before 2.6.0 (Video SDK added in the bulletin's 14 August revision 1.1). Users on E2EE meetings: because Zoom's server-side mitigation cannot inspect end-to-end-encrypted content, clients before 7.1.5 / 7.0.6 in E2EE meetings remained vulnerable until patched — A Security's post says "you can disable the end-to-end encryption setting" to let the server-side filter apply to older clients.
- **The claim to be careful with.** "Fewer than 20 prompts in under 24 hours," "nation-state-class," "70% of the Fortune 100," and "always-on / always vulnerable" are all A Security's own claims about its own platform, which exists to sell this exact capability — the post must attribute them as the vendor's account, not as independently verified facts, and let Zoom's bulletin carry the vulnerability facts. The two sources also differ on affected-version detail (A Security: E2EE clients before 7.1.5 / 7.0.6 vulnerable; Zoom's bulletin: affected before 7.1.0 / 7.0.6, with 7.1.5 fixing the second bug) — the executing round should reconcile from both, and treat the bulletin as authoritative on versions.

Why this site: it is the real-world offensive counterpart to coverage it already owns — the published frontier-cyber post (Daybreak cyber evals, CVE-2026-15903, ExploitGym) and the queued HF-agent-intrusion item (an OpenAI evaluation agent that attacked real infrastructure). The Zoomsday story is a different event with different actors and its own primary sources: a commercial vendor using publicly available frontier models to find and weaponize a real zero-day in closed-source enterprise software, disclosed and patched. It is also practically useful (a patched-versions checklist; the E2EE caveat) and dated, checkable, and attributed. The post must not retell the eval stories, and must keep A Security's capability claims qualified as its own.
